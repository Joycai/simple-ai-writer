# 长输出保存与恢复

> 状态：`shipped` · 版本：1.94.0。

## 问题与取舍

聊天原来在回合结束时保存，任务面板的版本只在内存中。网络错误能留下界面上已经收到的文字，
但进程崩溃不会经过 `finally`，一篇正在生成的长文可能整段丢失。

现在把**可见正文**单独保存到项目数据库 `output_recovery`，与会话的可执行历史分离。
恢复只生成文本，不复原工具调用、审批授权或未完成的工具参数。这样做的理由是：
一份中途保存的工具历史可能停在「写入已执行、结果还没入历史」之间，重放会重复修改文件。
原聊天、审批流程和任务输出继续使用原来的运行路径。

## 保存契约

- 聊天每回合、任务每个版本各有 UUID，绑定启动时的项目与模型，切项目不会改写归属。
- 流式输出每 1.5 秒尝试写入 SQLite；这不是等待安静后的 debounce，持续有字也会保存。
- 同一输出只有一个在途写入，待写快照采用最新值；结束时等待写入并保存最终状态。
- SQL 使用单条 UPSERT 原子更新。写失败保留待写内容、显示失败提示，并在后续保存时重试。
- 恢复记录包含请求的文本上下文、正文、模型 ID、状态和时间；不存渠道密钥、图片字节、
  工具调用或工具结果。历史中的文字素材会随项目数据库保留，与项目备份一起走。
- 成功输出也保留，避免任务面板结束后尚未插入正文或复制时崩溃导致丢失。
  不按数量自动淘汰作者的文字，作者在「已保存的输出」中复制、保留或丢弃。
- 正在保存的运行不在恢复列表中提供再次运行按钮。启动后读到 `streaming` 状态时，
  显示为 `interrupted`，绝不自动发起付费请求。

1.5 秒是尝试保存的间隔，不是硬性数据丢失上限：磁盘失败、I/O 延迟或突然断电仍可能使最近
尚未提交的内容丢失。界面里的文字不因此清空，保存失败提示也不能显示为「已成功存盘」。

## 续写与分节

「继续写」使用原模型发起新的纯文本请求，重新取得当前密钥与模型配置，系统提示词仍经
`profileSystemPrompt()`，带当前时间。原来的文本作为参考交给模型，新字只追加，绝不替换原文。
图片不会自动重新上传；恢复需要图片或未保存的工具结果时，作者需要另外提供素材。
服务端工具也关闭，因而恢复不可能重放写文件动作。

这不是原服务端流的精确续传，不能保证用词、衔接或重复完全一致。界面明确要求检查衔接。
原模型已删除或已不适合文本会话时，显示错误，不悄悄切换渠道或模型。整个请求仍受现有上下文
预检约束，不为了续写静默裁掉原指令或已保存正文。

可选的「分节生成长文」由作者填写写作要求、素材和逐行大纲（最多 20 节），使用当前所选模型。
完整大纲和已有正文随每一节发送，保持行文连贯；每节单独计费，经 `recordUsage` 记入两本账。
完成的节先提交正文与下一个节序号，再请求下一节。保存失败、网络失败或输出上限都会暂停，
续写从保存的节序号继续；上限截断不前移节序号。没有返回正文也不会悄悄推进大纲。
自动生成大纲、自动合并进编辑器和跨模型恢复不在这一版内。

## 流结束判断

连接关闭本身不算完成。Chat Completions 必须有 `[DONE]` 或明确的 `finish_reason`；
Responses 必须有终止事件；Anthropic 必须有 `message_stop`；Gemini 必须有 `finishReason`。
DashScope 原来就要求最后一帧的 `finish_reason`，保持不变。裸 EOF 抛出中断，已有正文保留，
未完成的工具参数不交给运行时执行。输出上限仍沿现有 `truncated` 通道处理。

这是应用的保守兼容性选择：只发正文而省略全部结束证据的兼容端点会被标成中断，
作者仍可复制或保留内容，而不是应用替端点猜测「已经完成」。

## 代码与验证

- `lib/agent/outputRecovery.ts`：记录格式、SQL 和串行周期写入器。
- `stores/outputRecoveryStore.ts`：恢复列表、项目隔离、纯文本续写及分节编排。
- `stores/agent/chatJob.ts` / `stores/aiTaskStore.ts`：捕获流式正文与结束状态。
- `components/ai/OutputRecoveryPanel.tsx`：聊天和任务面板共用入口，双语文案，沿用主题令牌。
- 定时写入、写入竞态、失败重试、重启状态、项目切换、无工具恢复、分节游标和逐请求记账有单测。
- 四个协议族的裸 EOF / 结束证据使用模拟流验证，不需要付费渠道。

# 工作流卡 · 概要设计

> **Status: planned** · 2026-08-23 审定
> 方向与设计已定（A 类：提示词式、best-effort）。审定时的追加：**内置卡随 app 发布，
> 开箱即用；项目目录里同 id 的文件整张覆盖内置**（见 §2）。

## 1. 问题

Agent 对"有既定套路的任务"会自由发挥流程。实录（日中翻译 + 词典，2026-08-23）：模型
习惯性地 ① 调 `translate` 生成 `.zh.md` → ② 重读原文和译文、拿词典逐条"校对" → ③ 重写
译文文件。第 ②③ 步是纯浪费——`enforceGlossary` 在写盘前已把词典强制落实，模型不知道，
于是花主模型的 token 复核一件代码已经保证的事。

翻译这一例的根治走的是 B 类（流程写死在工具里，见 §6），但同类问题会不断出现：作者想
固定的流程（输出格式约定、多步套路、先问什么再做什么）没有一个不写代码就能落的地方。

**目标**：作者用纯数据（一个 markdown 文件）写下一段流程指引；匹配的任务出现时它进入
模型的上下文。**Best-effort**——作者明确接受"大部分时候有效，偏了任务也还能完成"，
以此换来不改代码就能新增/修改工作流。

**非目标**：100% 遵循。必须保证的行为（词典必然落实、审批必然弹卡）只能是 B 类——
整条流水线塞进一次工具调用，translate / imagegen / batch / 一致性检查已是四个先例。
两类并存，互不替代。

## 2. 形态：一个工作流 = 一个文件

```
.ai-writer/workflows/<id>.md
---
name: 翻译输出格式
description: 作者要翻译日文文档时，先确认输出格式再动手
---
1. 先问作者要纯译文还是对照输出；对照再问译文在前还是原文在前。
2. 对照格式样例：
   > 原文行
   译文行
3. 确认后调 translate 工具，...
```

- frontmatter：`name`（清单里显示）、`description`（一行，模型判断"该不该加载"的唯一
  依据，限长 ~60 字）、`disabled: true`（可选，停用但保留）。复用 `parseFrontmatter`。
- 正文：自由 markdown——步骤、样例、格式模板。给模型看的，不注入任何正文写作上下文。
  内置卡正文不走 i18n：读者是模型，不是 UI。
- **内置 + 项目覆盖**（审定追加）：app 自带一组内置卡（`lib/workflow/builtins.ts`），
  开箱即用；`.ai-writer/workflows/<id>.md` 与内置同 id 时**整张替换**（含 `disabled: true`
  时隐藏该内置卡），不同 id 则是项目新增。覆盖是整张而不是逐字段合并——半张来自文件
  半张来自内置的卡没法讲清楚是谁的。第一张内置卡：「翻译输出格式」（§6 的 dogfood）。
- **项目级**。工作流描述的是"这个项目里的活怎么干"，跟着项目走。

## 3. 注入机制：两级渐进披露

照 Claude Code skill 的形态，而不是关键词自动注入：

- **索引恒在**：agent briefing（`ai.instructions.agent` 那一层）末尾追加一段「可用工作流」，
  一行一个 `name — description`。没有工作流时整段不出现，零成本。
- **正文按需**：新增只读工具 `read_workflow(name)` 返回正文。模型认为当前任务匹配某行
  描述时自己加载——加载动作在执行日志里就是一次普通工具调用，作者可见可查。
- **为什么不做关键词触发自动注入正文**：匹配不可靠（中文任务描述和触发词的对齐是猜的），
  且正文进固定头部就是每轮都付费。清单一行的成本可控，且被 agent-tool-context 的账管着。

接线范围：`AGENT_ASSIST_PRESET`（chat + AiPanel Agent 模式）。**不进**批量跑（无对话可
偏离）、lore 生成模态（流程已固定）、扮演 preset（隔离是结构性的，见 roleplay 文档）。

成本账（`docs/feature/agent/agent-tool-context.md` 的规矩）：`read_workflow` 的 schema
会撞 `agentToolBudget.test.ts` 的棘轮——同 commit 抬上限并说明；清单文本按行数上限
（建议 ≤10 个工作流进清单）封顶。

## 4. 为什么不放知识库、不做成 pack 任务

- **不进 `loreIndex`**：老论证（roleplay 记忆区同款）——并进去，隔离就从"它不在那里"
  降级成一个要处处正确的过滤器：一致性检查会把流程指令当正文扫矛盾，注入引擎会按别名
  命中它。工作流是给模型的指令，不是作品知识，住自己的目录。
- **不做成 pack 任务**：pack 任务是"一次调用的 prompt + tools"，作者点菜单触发；工作流
  是**跨多次工具调用的行为指引**，在对话中被动生效。且 pack 是代码内置数据，作者不写代码。
- 命名避开「技能」：novel pack 的知识库分类已有 技能（角色技能），UI 词用**工作流**。

## 5. UI（最小面）

Settings → 工作台（已是项目级 pane）加一节「工作流」：列表（名字 + 描述 + 启停开关）+
新建/编辑 drawer（name / description / 正文 textarea）。执行期间零额外 UI——"对用户
隐蔽"的部分就是它不打断任何流程。

开放问题：入口放工作台还是知识库墙独立 tab（倾向工作台：它不是知识库内容，见 §4）。

## 6. 与翻译 case 的关系

翻译的三小片仍按已议定的 B 类修（工具返回文本明说"词典已落实，勿重读校对"、`format`
对照参数、强制替换统计）——工作流卡挡不住那个浪费的根因（模型不知道 enforceGlossary
已发生，这是**信息缺失**，不是流程缺失）。第一个示例工作流卡可以做「翻译输出格式」
（§2 样例）当 dogfood：B 类保证机械正确性，A 类固定对话套路，两层恰好各管各的。

PR 1 / PR 2 实现记录：

- **注入点是两处，不是一处**：chat 的 system 层（`agentStore.sendChat`，与 briefing 同层同稳定性，**每会话播种一次**——会话中改卡下个会话生效）和 AiPanel 的任务 instruction 尾部（`aiTaskStore`，条件是 `task.tools === "full"`——按声明的工具档位匹配，绝不按任务 id）。
- `read_workflow` 是**常驻**工具（不进 `lore_write` 那种延迟装载组）：它服务的清单从第一轮就在 briefing 里，工具却要等装载就自相矛盾。实测 134 token，棘轮 10,000 → 10,150、常驻 7,400 → 7,500（`agentToolBudget.test.ts` 同 commit 抬）。
- 名字打错时工具回**可用卡清单**而不是干巴巴的失败——模型下一轮自己就能修正。
| PR 3 | Settings → 工作台 的管理节 + i18n | 真机：增删改停 |

每片一个 PR，片间停下等真机验证（老规矩）。

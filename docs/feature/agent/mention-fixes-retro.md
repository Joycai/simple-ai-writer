# `@` 引用三轮修复复盘 —— 为什么一直收不住

> 状态：`research` · 2026-09-27。复盘对象：#708（`fix/mention-caret-send`）与 #709（`fix/mention-cross-instance`，前后两段）。方案本身的决定与理由在 [`mention-scope-ui-brief.md`](mention-scope-ui-brief.md) 的三节「后续修复」里，这里只回答三个问题：为什么重复了这么多轮，为什么每次 review 都冒新问题，为什么修一轮又冒一轮。
>
> 修订（同日）：初版把根因归到「方案形状」和「范围来源」。作者的判断更准：**问题在做法——一直在代码里打补丁，没有拿已有逻辑和新需求在模块 / 功能层面重构。** 形状不对是结果，一直不换形状是选择。结论与第「零」节按此改写，一、二两节是这个根因的表现。

## 结论

不是 review 太严，也不是运气，也不只是问题本身难。根因是**做法**：每一轮新需求落到已有代码上时，都把现有结构当前提，只问「在哪加一个判断」，没问「这个模块现在要负责的事变了，它的形状还对不对」。结果是等待中的 `@` 引用（claim）从头到尾都是「组件 hook 里的一个偏移量」，而需求早已变成「多实例共用草稿、多方写入、读取是异步的」——于是只能在 `editRange` 这个单段启发式上一层层补。再叠上**范围的来源**（每一轮由上一轮的遗留定），循环就停不下来。修复自己引入的回归集中在最后一段，正是补丁叠到第三层的时候。

## 经过

| 轮次 | 范围怎么来的 | review 发现（单片 / 整体） | 其中由修复引入 |
|---|---|---|---|
| #708 | #704 留下的 3 个 bug（光标跳末尾、选区塌成点、读文件期间点发送） | 5 / 6 | 0 |
| #709 前半 | #708 记下的 2 个缺口（读取失败只作用于发起的实例、扮演面板认不出外来改动） | 5 / 5 | 0 |
| #709 后半 | 前半收尾时列出的 2 条剩余问题 | 3 / 6 | 4 |

每一轮都在两处续上下一轮：收尾写进「未做、可做」的条目，和 review 的附带发现。第三段是因为 `/goal` 的 stop hook 把「这两个已知问题」理解成最后列出的两条，才又开了一段。

## 零、根因：补丁代替了重构

### 错过的重构点

| 轮次 | 新需求实际说明了什么 | 该做的模块层面改动 | 实际做的 |
|---|---|---|---|
| #704 / #708 | 引用不只由作者在一个输入框里打出来 | 定下「谁拥有草稿与 claim、谁能写」 | claim 留在 `useMentionState` 的 `useRef` 里，偏移量靠光标修正 |
| #709 前半 | 多个实例共用同一份草稿，读取失败要跨实例生效——草稿在 `composerStore`，claim 却在组件里，归属已经错位 | 把草稿与 claim 放到同一个拥有者，按槽位管，只留一个写入口，平移在入口里统一做 | 另加一张按槽位的失败表（`mentionReads`）；每个宿主的每处写入包一层 `useOwnDraft` |
| #709 后半 | 非打字的改写（图例、片段、回退、清空）也要带着 claim 走 | 同上——有了唯一写入口，这一段不存在 | 在 `editRange` 上加光标提示、Myers 按字对齐、glued 守卫 |

### 当时就有的信号

结构不合适了，代码里是看得见的，三样都出现过：

- **同一个包装要在每个调用点重复加**：`useOwnDraft` 要包住每个宿主的每一处写入，漏一处就错。
- **状态要在两处之间来回同步**：草稿在 store、claim 在组件，`external` / `shiftClaims` 就是为了追平两边。
- **启发式要靠调用方递提示**：`editRange` 分不清插在哪边，于是要宿主把光标传进来。

每一样都被当成「再补一处」，没被当成「该重构了」。

### 为什么一直选补丁

- review 的发现是一条一条来的，天然引向局部修法；修法冲着那一条反例去，下一条换个角度又来。
- 默认把现有结构当前提，没把「模块现在负责什么」和「新需求要它负责什么」并排写出来比。
- `/goal` 的推进节奏下，不愿停下来提议一个更大的改动——但更大的改动恰恰是更小的总成本。

下面两节讲的现象——review 总有新问题、修一轮又冒一轮——都是这个根因的表现。

## 一、为什么每次 review 都有新问题

### 1. 这是一个多方改同一段文本、还要追位置的同步问题，却一直用局部补丁解

能改草稿的来源：

- 作者打字（提名开着 / 关掉两种状态）；
- 「+ 引用」、扮演图例、片段、开场白、回退、发送清空；
- 另一个实例的落字（已卸载的、还没渲染的、同一 tick 里两次的）；
- 知识库弹窗；
- 项目重置。

跟时序相关的变量：

- React 渲染 / 提交 / effect 的先后；
- `useSyncExternalStore` 的微任务；
- effect 里的更新是否与 store 通知合批；
- 抽屉退场动画；
- StrictMode。

每修一条，只处理了 review 举出来的那一个「来源 × 时序」组合；下一轮换一个组合，就又是一条。大部分发现属于这一类——同一个模型的另一个角。review 循环测出来的是补丁的覆盖面，不是方案收没收敛。

### 2. 位置映射只有 `editRange` 一个启发式，它原理上就有盲区

它把一次改动压成「一段替换」，于是这三种读不对：

- **两头同时改**：图例把整行套上 `*…*`。
- **前后各改一处被合成一段**：旧实例落字前追一次改动。
- **插入 / 删除的字与邻字重复**：`@@潮`，读不出在哪一边。

后来加的按字对齐（Myers）、光标提示、glued 守卫，都是在这个启发式上再打补丁，每个补丁又带来自己的边界（glued 守卫第一次就放错了层）。

### 3. 从没有先把「谁会写这份草稿」列全

第三段以为只是「非打字的改写」，定位时才发现打字也一样；知识库输入框也是中途才补上。如果设计阶段先把**所有写入方 × 所有状态**列成表逐格核，review 后来一条条挖出来的，大部分当时就看得见。

## 二、为什么修一轮又冒一轮

### 1. 修法冲着反例去，没检查对称的另一面

这是最直接的原因，四条回归都是这么来的：

- review 指出 `@@潮` 会被新提名接管 → 改成一律按最左读法（`lo`）→ 修好了「插在前面」，弄坏了「空 `@` 紧后面插 ` @`」和「退格删回去」。两种读法本来各对一半，最后改为按宿主写完后的光标判断。
- review 指出空查询、glued 的 claim 会被当成带过去 → 把守卫放进共用的对齐步骤 → 自己点图例时 glued 的 claim 又带不走了。守卫只该拦别的实例的落字，最后挪进 `shiftClaims`。

两次都是在出问题的那一点加条件，没回头问「这个条件对其他调用方意味着什么」。

### 2. 测试与修复同一个人写，盲区也一样

- 图例的测试手写了一个只在行首插 `*` 的字符串，真实的 `applyLineKind` 是两头一起改——测试绿，bug 在。
- 浏览器 harness 是照抄宿主逻辑的替身，验证的是抄写，不是宿主。
- vitest 只有 node，宿主里接线的那几行始终只有代码路径。

### 3. 没有能自动找反例的测试

「随机编辑序列之后，claim 仍指向作者原来那个 `@`」正适合性质测试（随机编辑 + 不变量断言）。`lo` 与贪心读法的不对称，用它几分钟就能暴露，不必等 review 一轮轮撞。

### 4. 流程放大

- `/goal` 要求不停下来问，设计与计划的确认门都跳过了，方案在写代码之前没被质疑过。
- 每轮结尾都列「剩余已知问题」，review 的附带发现照单记下，这些列表自然成了下一轮的范围。
- 没有给出停止判断。后面很多问题窗口极窄（同一 tick、退场动画、读的期间关项目），应早点把「修它的成本 vs 它的影响」摆出来，由作者决定记下不修还是换方案。

## 三、下次怎么做

1. **新需求落到已有代码上，先重推模块形状，再决定补还是重构。** 设计阶段把「模块现在负责什么」与「新需求要它负责什么」并排写出来，明确判断现有形状还合不合适；出现第零节那三种信号之一，就把重构方案和代价交给作者看，而不是先补。这一条是主动的，第 5 条的停止线只是事后兜底。本块的重构候选（未评估，作为 `proposal`）：
   - 草稿与 claim 归同一个拥有者：所有草稿写入收进 store 里的一个入口，按槽位维护 claim 表，在这个入口统一平移——而不是分散在各宿主、各实例、各 hook（即 #709 前半错过的那次重构）；
   - 落字时按内容就近找 `@query`，不信任偏移量（`editRange` 的注释记着「按光标找」试过三种失败，按内容找的代价是重复的 `@query` 有歧义）。
2. **设计阶段先交一张表**：所有写入方 × 所有状态，每格写怎么处理；review 拿这张表核，而不是自由找角落。
3. **测试直接调真实产生改动的函数**（`applyLineKind`、宿主里拼 `@` 的逻辑），不手写「以为它会产生的字符串」；加一个随机编辑序列的性质测试守不变量。
4. **修 review 的问题时写出这个修法对其他调用方、对称情况的影响**；说不清就先不改。
5. **按严重程度定停止线**：窄窗口、低严重度的记下，由作者决定修不修，不自动成为下一轮的范围；连续两轮出现回归，停下来提议换方案，而不是继续修。
6. **确认门不因 `/goal` 跳过**：至少把设计的关键取舍摊出来给作者看一次。

## 现状

三轮之后这套机制在已知场景下都对：单测 + 预览替身核过，已知取舍记在 brief「后续修复」各节。但它是三层补丁叠出来的，第三节的两个重构候选**没有做**。下次再碰这块，起点是先做那次重构，而不是在现有结构上再补。

# 三条上下文计量条

> 状态：`living`。
> 改 `lib/context/forecast.ts`、`lib/agent/contextBreakdown.ts`、`ContextBar.tsx`
> 或 AiPanel 的 `ContextAllocation` 之前读它。

应用里有三条形状相似的横条，回答的却不是同一个问题。它们相互抄错过一次，也各自
错过——这份文档记的是**哪些必须一致、哪些故意不一致**。

| 条 | 在哪 | 回答什么 | 数据在哪 |
|---|---|---|---|
| 上下文分配 | 生成（AiPanel） | **这一次请求**会把窗口切成什么样 | `lib/context/forecast.ts` |
| 上下文构成 | 助手 / 扮演（`ContextBar`） | **这场对话**还剩多少，离折叠多远 | `lib/agent/contextBreakdown.ts` |
| 预估态 | 扮演，首次发送之前 | 第一条请求**至少**会带多少 | 同上，`computePreflightBreakdown` |
| 核对分配条 | 一致性检查（设置区） | **一段**请求会把窗口切成什么样，文档因此要切几段 | `lib/consistency/budget.ts` |

核对那条**就是分配条**，不是第四种：段名换成 系统+工具 / 原文 / 知识库 / 前情 / 余量，
颜色沿用分配条的（原文用「选区/附加」的色——都是「这一次带进来的材料」），段的合计等于
上限这条不变量同样守着（`consistencyBudget.test.ts`）。图例恒展开、10px 凹槽，因为它
也是控件：作者改范围、换模型，段数就跟着变。它比生成那条多回答一个问题——「文档为什么
被切成 3 段」——答案写在条底下那一句里。

---

## 1. 为什么不合并成一条

一个是**预估**，另外两个是**实测**；一个量的是「一次请求」，另一个量的是「一场
对话」。合并只能靠一个既描述请求又描述会话的抽象——而那个抽象不存在：生成面板的
条上没有「对话」这一层，助手那条上没有「参考上文」这个作者能调的旋钮。

更实际的一条：**生成那条是控件，助手那条是读数。** 分配条上每一段都是作者当场能
换的东西（拿前情换条目，或者反过来）；构成条压在输入框上方，作者只是瞥一眼。这个
区别决定了下面「故意不一致」的那几条。

> 2026-09-05：分配条底下那排「窗口占用」芯片已经搬进 设置 → 上下文与记忆（一根
> 50–90% 的滑块），原地只剩标签 + 百分比 + 一条去设置的链接。**这不改变上面那句
> 话**——条上的六段仍然是作者当场能换的，搬走的是那六段共同争的那个上限，而它一次
> 定完就不用再动。理由见
> [compact-threshold-plan.md](compact-threshold-plan.md) §D。

## 2. 必须一致：颜色

**同一样东西不该在两块面板上是两个颜色。** 作者在这两栏之间来回切，两条条讲的是
同一件事的两个时刻。

| 分配条 | 构成条 | 为什么是同一样东西 |
|---|---|---|
| 系统+工具 | 系统+工具（`--color-text-dim`） | 折的是同一批东西，都不可回收 |
| 选区/附加 | 种子（`--color-border-accent`） | 都是「这一次带进来的材料」 |
| 近期 | 对话（`--color-sienna`） | 都是稿子自己的原文 |
| 条目 | 注入条目（`--color-success`） | 字面上就是同一样东西 |
| 前情 | 摘要（`--color-accent-mid`） | 都是对更早内容的压缩 |
| 余量 | 空余 | 那条留白见轨道，这条明写轨道色 |

**收敛方向是「往有出处的那一侧」**：构成条的颜色是照设计稿 02 屏 2c 的十六进制
逐段取的；分配条原来用的 `--color-alloc-lore` / `-memory` / `-tools` 是当时就地
起的三个 token，没有设计稿依据。三个 token 已随之退休（2026-08-27）。

> 验证方式：把两份 CSS module 和 `tokens.css` 拼进一张静态页，用
> `getComputedStyle` 逐段比对，明暗两套主题各跑一遍。**截图看不出这类问题**——
> 上一次「未定纹在浅色下消失」正是四个色标算出来全等、而截图上只是一条平淡的
> 米色带子。

## 3. 故意不一致

改这几条之前先想清楚是不是在把控件和读数混成一个东西。

| | 分配条 | 构成条 | 理由 |
|---|---|---|---|
| 条高 | 10px（2px 内衬 + 1px 边框） | 6px | 控件要够厚才点得动；读数只要看得见 |
| 段间距 | 2px | 0 | 同上：分段可点 vs 一条连续的量 |
| 轨道 | `--color-bg-inset` | `--color-bar-track` | 控件坐在自己的凹槽里 |
| 边框 | 恒亮 | 透明，hover 才现 | 恒亮的框在输入框上方是每条消息都要付的装饰 |
| 图例 | 恒展开 | 默认收起，点条展开 | 六个芯片在窄栏折三行，而它压着输入框 |
| 折叠竖线 | 无 | 有（可折时） | 一次性请求没有「下一轮」 |
| 超限警示 | 框变色 + 条下一句 | 框变色 + 读数变色 | 分配条的那句要说「能拿它怎么办」，因为作者手边就有旋钮 |

## 4. 各自的口径

- 构成条：`docs/feature/agent/chat-memory-plan.md` §8。
- 分配条：`src/lib/context/forecast.ts` 的文件头（#361 把它从 `AiPanel` 的
  `useMemo` 里抽出来的那一次——两个合法的 `TaskDef` 躺在同一个作用域里，是这类
  错误的温床）。

两处都记着同一类教训：**取错的那个值不会报错**。构成条曾经把折叠线画在
`上限 × 0.7` 而真实触发点在 `上限 × 0.7 + 工具 × 0.3`；分配条曾经在 Agent 模式下
把工具开销记成 0，于是承诺了 4,000 tk 的条目而实际注入零。两次都是测试全绿。

## 5. 分配条的两段固定成本

固定成本（系统提示 / 任务指令 / 选区 / 大纲 / 附加知识）原先不占段位，只让「余量」
变小。于是条的总宽是 `上限 − 固定成本`，而页脚的「预计输入」**含**它——同一屏上两
个数对不上；而润色/改写/总结里最大的那一块（选区）在条上完全看不见。

**分成两段，不是一段。** 构成条那条「不拆固定成本」的理由（拆开说不出作者能做的
事）在这里不成立：选区是作者一个手势就能改小的东西，埋进一条灰色的「固定」里算术
是对了，可作者仍然不知道是什么占满了窗口。

```
系统+工具 = 工具 schema + 系统提示 + 工具说明 + 任务指令（+ full 层的排版格式清单）
选区/附加 = 选区  ‖  大纲 + 附加知识      ← 由 runTask 决定装谁
```

上一章结尾归「近期」不归「选区/附加」：分界是**「逐字的 vs 概括的」**，不是
`planContextBudget` 把它记在哪个变量上。同理前情提要 + 全书前情并成「前情」。

不变量因此换了，`contextForecast.test.ts` 守着：**段的合计正好是上限，非 `free`
的合计正好是「预计输入」**。

## 6. 已知未做

- **工作流卡清单不算进预估。** `workflowBriefingSection` 要读盘（async），为了几百
  个 token 在组件里加异步加载 + 失效处理不划算。方向是**低估**，也就是条偏乐观。
  read 层的工具说明和 full 层的排版格式清单都算了。
- **助手没有预估态。** 新会话时只量得出工具 schema，第一条发出去后种子块一次性
  落地，条一跳。扮演的四段预估不能照搬（检索那一块在助手这边确实预先不可知），
  能搬的是「换个动词 + 撤掉那道线」，后者已经随 `canFold` 落地。

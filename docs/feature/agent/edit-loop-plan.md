# agent 编辑回路：行号契约与轮数

> 状态：`partial`（一至七期已实施：行号契约 PR #396 · 结构读与搜索上下文 PR #397 · 导出预检 + `inspect_html` PR #398 · `write` 档 PR #399 · 知识库全文检索 PR #400 · 创建回执 PR #401 · 知识库编辑寻址与回执 PR #403 · 预估只算常驻 PR #404 · 知识库读分页与 rewrite_lore_lines；还没做的见 §15）
> 起因：2026-08-30 以 Claude Code / Codex 的工具面为尺子，审阅了 HTML 生成这条链路（`create_file` → 预览 → 改 → `export_pptx`）。断的地方不在生成端，也不在预览端——在**改**这一段：模型手里从来没有一份带行号的原文，于是每一次修改都要多走一到两轮。同一把尺子随后量到 md / txt 和**知识库**：前者与 HTML 共用同一套工具，一并修好了；后者从来没有被这样量过，五期起补（§10–§14）。
> 相关：[`html-artifact-plan.md`](../html-artifact-plan.md)（HTML 交付物的由来）、[`pptx-plan.md`](../pptx-plan.md)（`read_slides` 的另一半）、[`agent-tool-context-lld.md`](agent-tool-context-lld.md)（工具 schema 的成本账）

## 1. 量纲：贵的是轮数，不是正文

工具 schema 每一轮原样重发，AGENT_ASSIST 实测 **≈ 15.1k token**（68 个工具、34,215 字符描述，`agentToolBudget.test.ts` 的棘轮量的就是它），历史也每轮重放。所以：

> **省掉一次往返 ≈ 省 15k+ token，比这条链上任何一份 HTML 正文都大。**

本文所有条目按这把尺子排序：一个把 4000 字符输出撑大 30% 的改动，只要能换掉一轮，就是净赚一个数量级。反过来，一个省下几十个 schema token 却让模型多问一次的设计，是亏的。

## 2. 现状盘点

| 环节 | 现状 | 代价 |
|---|---|---|
| `read_file` | 返回裸文本，只有末尾 trailer 写 `lines 120-232 of 900 shown`（[tools.ts](../../../src/lib/agent/tools.ts) `readWritingFile`） | 模型要在 4000 字符里自己数行；`propose_edit` 的 `find` 只能凭记忆重建缩进 |
| `rewrite_lines` 的说明 | 写着「give start_line and end_line (**the numbers read_file and search_text report**)」 | **read_file 并不报逐行行号**——说明描述的是一个不存在的契约 |
| `rewrite_lines` 成功回执 | 「…**re-read around the region** before naming another range」 | 每改一个区域固定三轮：读 → 写 → 再读 |
| `propose_edit` 成功回执 | 「Edit approved and applied.」 | 模型对改完的样子一无所知 |
| `read_slides`（.html） | 每页逐字源码，无行号（[htmlSlides.ts](../../../src/lib/pptx/htmlSlides.ts)，`lineAt()` 只在「单页超预算」那一支用） | 只能退回 `propose_edit`，把整页源码**再抄一遍**当 `find`：读 1 份 + find 1 份 + replace 1 份 |
| 找第 N 页 | 只能按 4000 字符逐段翻 | 30 页的 deck ≈ 15k token 才能定位 |
| 一轮多处编辑 | `partitionParallelSegments`（[runtime.ts](../../../src/lib/agent/runtime.ts)）**早就支持**：写调用各自成段、依次执行 | 但 `propose_edit` 说「Propose one focused edit per call」、`ai.instructions.agent` 说「写入类工具仍然逐个执行」，模型读到的是「一轮一个」 |
| `ai.instructions.htmlArtifact` | 第 4 步「整页重排用 `rewrite_document`」 | 与 `rewrite_document` 自己的说明、以及「大文件必须分段写」直接冲突——HTML 恰是最长的一类文件，这条把模型推向会被截断的那条路 |

对照 coding agent：Claude Code / Codex 的 read **永远**是 `cat -n`，Edit 成功后把改完那段带新行号回给模型。它们的准确率不是靠模型更聪明，是靠"模型手上永远有一份逐字准确、可寻址的原文"。

## 3. 不变量

- **I1 行号只存在于给模型看的输出里，绝不进文件。** 写工具的 `content` 参数永远是裸文本。这条在 trailer 里对模型说一次（而不是写进四个工具的 description，见 D1）。
- **I2 schema 零增长。** 棘轮 15,200，实测 15,135，余量 65。一期二期都不加参数、不加工具，全部改动落在**运行时输出**和 i18n 上。
- **I3 回执里的位移必须精确。** 它取代的正是那次重读——位移错了，模型据此算出的下一个区间就落在错的地方，而且不报错。
- **I4 契约是统一的，不是条件的。** `read_file` 永远带行号，不做"长文件才带"——"有时带"比"永远带"更难用，模型得先判断这次是哪种。

## 4. 一期：行号契约（PR #396）

### 4.1 `read_file` 永远带行号

每行前缀 `%6d | `，末尾 trailer 说明前缀是行号、不是文件内容（I1），并保留原有的分页信息。整份文件读完时也带 trailer（只是内容不同），因为 I4。

成本：每行 7 个字符（`     1\t`）≈ 2 token。HTML 约 35 字符/行，4000 字符 ≈ 114 行 ≈ **+200 token**（约 +20%）。买到的是：`find` 不再靠记忆重建、`rewrite_lines` 可以直接瞄准、以及那句描述从谎话变成真话（**一个 schema 字都不用加**）。

### 4.2 `read_slides`（.html）：每页行区间 + 分页时的整册目录

- 每页标题从 `## Slide 7` 变成 `## Slide 7 (lines 210-236)`。约 +10 token/页。
- **响应装不下整份 deck 时**，前置一份目录：一页一行 `7. 标题文本 (lines 210-236, 1.4k)`。约 15 token/页。

目录**搭分页的便车**，不是新参数（D2）。`readHtmlSlideRange` 本来就调 `splitHtmlSlides(html)` 切了整份文件，目录是纯本地、纯免费的信息。

### 4.3 写回执带回「现在长什么样」

`rewrite_lines` 与 `propose_edit` 批准后，回执给出：

1. 应用后的行区间；
2. **位移 Δ**——"这一行之后的每个行号都 +5"（I3）；
3. 一段带行号的应用后片段（上下各 2 行上下文）。

区间超过 `ECHO_MAX_LINES`(40) 行时降级为首尾各 3 行 + 位移，正文不回显——回显一份 400 行的片段就是把省下来的那一轮又花出去了。`propose_edit` 命中多处时只给行号清单，不逐处回显。

### 4.4 指令层

- `ai.instructions.agent`：说清**一轮可以发多个互不重叠的编辑调用**（机制早就支持），并给出唯一那条纪律——**同一文件的多处编辑必须按行号从后往前排**，否则前面的改动会让后面的行号失效。
- `ai.instructions.htmlArtifact`：第 4 步不再指向 `rewrite_document`；改为与全局纪律一致的「小改 `propose_edit`／区域重排 `rewrite_lines`／新建长页面骨架 + `append_file`」，并补上这条任务从来没提过的 `read_slides` 和 `export_pptx`。

## 5. 二期：结构读与搜索上下文

一期让模型能**指名**一个区域；这一期让它能在读之前就知道**该指哪里**——同一条尺子，同样零 schema。起因是把审阅面从 HTML 扩到 markdown / 纯文本：`.md` 是这个 app 的原生格式，而 `.pptx` / `.xlsx` / `.docx` 全都从 `.md` 或 `.html` 派生，所以「markdown 好不好改」是这三条导出线共同的上游。

对照 coding agent：它们定位靠 grep（正则 + `-A/-B/-C` 上下文）和符号表。散文没有符号表，但**标题树就是**——而 `extractHeadings` 早就在（`lib/fs/markdown.ts`，大纲面板用的就是它），只是 agent 看不到。

### 5.1 `read_file` 分页时前置标题索引

一页一行 `L7  风险`，按标题级别缩进。规则与 `read_slides` 的整册目录**严格同构**（D2）：只在响应装不下整份文件时出现，不做参数。

不需要按扩展名分派：匹配的是 markdown ATX 标题，所以没有标题的 `.txt` 和 `.html` 页面自然什么都不产出——而 `.html` 有 `read_slides` 的目录，那份目录按导出器切分它的方式切分。围栏代码块里的 `# 注释` 由 `extractHeadings` 跳过（`.html` 里的 `#hero {` 本来也不匹配：ATX 标题要求井号后有空白）。

### 5.2 `search_text`：命中少时给上下文

命中数 ≤ 6 时，每处给上下两行，`>` 标出命中行；命中多时维持原样。

理由是这条线上最典型的一次浪费：搜到了就要在那儿改，而改需要周边文本——于是紧跟一次 `read_file`，为的是这次调用**内存里本来就有**的那一段。命中三十条则意味着还没找到东西，答案是缩小查询而不是五倍的正文。上下文行**不做窗口截断**（长行才截，并标上 `…`）——这是模型可能抄进 `find` 的文本，而带省略号的片段抄不得；命中行仍然按匹配位置开窗，因为一条看不见自己匹配了什么的搜索结果不算结果。

### 5.3 `append_file` 回执报文件现在的末行

骨架 + 分段追加是这个 app 写长交付物的正路，而追加的全部意义就是模型**没读过**这个文件——所以它不知道文件现在到哪儿结束，下一次要改刚写下的那一节就得先读一遍。追加之上什么都没动，所以一个行号就够。

### 5.4 `create_file` / `create_chapter` 回执带回文件的地图（补做）

二期给 `append_file` 补了末行（§5.3），但**创建**这两条漏了，而它们其实是同一条规则更纯的形式：一次创建，模型对内容知道得一清二楚，对**坐标**一无所知。

下一步是 `append_file` 时无所谓（追加不需要坐标）；下一步是 `rewrite_lines` 改刚写下的骨架时，模型手上没有行号，唯一的取法是把自己刚写的文件**再读回来**——为了对话里本来就有的文本花掉一整轮 schema。

所以批准之后的回执多两样：文件现在多少行，以及 `read_file` 那份**同一个**标题索引（§5.1）。一节因此可以用同一种方式指名，不管模型是读到它还是造出它的。行数**从文件量**、不从 `content` 参数数——换行符的归属不止一处会差一行，而这里差一行是静默的（I3）。没有标题结构（`.csv`、`.json`、只有一个标题的短文件）就只给行数，那本来就是 `rewrite_lines` 要的那个数。

零 schema 增量：全部落在运行时输出里（I2）。

## 6. 三期：导出线预检拉齐 + `inspect_html`

一二期是**改**的回路；这一期是**验**的回路。三条导出线共用一个缺陷：转换不经过模型，所以正确性完全押在源文件合不合约定上——而不合约定的后果原先只有批准之后才看得见。`export_xlsx` 一开始就做对了（提案时把工作簿建好、卡上一行一张表带类型统计），另外两条没有。

对照 coding agent：它们的准确率来自能自己跑的确定性检查器（tsc / eslint / 测试）。这一期给 HTML 补上那个检查器，并把三条导出线的预检拉到同一深度。

### 6.1 `inspect_html`：模型第一次能看见自己画出来的东西

只读工具，无审批卡。把页面渲进 `harvest.ts` 那个离屏沙箱（参数与预览完全相同，仍然没有 `allow-same-origin`），回报：分成几张、按哪个选择器分的、幻灯片尺寸、**哪些盒子掉到幻灯片外面以及超出多少像素**、哪一页什么都没画出来、哪张图没加载上。

**一行 `harvester.js` 都没改。** 每个盒子本来就带着相对本页的 box，`canvas` 就是第一张幻灯片自己的矩形，所以「超出边界」是对既有数据做两次比较。这一条省下的不是代码量而是风险：动 harvester 就要重算 `tauri.conf.json` 里的 `sha256-`、还要让两份选择器表继续同步，而这个功能配不上那份风险。

**长页面不会误报**：没有分节的页面是一张幻灯片，而它的 canvas 就是它自己的框，所以一张 5000px 高的宣传页报的是「没有溢出」，不是「整页都在溢出」。检查只在它有意义的地方开口。

报告只列**有问题的那几页**，干净的用一句话收尾——一份 30 页没毛病的 deck 应该花掉一句话而不是三十行，否则模型学会的是略过它。

### 6.2 三条导出线的预检

| | 格式/依据 | 内容 |
|---|---|---|
| `export_xlsx` | — | 提案时建好工作簿，卡上一行一张表 + 类型统计（原本就有） |
| `export_docx` | 提案时解析（原本就有） | **新增**：块数 / 标题 / 表格 / 图片，以及光看 markdown 就确定的降级项；**空文档直接退回**（同 xlsx 的「没有表格」早退） |
| `export_pptx` | **新增**：页数 + 分节选择器 | 仍然要等批准（要 DOM），但 `inspect_html` 让模型自己先验 |

`export_pptx` 卡上那句「整页会压成一张」是这次真正要说的话：一个 `.slide` 都没有的页面，兜底会把整页当成第 1 页——作者原先看到的只有两个路径，批准之后才发现得到一张压扁的单页 deck。

### 6.3 顺手改掉的一句错话

`HtmlPreview.tsx` 的模块注释一直写着「blob 文档是自己的 opaque origin，所以它的脚本能跑」——[`html-artifact-plan.md`](../html-artifact-plan.md) D2 在 2026-08 实测更正过这句话（blob 文档**继承**创建它的页面的 CSP），但那份更正没有落回代码。它偏偏就在「沙箱参数只存在一份」的那个文件里，是下一次改动最可能拿来当依据的地方。连带把作者侧那半句也说清楚：应用内预览渲染 CSS 和内联 SVG 是准的，交互要到独立窗口里才真的动。

### 6.4 代价与它照出来的东西

`inspect_html` 的 schema **+202 token**，棘轮 15,200 → 15,400。它不能延迟装载（[`agent-tool-context-lld.md`](agent-tool-context-lld.md) §5 的机制要求「闸没开之前必然失败」，而这个工具的全部价值就是**早**能调），也不能挂在 pptx 的 Beta 上（量一个页面不是导出它，而从不开导出开关的作者正是没人替他检查图示的那个）。

抬到这里就撞上了一件早就该说的事，`contextForecast.test.ts` 现在把它钉住了：**32k 的本地模型上，助手的工具 schema 已经吃掉整个输入预算**（15.3k vs 14k），知识库分到零。这个数字不该再往上长；答案是按任务收窄工具集（§9）。

## 7. 四期：`write` 档——按任务收窄工具集

前三期都在省**轮数**。这一期省的是每一轮的**底价**：工具 schema 每轮原样重发，而 `full` 是 15,337（常驻那半 9,948，其余随已批准的方案才装）。图示/宣传页恰恰是文件最长、轮数最多的那类任务，也就是最先撞上它的那个。

`TaskTools` 从三档变四档：`none` / `read` / **`write`** / `full`。`write` = 查 + 写文件 + 验 + 交付，**不碰知识库**。`htmlArtifact` 改declare 这一档。

**实测 4,017**，对比 15,337（整份）/ 9,948（常驻）。

### 7.1 收窄的依据是「这条任务真的会调什么」

不是「什么看起来无害」。逐条对着 `ai.instructions.htmlArtifact` 的六步走：

| 留下 | 因为 |
|---|---|
| `list_files` `read_file` `search_text` `read_slides` `read_image` | 第 1、6 步 |
| `list_lore_entities` `read_lore_entity` | 第 1 步原文是「必要时**查**{{kb}}」——查，不改 |
| `create_file` `append_file` | 第 2、5 步（骨架 + 逐节追加） |
| `propose_edit` `rewrite_lines` `rewrite_document` | 第 6 步 |
| `inspect_html` | 第 4 步；这条任务是全应用最需要验证回路的那一个 |
| `export_pptx` | deck 的下一步 |
| `read_workflow` | 工作流卡对这类任务成立，而清单本来就随它挂 |

拿掉的：整套 lore 写工具连同 `propose_lore_plan`（对这条任务是一条永远走不到的岔路）、生图三件（页面里的图形是内联 SVG，这是产品线的前提，而生图**要花钱**）、memory、删除类、`export_docx` / `export_xlsx` / `read_doc_format`（那两条导出吃的是 markdown，产物是 .html）、`task_plan` / `task_progress` / 笔记（指令里一次都没提；作者看进度有执行日志）。

`maxRounds` 24 而非 40：一份页面的形状是「读材料 → 骨架 → 逐节追加 → 量一遍 → 修」，不是扫整个 lore 文件夹。

### 7.2 两份清单改成跟着工具走

`aiTaskStore` 原来用 `task.tools === "full"` 决定是否在指令尾部挂**工作流卡清单**和 **docx 格式清单**。那在 `full` 是唯一带这两个工具的档位时是同一件事；多出一档之后就不是了——`write` 有 `read_workflow` 没有 `export_docx`，按档位判会**同时**做错两件事：发一份它用不上的 Word 格式表，又扣下它 `read_workflow` 正要服务的那份工作流清单。

所以判据改成 `preset.tools.includes(...)`：清单跟着它服务的那个工具走。`forecast.ts` 的 `docxRosterChars` 项同改，否则预估会给 `write` 档多算一份它收不到的东西。

### 7.3 一个顺带看见的、这一期不改的数

`plannedToolTokens` 量的是**整份路由后的工具表**，包括 `lore_write` 那一组延迟装载的——而那一组在方案批准之前根本不上线。于是助手的预估比前几轮真实发送的多算约 5.4k（15,337 vs 常驻 9,948）。方向是安全的（宁可多留余量），但在 14k 的上限上多留 5.4k 是很多。改它会动到每一条计量条的含义，所以单独一片，记在 §9。

## 8. 决策与弃案

### D1 行号是运行时契约，不是 schema 契约

加在工具**输出**和 trailer 里，不加进 description。两条理由：棘轮余量只有 65 token（I2）；而 `rewrite_lines` 的描述**已经**声称 read_file 报行号——这次是让那句话变成真的，不是新增一个约定。

- 弃用【给 `read_file` 加 `numbered` 参数】：模型要多学一个开关，而"有时带行号"的契约比"永远带"更难用（I4）；schema 还要多付约 50 token。
- 弃用【在四个写工具的描述里各加一句「行号不要写进 content」】：约 +100 token，直接撞破棘轮。同一句话放在 trailer 里是免费的，而且出现在模型**刚刚读到行号**的那一刻，比出现在几千 token 之前的 schema 里更管用。

### D2 目录搭分页的便车，不做 `outline` 参数

同 D1 的理由，外加一条：模型第一次调 `read_slides` 时**本来就要**知道这册有多少页、第 7 页在哪，目录是它那一刻正需要的东西。做成参数意味着它得先花一轮问、再花一轮读。

### D3 .pptx 这一期不给目录与行区间

`.html` 的切分已经在内存里（`splitHtmlSlides` 切的是整份文件），`.pptx` 要再跑一次整册 IPC 解析才拿得到标题。而且两者的使用形态不同：`.pptx` 通常读一次，`.html` 才是模型反复改的那一个。行号对 `.pptx` 更是没有意义（它不是文本文件）。

### D4 回执回显，而不是让模型重读

「re-read before naming another range」是把一次**确定性的算术**（区间长度差）外包给了模型的第二次阅读。位移是本地算得出来的，算一次写进回执，比让模型再读 4000 字符便宜两个数量级。

### D5 一轮多处编辑是指令问题，不是机制问题

`partitionParallelSegments` 早就把写调用切成"各自成段、依次执行"，一轮里发五个 `propose_edit` 今天就能跑通，每个各自弹卡、按序落盘。所以修在 i18n，不动 runtime。

- 弃用【MultiEdit 式的批量编辑工具】：一张卡片承载 N 处改动，作者审的粒度就变粗了——而这个应用的整个 L2 设计就是"一次改动一张卡"。真正的问题是模型不知道自己可以一轮发五个，那是一句话的事。

### D6 `htmlArtifact` 的指令与全局纪律对齐

一条任务指令不该和它调用的工具的说明互相矛盾。这条是纯 i18n 修正，两个 locale 同步。

### D7 标题索引不按扩展名分派

判据是「有没有 ATX 标题」而不是「是不是 .md」。少一处要维护的类型表，而且行为恰好正确：`.txt` 有标题就有索引，没有就没有；`.html` 天然产不出（`#hero {` 井号后无空白），而它本来就有 `read_slides` 的目录。

### D8 `search_text` 仍然不做正则

不是没排上，是**已经否掉过**：查询串来自模型，一个病态回溯模式会把 UI 线程挂死，而作者没有任何中断它的手段（`searchWritingFiles` 的模块注释记着这条）。5.2 的上下文行走的是另一条路——不扩大匹配能力，只让**已经命中**的那一次少花一轮。

### D9 三条导出线的预检不同期做（二期不做，三期做）

`export_docx` / `export_xlsx` / `export_pptx` 的正确性完全取决于源文件合不合约定，而不合约定的后果只有批准之后才看得见。那是审批卡一侧的事，与二期的读写回路不是同一处改动——所以推到三期，和 `inspect_html` 一起（§6）：它们是同一个形状，「在写下去之前就把确定性转换器会做的事算出来」。

### D10 `inspect_html` 不动 `harvester.js`

溢出是对既有数据的两次比较：每个盒子本来就带着相对本页的 box，`canvas` 就是第一张幻灯片自己的矩形。往 harvester 里加一个 `scrollHeight > clientHeight` 的内部溢出判定**会**多报一类问题，但代价是重算 `tauri.conf.json` 的 `sha256-`、让两份选择器表继续同步、以及一类只在真实布局里才复现的 bug。掉出幻灯片才是 pptx 真正的失败模式，而它免费。

### D11 `inspect_html` 不挂 pptx 的 Beta 开关

量一个页面不是导出它。HTML 交付物本身是已发布的功能（`htmlArtifact` 是默认任务之一），而从不打开 PowerPoint 导出开关的作者，正是没有任何人替他检查图示的那一个。代价是 202 token 常驻——记在 §6.4，连同它照出来的那件更大的事。

### D12 新增的是**档位**，不是「给 htmlArtifact 开个特例」

`presetForTools` 存在的理由就是让 `lib/profile` 不依赖 agent 层：能力包只写 `tools: "write"`，preset 是什么由 agent 层自己决定。所以收窄工具集只能是**加一档**，不能是按 task id 分支——那正是 CLAUDE.md 明令禁止的那件事，而且能力包也就没法用上这一档。

- 弃用【给 `TaskPreset` 加一个 `preset` 字段让任务直接指定】：那会把 agent 层的类型漏进 pack schema，也让「一个包能声明什么」变成开放集合。

### D13 档位叫 `write` 而不是 `html`

判据是**产物是不是一份文档**，不是文件后缀。周报、文案、投标应答都是同一形状：查资料、写文件、验、交付，不动知识库。叫 `html` 会让下一个同形状的任务无处可去，只能退回 `full`。

- 弃用【`author`】：这个应用里「作者」是人（见 `terminology.md`），拿它当档位名会立刻和面向作者的措辞打架。

### D14 `write` 档不给 `task_plan` / 笔记

`ai.instructions.htmlArtifact` 一次都没提过它们，而一个指令从不要求、模型偶尔想起来的工具，是每轮都付、几乎不调的那种。重开条件很明确：等这条任务的指令真的写成「先立清单再分节做」的时候，那两个工具跟着指令一起加。

## 10. 五期：知识库的「查」——`search_text` 覆盖知识库

一到四期把正文这一侧（md / txt / html）拉到了 coding agent 的水平：读有行号、有标题索引，搜有上下文，写有回执，还有 `inspect_html` 能验。**知识库这一侧一样都没有。** 拿同一把尺子回头量它，第一条就是最贵的：

### 10.1 知识库根本没有全文检索

`read_dir_recursive`（[commands.rs](../../../src-tauri/src/commands.rs)）跳过全部点开头的条目，所以 `.ai-writer/lore/` 对 `search_text` **从来不可见**；而知识库也没有第二个内容检索工具。于是「哪一条条目提到了青铜钥匙」这个问题只有一条路：

```
list_lore_entities            → 一堆名字和一行摘要
read_lore_entity(候选 1)      → 一轮
read_lore_entity(候选 2)      → 一轮
…
```

五十条条目的项目，最坏五十轮，**每轮重发整份 15.1k 的 schema**。按 §1 的尺子，这是这条链上最贵的一处，而且它贵得**不显眼**——每一次调用看起来都很正常。

而摘要救不了它：`list_lore_entities` 给的是作者写的一行 summary，「青铜钥匙」多半只出现在某条人物的正文第三段里。

### 10.2 做成 `search_text` 的一部分，而不是第二个工具

一个 `search_lore` 新工具约 **250 token / 轮 / 每一次运行**，只为把这个工具已经在说的话再说一遍。改成一个工具、一个心智模型（coding agent 只有一个 grep），实测 `search_text` 252 → **301（+49）**，整份 AGENT_ASSIST 15,337 → **15,385，棘轮 15,400 不动**。

不同的是**标号**。正文命中标路径（`propose_edit` 收路径），知识库命中标 `条目 · 文件`——因为 `edit_lore_file` 收的正是 `entity` + `file` 这两个参数。把知识库命中报成一个路径，等于报了一个那一侧任何写工具都不接受的坐标，模型会转头去调 `propose_edit`，而它拒绝 `.ai-writer`。

两侧**各有各的配额**（正文 40/8，知识库 12/4），也**各自决定要不要给上下文**（§5.2 的 ≤6 条阈值分别判）。合成一份配额的话，三百章书里一个常用词就会在那条**定义**了这个词的条目被报出来之前把额度花光——而那条条目通常就是问题本身。上下文同理：正文被淹没时，唯一真正定位到答案的那条知识库命中反而失去上下文，正好赔掉 §5.2 要省的那一轮。

### 10.3 两条边界没有动

- **不放宽 `read_file`。** 它仍然拒绝 `.ai-writer`（被注入的模型把 `profile.json` 读回给下指令的人），而搜索返回的是模型**本来就能按名字整篇读到**的文件里的几行，不是新权限。
- **不越过取材范围。** 扫描就是「自动发现」，而围栏narrow的正是这一件事（[collections.ts](../../../src/lib/lore/collections.ts)）。所以被挡掉的条目数照实报出来，而不是假装不存在——按名字点读仍然通得过。

`folder` 参数一给就跳过知识库：folder 是一条正文路径，要一棵子树就是只要这棵子树，而不是「一侧收窄、另一侧偷偷当没看见」。没命中时这句话会说出来，因为那正是会得出错误结论的地方。

**磁盘代价**：一次搜索现在会把每个条目的每个 .md 读一遍（条目正文不缓存——`LoreEntity` 只在扫描时解析 frontmatter，正文按需读）。这与正文那一侧本来就在做的事同形（它也读每一个章节文件），而它换掉的是最多 N 次**模型往返**——本地文件读和一轮 15.1k 的请求不在同一个量纲上。真要优化，方向是给条目正文做一层扫描期缓存，那件事对注入路径同样有用，不属于这一片。

### 10.4 顺带修好的一件事

搜索结果里的 `N files` 改成 `N documents`：有了两栏之后，「文件」同时指正文文件和条目文件，是个会读错的词。

## 11. 六期：知识库的「改」——寻址与回执

五期修的是「查」。这一期修「改」。对着正文这一侧一到二期做过的事逐条量知识库，一共五条差距，其中三条是同一件事的三个面：

| | 正文这一侧 | 知识库这一侧 | 状态 |
|---|---|---|---|
| L1 | `search_text` 全文检索 | 完全没有 | ✅ 五期 |
| L2 | `read_file` 4000 字符分页 + 标题索引 | **完全没有上限**，一次读回条目的全部 .md；也没有 `file` 参数 | §12 |
| L3 | `rewrite_lines` 按行区间重排 | 没有对应物 | §12 |
| L4 | 写回执带位移 + 应用后片段（§4.3） | 只回「Replaced N chars with M」 | ✅ 本期 |
| L5 | `propose_edit` 有 `occurrence` / `replace_all` | 命中 >1 直接拒绝 | ✅ 本期 |

### 11.1 L5：重复文本从「不可寻址」变成三条出路

原先 `find` 必须唯一，命中两次就直接拒。于是一个条目里出现两次的同一个短语——时间线上重复的名字、两段勾勒同一件衣服的散文——**根本无法定位**，唯一的出路是 `update_lore_file` 把整条重发一遍：既贵，又把「只改这一处」变成「重写全篇」这种什么都可能被顺手改掉的操作。

三条出路照抄 `propose_edit`：把 `find` 写长到唯一、`occurrence` 指第几处、`replace_all` 全改。**照抄是要点本身**——一个已经在正文那边学会这三句话的模型，不该为知识库再学一套不一样的答案。落地也是同一份 `applyFindReplace`（[editApply.ts](../../../src/lib/agent/editApply.ts)），所以「第三处」在应用两侧是同一个意思。

拒绝的那句话顺带**报出这些命中在第几行**。这是本期最便宜的一处收益：模型在**同一轮**里就能改用 `occurrence`，而不必再读一遍去看另外几处在哪。行号是**整份文件**的行号（frontmatter 算在内）——五期给知识库命中报的就是这套坐标，一份文件两套编号比没有编号更糟。

### 11.2 L4：回执带回条目现在的样子

原先只回「Replaced 12 chars with 15」，模型能知道**有东西被写下去了**，不知道它落进的那句话现在读不读得通。

正文那边这个缺口值一整轮（§4.3）；在条目里它还多藏一种失败：`find` 匹配到了**相邻句子**里，两句话被焊在一起——而回执照旧报「成功」。所以回执现在带回应用后的区域（带行号）加位移，和 `rewrite_lines` / `propose_edit` 完全一样，用的也是同一个 `appliedReceipt`。

`replace_all` 改了多处时**不给区域**，改为一句「N 处已改，下面的行号都动了，要用行号先重读」。位移在文件里累加，没有单一区域可回显、也没有单一数字能描述——编一个出来不会失败，只会让下一次编辑落在错的地方。

`append_lore_file` 同时补上「条目现在到第几行结束」（同 §5.3：追加之上什么都没动，一个行号就是全部）。

### 11.3 代价：加在**方案批准之后才上线**的那一组里

`edit_lore_file` 的 schema 315 → **436（+121）**。整份 AGENT_ASSIST 15,385 → **15,506**，棘轮抬到 15,600。

但真正要看的是另一个数：**常驻那半一动没动，前后都是 9,996**。这 +121 全部落在 `lore_write` 组内，而那一组要等作者批准了知识库方案才上线——也就是这个工具**变得可调用的那一刻**。[`agent-tool-context-lld.md`](agent-tool-context-lld.md) §5 说的正是这种增长方式，而机制早就在位。`write` 档同样没动（4,065）。

两个数字要一起读，并且把**常驻**那个当账单：过去五片里它一共动了不到 500，而整份那个长了 1,700。会动到常驻的改动才值得辩论，这一条不值。

## 13. 七期：预估只算常驻——那 5.4k 的虚报

`plannedToolTokens` 原先量的是**整份路由后的工具表**，包括 `lore_write` / `lore_organize` 那两组延迟装载的。可方案闸门是**每次运行新建的**（`createPlanGate()`），所以**任何一条在运行之前规划的请求都不可能带着它们**——不是「多半不会」，是结构上不可能。于是助手的每一条计量条、每一次预算规划都多扣约 **5.4k**（15.5k vs 常驻 9,996）。

后果不是「显示得保守」，而是真金白银：32k 的本地模型上（14k 输入上限），这 5.4k 的虚报是「知识库分到 2,881」和「知识库分到零」的差别——`contextForecast.test.ts` 原来钉的 `over=true` 那半是虚的，现在钉的是修完的事实。

### 13.1 两半，各在它知道真相的地方

- **规划侧**（`plannedToolTokens`）：路由后再 `partitionByGroup`，只算常驻那半（+handoff）。所有调用方——生成面板预估、chat 计量条、`messageCeilingFor` 的裁剪与压缩阈值——自动跟着变，一个都不用改。
- **运行侧**（`runAgent`）：方案批准、组装载的那一刻，**runtime 自己把 message ceiling 收缩掉该组的实测成本**。中途装载只有 runtime 知道发生了，规划侧只能猜——所以补偿放在知道的那一侧，裁剪和 scratchpad 的「快到上限」提示都跟着活的 ceiling 走。

这两半合起来才是完整的契约：规划按「现在真的会发什么」算，装载的增长在发生的那一刻被精确抵扣。只做前一半，写知识库的长对话会按一个多出 ~5k 的 ceiling 裁剪——正好在最小的窗口上、最需要裁剪的那类运行里把静默超限请回来。

### 13.2 代价

零。没有 schema 变化，没有新工具——这一片修的是**账**，不是工具面。计量条上的可见变化：助手档的「工具」段从 ~15.5k 缩到实际发送的常驻数（默认路由下 ~6.7k：常驻 9,996 再被路由剥掉未绑定的生图三件与关着的导出线），「余量」与「知识库」相应回来。

## 14. 八期：知识库的「读」——分页、行号与 `rewrite_lore_lines`

L2/L3，六期收尾时明知要动常驻 schema 而留下的两条。它们必须一起做：L3 收行号，而行号只能从 L2 的编号输出里来。

### 14.1 L2：`read_lore_entity` 有了上限、行号和 `file` 参数

原先读一条条目 = 读它的全部：一个八特征的人物，每次随手一查都付几万字符，而 `read_file` 早就是 4000 字符分页 + 标题索引。现在：

- **每个文件的正文带行号**（各自从 1 数起，frontmatter 算在内）——与 `search_text` 的知识库命中、`edit_lore_file` 的拒绝与回执**同一套坐标**，末尾一句话点明这就是 `rewrite_lore_lines` 收的数。
- **上限之内维持整条返回**（`ENTITY_MAX_CHARS` = 10,000）。这一条是刻意的：一轮拿到全部是省轮数的正形状（§1），「永远按文件点读」会让装得下的条目也付一轮一个文件的代价——方向就反了。
- **超上限才降级**：index.md（分页后的第一页）+ 其余文件的一张表（文件名 · 特征名 · 行数 · 字数 · 互斥组），按名点读。
- **`file` + `start_line`**：单文件分页，契约与 `read_file` 完全同形（`pageLines` 一份实现）。`images.md` 拒读——图集另有通道。

### 14.2 L3：`rewrite_lore_lines`

`rewrite_lines` 的知识库版：长特征重排指行区间，只发替换文本，不再被迫 `update_lore_file` 整篇重发。照抄的三条纪律——**frontmatter 拒改**（行区间盖过 YAML 是特征静默停止注入的路子，与 `edit_lore_file` 只匹配正文同理，拒绝语报出正文从第几行开始）、**焊接护栏**（区间带走末行换行符时替换文本补上）、**回执走同一个 `appliedReceipt`**（新区间 + 位移 + 应用后片段）。方案闸门、备份、快照刷新与其他 lore 写完全一致。

### 14.3 代价

`read_lore_entity` 170 → 280（**+110 常驻**，§14 预算的 ~+90 的实测数）；`rewrite_lore_lines` 321，**全在延迟组**。整份 15,506 → **15,937**，棘轮 15,600 → 16,000；常驻 9,996 → **10,106**。按 §11.3 的读法：这次常驻真的动了，动的理由就是 L2 本身——它买断的是「读一条条目 = 付它的全部」。

# 设计任务：为一款桌面写作应用设计「写手」——一个替 AI 助手完成最终成文的第二模型

## 产品背景

这是一款给小说 / 剧本 / 跑团模组作者用的桌面写作应用（Tauri + React，Mac 和 Windows）。左边文件树，中间 Markdown 编辑器，右边呼出一个很宽的 AI 抽屉。作者在应用里维护一个「知识库」——人物、世界观、势力、道具这些设定条目。

AI 抽屉里有一个**对话助手**：作者和它聊，它能读文件、查知识库、联网检索、看图，也能提出修改稿件（作者在一张确认卡上批准或拒绝）。它已经能把耗上下文的活儿分给几个**子代理**（联网检索 / 图像理解 / 长文精读 / PDF / 图片生成 / 日中翻译），每个子代理由作者在设置里绑一个专门的模型。

现在要加的第六个成员和前面五个**根本不同**，这是整个设计的起点。

## 这个功能是什么

**「写手」是一个开关。打开之后，对话助手不再自己写最后那段文字。**

它变成这样：助手照常干活——读文件、查设定、检索、思考——但当它准备好要回答的时候，它不写答案，而是交出一张**工单**（要交付什么、有哪些不能违背的约束、材料在哪几个文件里、要模仿的文风片段是哪几段）。然后另一个模型——作者专门为「写手」绑定的那个，通常是更贵、更会写的那个——拿着工单，重新在一个干净的上下文里把这段文字写出来。

作者最终读到的每一个字，都是写手写的。

**关键点，请务必吃透：**

1. **这不是省钱，是换人。** 其余五个子代理存在的理由是"别把搜索原文塞进主上下文"。写手正好相反——它更贵、更慢（每一轮多一次完整请求），换来的是**更好的文笔**。
2. **没有任何模型决定要不要用它。** 开关一开，每一轮都走它。助手不能"觉得这次不需要"。
3. **助手的思考过程仍然完全属于助手。** 工单是助手的产物，写手只负责把工单变成文字。
4. **写手看不见对话。** 它拿到的只有工单和工单点名的那几个文件。这是刻意的——它是来写字的，不是来续聊的。

## 这个界面要解决的核心张力

### 张力一（最重要）：署名 vs 安静

作者在读一段散文。这段字是**第二个模型**写的，而面板顶上写着的是助手的模型名。

- **不显示** → 作者分不清"这一轮真的走了写手"和"写手没跑起来、你读到的是助手写的"（后者会在某些接口上真实发生，见下面的「降级」）；一段文笔垮掉的回复也无从判断该换哪个模型。
- **显示得太重** → 每条回复顶一个徽章，阅读体验变成看仪表盘。作者要的是读小说，不是读日志。

**这个平衡就是这次设计的成败点。** 请给出你的答案并说明理由。

### 张力二：工单该被看见多少

工单是有价值的内容——它是助手"想清楚了什么"的显式版本，作者会想看，尤其是当结果不对的时候（"是它没说清楚，还是写手没写好？"）。

但它**绝不能被误认为是答案**。它是内部工件，写给另一个模型的，语气、编号、标题都不是给人读的。

现在它被埋在执行日志里两层展开之下。那太深了。但把它平铺出来又会和答案抢注意力。

### 张力三：诚实地表达"这更慢更贵"

一次回复变成两次请求。作者应该**感觉得到**这件事，而不是某天看账单才发现。但也不能变成一个劝退的警告横幅。

## 视觉规范（硬约束，必须遵守）

这个应用有严格的既定视觉语言，新东西必须无缝融入：

- **风格**：克制的、现代的、Apple 式的。整体气质是"手稿"——像裁切的纸，不像圆角卡片。
- **圆角：全局为 0。** 所有容器、按钮、输入框都是直角。唯一允许的圆形是状态圆点、加载指示器、单选标记、以及头像。开关是方形的。
- **强调色：只有一个** —— 赭石色 sienna（浅色模式 `#A0522D`，深色模式 `#D9925B`）。禁止在交互元素上用多色渐变。需要区分状态时用中性灰阶 + 这一个强调色的深浅。**特别注意**：本功能天然想用"第二种颜色"来区分"助手 vs 写手"，**不可以**。请用别的手段。
- **层次靠阴影，不靠边框。** 有一套四级阴影（sm/md/lg/xl），取能读出来的最小那一级。
- **字体**：正文用衬线（手稿感），UI 标签用无衬线，数字/代码用等宽。中文正文默认宋体系。
- **动效**：120–320ms，Apple 缓动曲线，"几乎察觉不到但很顺"。不要弹跳、不要大位移。
- **深浅双主题**：两套都要出，不是深色改个背景色了事。
- **选中 vs 悬停要分开**：选中用强调色淡染，悬停用中性灰。

## 画布尺寸

- **AI 抽屉**：从右侧滑出，宽 1180px（最大 94vw），高度占满窗口。对话在其中一个 tab 里。
- **设置页**：整窗页面，左侧一列导航，右侧内容区。「子代理」是导航里的一项。

## 需要设计的界面

### 1. 对话里的一轮（最重要）

一轮完整的助手回复，现在有了**三个阶段**，而现在的实现里前两个阶段几乎没有视觉表达：

1. **助手在干活** —— 读文件、查设定、调用子代理。已有一条可展开的执行日志，折叠时是一行小字。
2. **交接** —— 助手交出工单，写手接手。这是一个**转折点**，目前完全不可见。
3. **写手在成文** —— 文字开始流式出现。

请设计这一轮的完整时间线。特别是：

- 阶段 2 到 3 的过渡长什么样？这是"另一个人接过笔"的时刻，值得一个动作，但必须极轻。
- 流式出现的这段文字，怎么在**不打断阅读**的前提下让人知道"这是写手写的"？
- 回复结束之后，那个标记还在吗？还是只在悬停/展开时出现？
- **多轮往复的对话流里**，每一条都带同样的标记会不会变成噪音？如果会，第一条之后要不要退化？

请把**一段完整的多轮对话**画出来，不要只画单条气泡——噪音问题只有在连续几轮里才看得见。

### 2. 工单

它在执行日志里有一张卡（和其他子代理的卡并列）。卡的内容是：

- 目标（一句话）
- 交付形态：正文 / 分析 / 直接回答
- 材料：N 个文件路径
- 不可违背的约束（若干条）
- 文风锚点：**原文片段**（可能是多行的、带换行的一小段散文）
- 避免的东西（若干条）
- 篇幅要求
- 可选：要写进哪个文件、用什么方式（新建 / 追加 / 整篇重写 / 替换第 M–N 行）

请设计这张卡。要考虑：

- 它是**给人读的呈现**，但内容是**写给模型的**。这两件事的距离要在排版上处理掉。
- 文风锚点是里面唯一的"文学内容"，其余都是清单。它值不值得一个不同的排版？
- 空字段怎么办（很多轮只有目标 + 材料，没有约束也没有锚点）？
- 这张卡该在第几层展开里？现在是两层（执行日志 → 子代理卡）。给出你的建议。

### 3. 「降级」这条警告

有些模型接口会**静默地**拒绝"必须调用这个工具"的指令。发生时，应用仍然会把活交给写手（它拿助手那一轮的文字当工单），但作者应该知道**这张工单是推出来的，不是助手交的**。

这是本功能唯一一个"看起来一切正常、其实走偏了"的状态。请设计它：一行字？一个记号？在哪一层？

分寸：它不是错误，回复是好的；它是一条"你可能想换个模型"的线索。

### 4. 写手没跑起来

作者开了开关但没绑模型、或者绑的供应商没填 API key。这一轮的回复会变成一条说明原因的系统提示。

请设计这个态。要点：**这不是助手在说话**——它是应用在解释一个配置问题。它长得必须和一条正常回复明显不同，并且应该能一键跳到设置里对应的位置。

### 5. 输入框上方的会话开关（芯片行）

输入框上方有一排小芯片，每个是一个子代理的"本次对话开关"（只能关，不能开——开需要去设置里绑模型）。现在是：联网 / 识图 / 长文 / PDF / 绘图 / 翻译。

写手是第七个，**但它和前六个不是一类东西**：

- 前六个是"这个能力可用"——开着也不一定用得上。
- 写手是"从现在起每一句话都由它写"——它一定会生效，而且改变每一轮的成本和时长。

它现在长得和其他六个一模一样。**这是错的。** 请设计一个能表达这个差别的方案：位置？密度？一个"生效中"的持续态？还是干脆不放在这一排？

同时请画：**芯片行在角色扮演面板里的样子**——那里写手不适用，这一排只有六个（不能显示一个按下去没反应的开关）。

### 6. 设置 → 子代理：第三组

设置里的子代理页现在按运行时的真实分界分组：

- **对话委托**（联网 / 识图 / 长文 / PDF）——助手在对话中通过工具调用，独立上下文执行
- **直接工具**（绘图 / 翻译）——这些模型无法对话，助手通过工具直接调用
- **收尾成文**（写手）——← 新增的第三组，**只有一张卡**

每张卡现在的结构：状态圆点 + 名称 + 前置条件芯片（如"需 web_search"）+ 就绪/需要处理/已停用 + 开关 / 说明文字 / 「执行模型」下拉 + 一行元信息 / 出问题时卡底一条警告条。

写手这张卡有三件别人没有的事：

- **它没有前置条件**。任何文本模型都能写。别人卡上那个"需多模态""需 PDF 输入"的位置，它是空的。
- **它有适用范围**：只作用于 AI 助手对话，角色扮演不受影响。这句话必须在卡上说清楚，否则作者会以为哪里都生效。
- **它有代价**：每一轮多一次请求。这是张力三的落点之一。

请设计这张卡，以及第三组的组标题该怎么和上面两组区分开（它只有一张卡，直接套用同样的组头会显得很空）。

### 7. 写手把文字写进文件时的确认卡

工单可以带一条"写进哪个文件"。写手写完之后，应用会弹出一张**确认卡**让作者批准这次写入——这套卡片已经存在（助手改稿子时用的就是它），显示路径、改动内容、批准 / 拒绝。

新的一点是：**卡上这段内容不是助手写的，是写手写的，而且中间没有经过任何模型转手。**

要不要在卡上体现？这关系到作者的信任——"我批准的这段字，就是我刚才在对话里读到的那段字，一字不差"。请给出方案。

### 8. 第一次打开开关

作者刚在设置里打开写手、绑好模型，回到对话。**下一句话开始，一切都不一样了。**

现在没有任何东西告诉他这件事。请设计一个一次性的、极克制的引导——它要回答三个问题：从现在起谁在写字、在哪里能看到工单、怎么临时关掉。

## 交付

- **一段完整的多轮对话**，深色 + 浅色两版——包含正常轮、降级轮、写手未配置轮
- 一轮的**时间线细节图**（助手干活 → 交接 → 写手成文），把过渡放大画
- **工单卡**的细节图（含空字段的版本、含文风锚点的版本）
- **芯片行**的两个版本（对话助手 7 个 / 角色扮演 6 个），以及写手芯片的各个态
- **设置页第三组 + 写手卡**（就绪 / 未绑模型 / 已停用 三个态）
- **写入确认卡**
- **首次引导**
- 一段说明：你怎么解决张力一的（署名 vs 安静），为什么

## 不要做的事

- **不要引入第二个强调色**去区分"助手 vs 写手"。这是最容易犯的错，也是最难改回来的。
- 不要加圆角。
- 不要给回复加头像或"AI 人格"。这不是两个角色在说话，是一条流水线上的两道工序。
- 不要把工单做成可编辑的表单。作者不填工单——助手填。作者要做的是**读**它，然后决定是改自己的要求还是换个模型。
- 不要用"打字机效果"表现写手在写字。文字本来就是流式的，加特效只会更慢。
- 不要把"每轮多一次请求"做成一个需要点掉的警告横幅。它是一个事实，不是一个风险。
- 不要暗示写手能看到对话历史——界面上任何"它记得刚才那句"的暗示都是假的。

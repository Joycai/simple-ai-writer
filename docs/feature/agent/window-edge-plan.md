# 窗口边缘：卡死、重读循环与「完成了却什么都没写」

> 状态：`partial`（2026-09-11 实测；方案经作者批准，按 PR-1 → PR-2 → PR-6 → PR-3 → PR-4(a) → PR-5 执行。✅ PR-1 · PR-2 已实施）
> 起因：作者报告本地小模型（qwen3.8-27b，LM Studio，32k）「经常卡死、死循环、突然中断」。拿真实运行时对着真实端点量了一遍，三个症状对应到六个机制——其中五个**跟窗口走，不跟模型走**：同样的上限压到 DeepSeek 上，它一样重读、一样把轮次花在记账上，只是每轮快十倍，所以看不出来。
> 相关：[`edit-loop-plan.md`](edit-loop-plan.md)（「省一轮 ≈ 一整份工具表」的量纲）· [`agent-tool-context.md`](agent-tool-context.md)（常驻工具的成本账）· [`compact-threshold-plan.md`](compact-threshold-plan.md)（归纳触发线）· [`../../api/streaming.md`](../../api/streaming.md)（失败怎么送达）
> 台架：`scripts/local-model-probe.ts`（§7）

## 1. 结论

**小模型不是另一类问题，而是开局就站在窗口边上。** 助手档的常驻工具 schema ≈ 10.8k token、系统层 ≈ 3.4k，32k 窗口在默认「窗口占用」50% 下的输入上限是 16k——固定成本占上限的 89%，留给整段对话的是 **≈1.8k**。200k 的模型同样的代码路径要到长对话的后半段才碰到。

对照实验把这件事钉死了（§2.3）：

- **同一个 qwen、同一个任务，只把占用从 50% 调到 90%**：7 轮 223 秒、一个字没改 → 4 轮 49 秒、改成。
- **同一个 50%/32k 上限，换成 DeepSeek**：它也重读了四次、13 轮才改成，还在任务日志里写下「回执被上下文裁剪丢弃，未能读到批准结果」。

所以修法是**跟窗口挂钩的不变量**，不是「如果是本地模型」的分支——这和整个项目「不按 id 分支」是同一条规矩。

只有一条真正属于小模型：**思考打转**（§3 M6）。但它的分量一点也不轻——在写作类任务上它是 qwen「卡死 + 突然中断」的主因，而且**窗口宽裕时照样发生**：续写档上限 14k、估算不到 3k，它照样思考了 307 秒、把 32k 写满、一个字的正文都没有。更糟的是运行把这种结局报成 `completed`（M3），所以作者看到的只是「转了五分钟，然后什么都没有」。

两条直接用 curl 打的端点探针：

- **撞窗**：22,453 token 的提示 + 不设上限的输出 → 首字 14.4 秒，思考 8,263 + 正文 1,284 = 恰好 32,000，`finish_reason: length`，断在半个词上，218 秒。

### 2.4 流的形状

- **工具参数一次到齐。** LM Studio 把 `tool_calls[].function.arguments` 攒到生成完才发一整块——模型写一条长参数的这段时间流是静默的（实测最长 7.4 秒；一整章的 `rewrite_document` 按 50 tok/s 算是分钟级）。`toolArgsProgress` 对它无能为力。
- **前缀缓存是本地的命脉。** 同一轮次序列里冷预填充 8.7 秒、之后每轮 0.6–0.8 秒；而 `trimHistory` 改的是 history **中间**的消息，改完那一轮的首字回到 2.7 秒。
- **估算器对中文偏保守。** `estimateTextTokens` 把一个汉字算一个 token，Qwen 的分词实测约 0.6 token/字。方向是安全的（早裁不晚裁），记下不改。

## 3. 机制

### M1 裁剪会删掉模型这一轮刚拿到的东西（重读循环）

`runtime.ts` 的 `trimHistory` 从最早的 `role: "tool"` 往后逐条替换成占位符，直到估算回到上限以下。它**不认识轮次**：只要不可裁的部分——系统层、用户消息、注入、助手正文、**以及所有工具调用的参数**——已经逼近上限，最新的那条结果就会在模型读到它之前被替换掉。

模型看到的是 `[earlier tool result dropped …]`，唯一合理的动作是再读一次；再读一次又被裁。强模型会换着页码读、会写笔记绕开（DeepSeek 13 轮），弱模型会读到轮数用完或者在思考里打转（qwen 223 秒、零产出）。

两个加重因素：

- **工具调用参数从来不裁。** `write_note` 把一整份分析写进参数、`propose_edit` 把整段原文放进 `find`——这些都留在 history 里，而且恰恰是本来就已经落盘的东西。DeepSeek 的 survey 跑到估算 7.4k（上限 5.2k）之后，每一轮都会把刚到的全部结果裁掉。
- **改 history 中间的消息会打掉前缀缓存**（§2.4），本地模型每裁一次就多付一次预填充。

### M2 检查点提示在小上限上变成每隔一轮一次

`CHECKPOINT_RATIO = 0.85`：估算超过上限的 85% 就注入「用 write_note 把结论写进笔记」。`checkpointArmed` 在**每次**裁剪后被重置——而在小上限上几乎每轮都裁、估算几乎永远在 85% 以上，于是提示每隔一轮就回来一次。再加上系统层「任务清单」一节要求逐步 `task_progress`，模型把轮次花在记账上：qwen longdoc 2/6，DeepSeek longdoc 5/8。

每一轮都要把 10.8k 的工具表重发一遍（`edit-loop-plan.md` §1 的量纲），在本地模型上每一轮还是几秒到几十秒。

### M3 思考吃掉窗口，截断被当成「完成」

三处缺口叠在一起：

1. **没有给输出留位置。** OpenAI 兼容适配器不发 `max_tokens`（`modelLimits.ts` 的「planning-only」约定），`streamCompletion` 的预检只比 `input ≤ contextSize`。于是一次 22k 输入的请求在 32k 窗口里只剩 9.5k 给思考加正文——而 qwen 光思考就要 8k。
2. **只思考、没正文的截断不算截断。** `runtime.ts` 的恢复条件是 `roundTruncated && roundText.trim()`；思考把窗口用完、正文一个字没出的那一轮，既不恢复也不报错，运行以 `outcome: "completed"` 和空输出结束。`longform` 和 `chat-bigdoc` 都是这样收场的。
3. **归因说错了。** 日志那一行是「输出被上限截断，回答未写完」——但既没有「输出上限」这回事（是窗口满了），也没有「未写完」的回答（一个字都没开始）。作者照这句话去调输出上限，调多少都没用。

另外，对「窗口满了」这种截断走「接着写」恢复是只会更糟的：续写请求带着更长的 history 回去，剩给输出的只会更少。

### M4 流没有看门狗

四个适配器的 `reader.read()` 都没有超时；`AgentLog` 的轮次秒表从轮次开始一直走，分不清「在预填充」「在静默地写工具参数」「连接已经死了」。本地服务被卸载模型、中转层断流而不关连接，界面就永远停在「思考中… 3:47」。

这一条和窗口无关，是任何端点都会有的——只是本地模型的正常静默更长（冷预填充十几秒、长工具参数几十秒），所以更容易被读成卡死，看门狗的阈值也因此不能拍脑袋定得很紧。

### M5 小窗口上几乎每次发送都先归纳一次（读代码得出，未实测）

`compactTriggerFor` 的第三条线是 `0.7 × 消息上限` = 3,620（32k、50%），这个数**包含系统层**。`planFold` 折叠后保留 `prelude + SUMMARY_BUDGET_TOKENS(1000) + 最近 2 轮`，光前两项就 ≈ 4.4k，已经高于触发线——而 `planFold` 不检查「折完之后是否回到触发线以下」。于是对话一旦超过两轮，**每次发送前都先让同一个本地模型做一次总结**，折完仍在线上，下一次再折。

对作者来说是「点了发送，很久没有反应」。台架不跑对话归纳，这一条要在真应用里确认（§5 PR-5）。

### M6 思考打转（模型侧）

qwen 在 `longform` 里写了 42k 字的思考、在 `chat-bigdoc` 第 7 轮写了 60k 字、在 `continue` 第 4 轮写了 **117,766 字（307 秒）**，内容是在几个方案之间来回（「或者更戏剧……太狗血」「可以写现实悬疑……」），**不是逐字复读**——n-gram 式的退化检测抓不到它（Sakura 的 tok/行 判据也不适用）。能管住它的只有长度或时间预算，或者干脆关掉思考。

它和窗口无关：`continue` 那一轮的输入只有 4.8k，是思考自己把剩下的 27k 写满的。同一批提示上 DeepSeek 的思考都是有界的（`longform` 65 秒写出 2,412 字、`continue` 14 秒）。这是六条里唯一真正属于小模型（加上 IQ3 低量化）的一条，**也是写作类任务上代价最大的一条**。

## 4. 设计取舍

**D1 修不变量，不做模型分支。** §2.3 的两组对照说明问题跟上限走；按「本地 / 小模型」开关修，大窗口模型在长对话尾部照样会踩，而且判断「谁是小模型」本身就是一个会过时的名单。

**D2 本轮拿到的结果永远不裁。** `trimHistory` 的可裁范围截止到**最后一条带 `tool_calls` 的助手消息之前**；那之后的工具结果、图片跟帖，以及当前这一问，一律不动。其次，把**早先轮次**里写工具的大参数（`write_note.content`、`create_file.content`、`propose_edit.find/replace`……——都已落盘或已应用）替换成合法 JSON 的占位对象，这是 M1 里真正长大的那部分。两步之后仍然超，就让这一轮照发：真超窗时预检闸门会报 `ContextSizeError`，比静默删掉模型刚读的东西诚实。

> 不选「检测重复读、直接告诉模型你读过了」：那是在治症状——模型再读一次，恰恰是因为它真的需要那段内容。

**D3 消息上限要有保底。** 「窗口占用」的本意是「单次请求占窗口多少」，但当固定成本吃掉上限的 89%，这个设置的实际效果是「不能工作」。三个选项：

- (a) 上限 = `max(窗口 × 占用, 固定成本 + 工作区保底)`，再封顶在 `窗口 − 输出预留`；上下文条上说明「为了留出工作区，本次按 N% 计」。
- (b) 只警告，不改数。
- (c) 固定成本过高时自动降档（`full` → 工具包模式 / `write`）。

推荐 (a)：它是 §2.3 那组 90% 对照的自动版本，而且只在上限小到不能用时才生效。**这一条改了一个设置的语义，需要作者定。**

**D4 检查点提示限频，而不是只发一次。** 最初写的是「每次运行至多一次」，动手时查到 [`subagent-lld.md`](subagent-lld.md) 那条**有意为之**的记录：第一版正是只发一次，结果「长任务照样丢」，所以才改成每裁一次就重新布防。两件事都对——大窗口的长任务需要被再提醒，小窗口不能隔轮提醒一次。落地的规则是：**裁剪真的丢过东西才重新布防，且两次提示至少隔 `CHECKPOINT_MIN_GAP_ROUNDS`（4）轮**。对照实测：qwen longdoc 两次提示隔 2 轮，新规则下只剩第一次；30 轮的长任务照样每 4 轮以上被提醒一次。

**D5 截断要分清是谁满了。**

- 预检加输出预留：`input + reserve ≤ contextSize`，`reserve` 取 `effectiveMaxOutput` 与一个思考余量中较小者（口径与 `budget.outputReserveTokens` 对齐，不另起一套）。
- 新增截断归因：`window-full`（`input + output ≥ contextSize − 余量`）与 `output-cap` 分开；**只有思考、没有正文**的截断单列一类，运行结局不再是 `completed`，日志说「思考用完了窗口，没有写出回答」。
- `window-full` 不走自动「接着写」，直接出截断卡——续写只会让它更满。
- 不改线上字段：OpenAI 兼容这边照旧不发 `max_tokens`（「未设置的模型请求体不变」这条不变量不动）。

> **落地时的两处调整（PR-2）**
> - **预检的输出预留挪到 PR-4。** 估算器把一个汉字算一个 token，而 Qwen 实测约 0.6——在发送闸门上硬扣一份预留，会把其实装得下的中文请求挡在门外，而且报的是 `ContextSizeError`，比截断更难懂。PR-4 的上限保底本来就封顶在 `窗口 − 输出预留`，那是规划侧的软版本，同一件事只做一处。
> - **窗口满了不出截断卡，直接以 `truncated` 结束。** 卡上的「继续」在窗口满时只会再截一次，把一个注定失败的按钮递给作者不是询问；部分正文照样留在输出里，日志那一行说清是窗口满了、该调什么。作者下一轮自己说「继续」时，对话归纳有机会先腾出位置。
> - 归因需要窗口大小和端点的 usage：`input + output ≥ 窗口 − max(64, 3%)` 记为 `window`，装得下记为 `output-cap`，**两者缺一就不下结论**、按原来的路恢复——没声明窗口的模型行为与今天完全一致。3% 的余量盖住「作者声明 32,768 / 服务端实际加载 32,000」这种常见落差。

**D6 思考：开关已经存在，缺的是让作者找得到、以及开着时的兜底。** 同一句短提示（上限 600 token）在 LM Studio 的 qwen 上逐个试开关：

| 请求体 | 思考字数 | 正文 | 结论 |
|---|---|---|---|
| （什么都不发） | 199 | 71 | 默认开 |
| `reasoning_effort: "none"` | **0** | 88 | **唯一管用的** |
| `reasoning_effort: "low"` | 193 | 64 | 被忽略 |
| `enable_thinking: false` | 194 | 66 | 被忽略 |
| `chat_template_kwargs.enable_thinking: false` | 201 | 70 | 被忽略 |
| `thinking: {type: "disabled"}` | 201 | 70 | 被忽略 |
| 提示词末尾 `/no_think` | 107 | 46 | 减半，不可靠 |

`reasoning_effort: "none"` 正是应用里「通用」思考类别（`openai-generic`，OpenAI 兼容端点的默认类别）档位选「关闭」时 `reasoningBody` 发出去的东西（`OPENAI_EFFORT.off = "none"`）。所以**作者今天就能把它关掉**，而且开关并不深：`ReasoningControls` 就在对话输入框底栏（`AgentChat`）、AiPanel 设置行和一致性检查里，档位菜单里有「关闭」（它改的是模型本身的设置，不是单次覆盖）。缺的是**动机**：档位显示「默认」、什么都不发，作者没有任何理由怀疑五分钟的空转是它造成的。

还有一个字面陷阱：**两个控件都叫「关闭」**。模型设置里的思考**类别**有一项「关闭」，说明是「不发送任何思考参数，由服务端自行决定」——在 LM Studio 上它的效果是**思考照开**；真正管用的是「通用 (reasoning_effort)」类别下、输入框底栏那个**档位**里的「关闭」。一个想关思考的作者在模型设置里点到的那个「关闭」，是不管用的那个。关掉之后，经应用自己的 `reasoningBody` 重跑那两个零产出的写作场景（台架 `LOCAL_LLM_EFFORT=off`）：`continue` 315 秒 → **20 秒**写出 819 字，`longform` 358 秒 → **32 秒**写出 2,716 字，都没有截断（§2.3 末两行）。代价是不思考的 qwen 更爱一轮只发一个工具调用——`continue` 用满了 8 轮，是最后那个强制成文的轮次写出的正文。

所以这一片分两半：①让关得掉这件事被看见（M3 的新截断归因里，「只有思考、没有正文」那一类直接指向思考设置）；②开着思考时的兜底——思考超过预算就中止本轮、带一句「直接作答」重试一次，预算默认取窗口剩余的一半。第二半等第一半落地、作者真机用过再定要不要做。

**D7 看门狗放在 `streamCompletion` 一处。** 四个适配器共用：任何 chunk（正文、思考、`toolArgs`）都重置计时；「等首字」和「流中断」分两个阈值，首字的那个按估算输入放大（本地冷预填充量级 ≈ 1.5k tok/s）；超时抛一个带原因的错误，文案说清是哪一种。LM Studio 的工具参数静默是正常形态，所以间隔阈值要以分钟计，不以秒计。

**D8 归纳要有回差。** `planFold` 在「折完预计仍不低于触发线」时拒绝折叠，改为出一次说明（「窗口太小，归纳帮不上这一轮」）——和 `contextBreakdown` 里 `over` 与 `willCompact` 分家是同一个道理。

# 分类的管理面——批量移动、删除，以及 agent 那一侧的缺口

> 状态：**已实施**（三片：墙上多选 →「移到分类」+ 置顶重指；「删除分类」的两出口确认；agent 方案卡的分类 target 轴）。
> 相关：[`lore-collection-plan.md`](./lore-collection-plan.md)（第二根轴，它的管理面是**做全了**的那一根）、
> [`lore-entry-type-plan.md`](./lore-entry-type-plan.md)（分类的类型 schema）、
> [`design-system.md`](../../reference/design-system.md) → 知识库设计语言。

## 1. 问题

集合那根轴的管理面是齐的：建、改名、删、多选批量归入/移出，加上 agent 的
`manage_collection` / `file_lore_entries`。分类这根轴不是。盘下来是三个缺口：

| 动作 | 作者在 app 里 | agent |
|---|---|---|
| 建分类 | ✅ 墙上「+ 新建分类」/ 设置 → 工作台 | ✅ `create_lore_category` |
| 改单条的分类 | ✅ 条目详情页的编辑表单 | ✅ `move_lore_entity` |
| **批量改分类** | ❌ 墙上多选只接集合 | ⚠️ 一条一个调用、方案卡一条一行 |
| **分类改名** | ⚠️ 只改标签，且只对自建分类 | ❌ 刻意没有 |
| **分类删除** | ⚠️ 见下 | ❌ 刻意没有 |

「分类删除」那一格值得单独说，因为它是三个里最容易让作者误解的一个。入口只有一个：
设置 → 工作台 → 自定义知识库分类的 `X`（[`WorkspacePane.tsx`](../../../src/components/settings/panes/WorkspacePane.tsx)）。它

- **只列作者自建的分类**——能力包带来的角色/世界观/势力不在这里，想去掉只能整包关掉；
- **不删任何东西**：只把这一条从 `profile.json` 摘掉，磁盘上的 `.ai-writer/lore/<id>/` 和
  里面的条目一条不动。它们随即变成 **orphan 分类**，继续挂在墙上，标签退化成文件夹 id
  （[`categories.ts`](../../../src/lib/lore/categories.ts) 的 `orphanCategory`）。作者的感受是
  「我删了，它还在，而且名字变丑了」；
- **不确认、不报数**：分类里有 30 条也是一下就摘掉。

i18n 的 `categoriesHint` 是诚实的（「移除分类不会删除其文件夹与条目」），但它印在整段
说明里，不在按钮上——一句写在别处的真话挡不住一次点击。

## 2. 为什么两根轴的管理面天生不对称

不是遗漏，是代价不同，所以**不能照抄集合的做法**：

| | 分类 | 集合 |
|---|---|---|
| 存在哪 | 磁盘文件夹名 | `index.md` frontmatter 的一个字段 |
| 改一次 | 整个条目文件夹搬家 | 重写一行 |
| 归属数 | 恰好一个（**替换**语义） | 任意多个（**只加不减**语义） |
| 谁会失效 | `[[lore:分类/id]]` 路径引用、按 dirPath 存的置顶、同步哈希 | 无 |
| 可逆 | 要再搬一次 | 再点一下 |

[`organizeTools.ts`](../../../src/lib/agent/organizeTools.ts) 顶上那条「分类只给 create」的
不对称，理由正是这一栏。分片 1 不动这条：它做的是**作者亲手**的批量搬家，审批就是作者
自己那一下点击。

## 3. 三条不变量

1. **改分类＝搬家，作者必须先看见影响面。** 批量入口在提交前报「N 条 · 从哪几个分类来」，
   不是一个光秃秃的下拉。已经在目标分类里的条目算跳过、不计入 N——报一个含水的数字，
   下一次作者就不再读它了。
2. **「移除分类」永不删条目，但也不许假装删了。** 现状的一半（不删）是对的，另一半
   （不说）不是。分片 2 的出口只能是两个：把条目搬去另一个分类，或明说文件夹留下。
3. **置顶按 `dirPath` 存，所以搬家必须同步重指。** [`pins.ts`](../../../src/lib/lore/pins.ts)
   的键是绝对路径（含 `#facet` 后缀）。不重指的话，批量移动 20 条 = 静默取消这 20 条的
   置顶，而作者要等到下一次运行读到一段没带人设的正文才发现。这条是分片 1 里唯一
   「不做也能跑」但必须做的部分。

## 4. 分片 1（已实施）：墙上多选 →「移到分类」

墙上的多选（勾选框 / ⇧ 连选 / 框选）本来就在，只是动作条只挂了集合的两颗按钮。这一片
在同一条动作条上补第三颗，落在集合两颗**之前**——分类是第一根轴。

- `moveEntitiesToCategory()`（[`entity.ts`](../../../src/lib/lore/entity.ts)）：照
  `fileEntities` 的形状——逐条 try/catch、已在目标分类的跳过、单条失败不中断整批，返回
  `{ moves, skipped, failed }`。`moves` 里带旧新 dirPath，因为调用方要拿它重指置顶。
- `repointPins()`（[`pins.ts`](../../../src/lib/lore/pins.ts)）：纯函数，按 `dirPath` 前缀
  重写置顶串，`#facet` 后缀原样带过去。
- `useLoreStore.moveEntitiesToCategory()`：搬 → 重指置顶 → 重扫。不碰 `profile.json`，
  所以住在 loreStore 而不是 projectStore（对比 `fileIntoCollections`，它要补集合声明）。
- `CategoryMoveMenu`（[`components/lore/`](../../../src/components/lore/CategoryMoveMenu.tsx)）：
  **单选**的菜单，不是勾选清单——分类是替换语义，三态复选框在这里是错的话术。视觉走
  **分类色点**，不碰集合的装订语汇（`3px double` 一次都不用）。
  - 目标列表用 `loreCategories()` 而不是 `assignableCategories()`：**orphan 不能当目标**，
    往一个没有能力包声明的文件夹里搬东西，是在制造第二个第 1 节里的问题。
  - 当前分类那一行照常列出、标「已在此」并禁用，因为「都在这儿了」本身就是一次有用的
    回答；藏掉它只会让作者以为自己漏点了。
  - 底部一行常驻脚注：这一批会搬家，`[[lore:分类/id]]` 形式的路径引用会改指——不是
    弹窗，是脚注，因为它每次都成立、而每次都弹的东西第三次就被无视了。

**没做的**：撤销。搬回去是再选一次同一批（选择态在提交后保留，正是为了这个），而
`.ai-writer/backups/` 那套是文件级的、对文件夹搬家帮不上忙。

## 5. 分片 2（已实施）：让「删除分类」做它字面上的事

一次确认（[`CategoryDeleteModal`](../../../src/components/lore/CategoryDeleteModal.tsx)），
先报「里面有 N 条」，再让作者说它们去哪：

- **连同 N 条移到 ⟨另一个分类⟩** —— 复用分片 1 的 `moveEntitiesToCategory`。
- **只移除分类，保留文件夹与条目** —— 今天的行为，但这次把后果写在选项里：条目一条
  不少、AI 照常读得到，而这个分类会退化成「未声明」，标签变成文件夹 id，也不能再在
  里面新建条目。

两个出口是**并列的两张卡**而不是一个复选框：复选框会让「没勾」也成为一个默认后果，
而这两条路的结果差得很远。默认一条都不选，确认键跟着禁用——删除是不可逆那一侧，作者
必须主动说出他要哪一条。

三处和 §5 原计划不同，都是做的过程中发现的：

1. **入口不是「搬走」，是两扇门共用一次确认。** 原计划说把入口从设置页搬到墙上分类
   芯片的右键菜单。真搬了之后，设置页那颗 `X` 要么消失（但重命名还在那儿，一半功能
   搬走一半留下更难理解），要么留着——而留着一颗没有确认的 `X`，等于开了第二扇更差
   的门。最后是**两处都开这一个弹窗**：墙上分类芯片右键，和设置 → 工作台的 `X`。
2. **orphan 分类拿到了一条真出路。** 原计划没提它。orphan 没有声明可摘（「保留文件夹」
   对它等于什么都不做），但**把条目搬走**是真的出路——`scanLore` 只把「至少有一条」的
   目录算成 orphan，搬空之后那个文件夹自己就从墙上消失了。所以 orphan 的菜单项是
   「把 N 条搬走并清空…」，弹窗里只剩搬这一条出口。
3. **候选名单收进了 `relocationTargets`**（[`categories.ts`](../../../src/lib/lore/categories.ts)）。
   两扇门各算一遍「能搬去哪」，是这类重复最典型的走样方式。它和 `assignableCategories`
   只差一条，而那一条正是这个文件开头的不对称：orphan 是「有什么」的答案，永远不是
   「能放哪」的答案。

另外两条实现纪律：

- **先搬条目、再摘声明。** 反过来的话，摘声明会先把分类变成 orphan，而搬家失败时作者
  就同时失去了分类和一次干净的重试。现在失败会抛回弹窗，`profile.json` 一个字都没动。
- **能力包带来的分类仍然不给删**——那是包的定义，删它的地方在工作台的包开关。右键菜单
  把这句话**留着并禁用**，而不是把菜单项藏掉：藏掉会让作者以为自己点错了地方。

「保留文件夹」那条出口所承诺的降级形态（标签退化成文件夹 id、不能在里面新建），以及
「搬空之后分类自己消失」，都由 [`orphanCategories.test.ts`](../../../src/lib/__tests__/orphanCategories.test.ts)
既有的用例锁着；这一片新加的用例只覆盖 `relocationTargets`。

## 6. 分片 3（已实施）：给 `move_lore_entity` 接上 target 轴

`plan.ts` 的步骤本来就有 entity / collection / **category** 三种 target，但 `move_lore_entity`
过门时 target 恒为 `entity`，所以「把这 12 条挪到势力」在方案卡上是 **12 行**——
[`organizeTools.ts`](../../../src/lib/agent/organizeTools.ts) 开头说的「一张让作者橡皮图章的
卡」，集合那侧躲开了，分类这侧一直踩着。

现在一条 `{ action: "move", target: "category", entity: "势力", members: [...] }` 的步骤就够，
`move_lore_entity` 逐条兑现它（[`writeTools.ts`](../../../src/lib/agent/writeTools.ts) 的
`moveGate`）。授权边界不变：**只动 `members` 列出的那些**，批准 12 条不是批准第 13 条。

三条在真机上**不报错**、因而必须写下来的：

1. **卡上是标签，工具收的是 id。** 方案是写给作者读的，步骤上写「势力」；`move_lore_entity`
   的参数是文件夹 id（`factions`），因为那是它 enum 里的值、也是扫描器认的东西。字符串
   直接比会把**刚批准完的**每一次批量搬家都拒掉——作者读到的是「agent 坏了」。所以
   `plan.ts` 有 `sameCategory`，和 `sameEntity` 在另一根轴上做同一件事。
2. **`category` + `move` 装的是 `lore_write`，不是 `lore_organize`。** 这一条是做的过程中
   踩出来的：只改了 target 那一侧之后，一份只有一条 category/move 步骤的方案（正是这次
   要造的那种「一行卡」）会把组织结构工具装上、却**不装** `move_lore_entity`——作者批准了，
   模型却拿不到兑现它的工具，而且不报错，它只是看不见那个工具名。映射因此收进
   `planLoadsEntityWrites` / `planLoadsOrganize`（[`plan.ts`](../../../src/lib/agent/plan.ts)），
   和 target 轴住在一起，而不是散在 `runtime.ts` 的循环里。
3. **改名不吃这条路。** 一个分类步骤说的是「谁搬进来」，从来不是「顺便改个名字」——
   `moveGate` 只在带 `new_category` 时才回退到分类步骤。

**仍然不加**分类的改名/删除工具：§2 那一栏没变，而分片 2 落地之后，作者在 app 里已经有
做这件事的地方（`create_lore_category` 的工具结果现在直接指向知识库墙的分类右键）。

代价记在 [`agentToolBudget.test.ts`](../../../src/lib/__tests__/agentToolBudget.test.ts)：常驻
那一半 **9,457 → 9,453（−4）**，因为两句 schema 说明是**改写**而不是新增，都比它们替掉的
那两句更短；真正的 +51 落在 `move_lore_entity` 上，而它是延迟装载的——一次运行只在作者
批准了方案之后才付这笔钱，也正是那句话唯一可能改变模型行为的时刻。

## 7. 被否掉的

- **把分类做成多值、和集合合并成一根轴。** 分类是文件夹，一个条目在两个文件夹里要么是
  硬链接要么是复制，两个都会让「改一条」变成「改哪一份」。而且类型 schema 挂在分类上，
  多值分类等于一个条目同时受两套槽位约束。
- **批量移动走 L2 审批卡。** 这是作者自己在 UI 上点的，不是模型提议的；给它套一张审批卡
  是把「你确定吗」写成了「模型想这么做，你批不批」，主语错了。
- **移动后把旧文件夹留一个 tombstone 让旧引用还能解析。** `[[lore:…]]` 已经有按名字回退的
  一路（见 `citations.ts`），tombstone 会让扫描器看见一个没有 `index.md` 的空目录，代价
  落在每一次扫描上，换回来的是一条已经被覆盖的回退路径。

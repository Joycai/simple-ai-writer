# Project-scoped semantic retrieval Beta

> Status: `shipped` · live Ark Agent Plan embedding smoke test verified (2026-10-09); broader retrieval quality remains unverified. Protocol fixtures and offline integration tests cover the implementation.

## Intent and design

An author can describe a task without naming the relevant knowledge-base entry. Existing name/alias matching and explicit links remain authoritative; this optional channel discovers additional entries from their compact descriptions. The author requested a **per-project Beta switch**, selectable local or hosted embedding/reranker models, and the existing theme system.

Settings → AI configuration → Labs contains **Semantic retrieval · Beta**. Its first row identifies the current project and has the existing square Toggle. Off is the default. No open project means an explanatory empty state instead of an actionable switch. On reveals an optional embedding selector, optional reranker selector, and a minimum relevance score. At least one model is needed. Neither selection silently falls back to a chat model.

Model registration lives exclusively in **Channels & Models**. The model type chips and list filters include **Embedding** and **Rerank**. Their shared drawer edits channel-bound identity, fee group and dedicated retrieval format/path; embedding models additionally offer query/document prefixes. Chat limits, thinking, sampling, capability probing and chat-route controls do not apply. Existing theme colours are reused for the new type badges without expanding the theme contract.

Labs contains only project enablement, typed model selectors, minimum relevance and index preparation. A hint directs authors to Channels & Models to manage models. Only enabled models with an existing channel appear as choices. Missing, deleted, disabled or retyped selections stay visibly unavailable until replaced; there is no silent fallback. Models are installation-wide, while enablement and selections use `prefs.ts`'s project-keyed family `lore:semantic:`. Like existing project pins/scope, these are per-project **on this device**, not portable project files or app-config backup entries.

Legacy registrations stored as text models are normalized on DB/backup reads from their existing retrieval format into embedding/rerank types, preserving ids, paths, prefixes, fee groups and project selections. Typed rows missing a retrieval format receive the corresponding default. Both types remain excluded from conversational pickers even when format metadata is absent. Switching a model back to a conversational type clears its retrieval declaration on save so it can be selected for chat again. This unifies model maintenance without changing the retrieval protocol or paid execution flow.

The production Section / Row / Toggle / Select / form controls carry the app's Settings palette and typography. Turning the switch off hides the project controls but preserves configuration and makes no retrieval request. Saving configuration itself never calls a model.

## Pipeline and invariants

The first Beta applies to **writing tasks and assistant chat**, including subsequent chat turns. Roleplay and consistency-review retrieval retain their existing rules. This boundary avoids changing their binding/memory and exhaustive-review semantics in a retrieval experiment.

1. Run existing pins, exact matches, facet rules and linked-entry expansion unchanged.
2. Filter the semantic candidate catalog by the source scope and existing selections/resident exclusions **before transmitting any descriptions**. Pins retain their existing ability to cross the scope fence.
3. Each description contains the entry name, aliases, summary and non-manual facet titles/keys. No full entry bodies or images go to the retrieval endpoint. A connection absent from these descriptions cannot be inferred reliably: authors should improve the summary rather than expect the selector to invent it.
4. Embedding-only: encode descriptions, encode the query, rank by cosine similarity. Reranker-only: score the eligible catalog directly. Combined: embeddings produce 30 candidates and the reranker determines the final score. A reranker never sees only keyword matches; that would fail to recover unnamed entries.
5. Apply the configured score threshold (default 0.5, **not a probability**) and select at most five. Empty results are valid. The embedding threshold is not applied ahead of the reranker.
6. Load their real bodies through `selectLore`, using only remaining context space. Each semantic entry's summary must also fit; it does **not** receive the normal named-entry L0 guarantee. Existing matches are never displaced. Facets still obey keys, manual mode, exclusions, groups and the whole-facet budget rule. Semantic entries do not recursively expand references.
7. Report semantic provenance, score, counts, catalog/query/description truncation, top-five cap, budget drops, timeout or unavailable service. Task results show this in the injection report; assistant chat stores it on `context-seeded`, even if no text was injected.

Limits intentionally bound the initial experiment: 256 eligible descriptions in deterministic path order, 1,600 characters per description, 4,000 characters of query, batches of 32 embeddings and 20 seconds for the whole semantic phase by default; the verified Ark Agent Plan endpoint uses batches of 10 and a 60-second whole-phase deadline. Writing-task intent is placed before the selection so a long selection cannot displace the author's request. A larger catalog reports omissions and can be narrowed with the source scope. Pagination, persisted indexes and a general language-model selector are not part of this Beta.

Embeddings are persisted in the project's `kb_embeddings` table. Each row stores a relative entry path, SHA-256 description hash and validated vector, partitioned by a versioned hash of effective endpoint, model ID and retrieval configuration. Credentials and source descriptions are not stored. Unchanged descriptions survive restarts; edits replace only that entry's row. Deleted entries are pruned across namespaces on the next indexing pass using the full catalog, never the narrowed source scope. Different model/configuration namespaces remain separate and can be reused when switching back. Query embeddings remain fresh.

The source files remain authoritative; the table is disposable derived data. Malformed stored vectors are treated as misses. A dimension mismatch invalidates the namespace and visibly falls back rather than mixing vectors. A provider replacing a model without changing its ID or dimensions cannot be detected automatically; Rebuild index is the explicit recovery action.

## Transport, persistence and usage

`ConnOptions.retrieval` owns the transport configuration. `Model.retrieval` references its type; the `models.retrieval` JSON column survives save/load and config export/import. These models are excluded by `conversationalModels`, labelled by purpose in Channels & Models, and refused by `streamCompletion` as a final guard against stale/direct bindings.

Supported formats: OpenAI-compatible float embeddings, Ollama native `/api/embed`, DashScope native multimodal embeddings (text input only), Cohere-compatible rerank and DashScope native text rerank. `qwen3.7-text-rerank` requires the dedicated DashScope rerank format: `input:{query,documents}` plus `parameters.top_n`, reading `output.results` and prompt-token usage. Purpose classification is shared by model normalization, the drawer and retrieval routing, so both rerank formats stay out of embedding selectors and execute only as rerankers. Its default host-root path is `/api/v1/services/rerank/text-rerank/text-rerank`; changing a Cohere path alone would leave the body and response incompatible. For `qwen3.7-text-embedding-flash`, select OpenAI-compatible embeddings on the official `/compatible-mode/v1` base; its documented 20-text batch cap applies to both index preparation and on-demand retrieval. The same cap is documented for `qwen3.7-text-embedding`; unrelated endpoints keep their own limits. The DashScope format uses independent `input.contents` text items, reads indexed `output.embeddings` and input token usage, and shares a 20-item batch limit across preparation and on-demand indexing. It is selected explicitly in the model drawer, because a model name alone cannot distinguish native serving from a compatible relay. The default native path is host-root `/api/v1/services/embeddings/multimodal-embedding/multimodal-embedding`, so it also works when the channel’s conversational base ends in `/compatible-mode/v1`; credentials stay on the same host. Existing cache namespaces include the retrieval format, so switching interfaces cannot mix cached vector spaces. Endpoint paths are configurable but same-origin; an endpoint path cannot forward a channel key to a different host. Bearer credentials use the existing keyring and empty local keys omit Authorization. HTTP(S) requests use the existing Tauri HTTP bridge. Other proprietary APIs are **not** made compatible by model name alone; they require an adapter or compatible serving layer. Wire references are in [retrieval.md](../../api/retrieval.md).

Malformed vectors, dimension changes, missing/duplicate indices and invalid rerank scores are refused. A failed/unconfigured selected model or deadline returns the original matching result and a visible status; it does not silently use a different retrieval mode. The user's cancellation propagates and stops the parent request. The timeout races the whole phase so an endpoint that ignores cancellation cannot hold the writing request indefinitely.

Every successful retrieval response records usage through `recordUsage` in both ledgers using the selected model's fee snapshot. OpenAI/Ollama input token counts and Cohere search units are read when present; missing counts are not guessed. Tasks are `kb-embedding` and `kb-rerank`. Fee groups remain the only pricing source. No prices are fetched or invented; users configure the appropriate token/request/spec fee group. Cache hits produce no document-embedding request and no corresponding usage row. No automatic retries amplify costs.

Existing retrieval and repository guard tests also run.

Report these separately from protocol correctness. A live endpoint is not selected automatically for testing.

## Chat report and endpoint correction (1.95.1)

The semantic report is an execution-log list row with the shared marker, typography and padding. Its own content wraps long entry names and status text within the available width. Failure reports preserve only a typed reason and HTTP status, never raw upstream errors or credentials. Legacy saved reports without these fields still render.

The default OpenAI embedding path now follows the channel API prefix: a channel ending in `/api/plan/v3` calls `/api/plan/v3/embeddings`, rather than dropping the prefix and calling the host-root `/v1/embeddings`. Root-only local channels continue to use `/v1/embeddings`; custom non-default paths remain host-root paths. This fixes the generic default for prefixed providers without changing user channel configuration. Authenticated Ark inference was subsequently verified on the author-supplied `/api/plan/v3/embeddings` endpoint with `doubao-embedding-vision`: HTTP 200, indexed 2,048-dimensional float vectors, and the relevant fictional entry ranked first. This verifies the wire format and endpoint, not the native keychain/UI path.

First-turn assembly no longer appends the author matching text twice to the semantic query. The 4,000-character bound still applies to genuinely long queries and remains visible as an informational notice.

## Ark Agent Plan batch correction (1.95.2)

The earlier four-input smoke test did not exercise the catalog batch size. The Agent Plan endpoint rejects 32 inputs with HTTP 400 and an explicit maximum of 10. Retrieval now selects a 10-input batch size by the effective official endpoint and OpenAI embedding format, not by the model name (which may also be served by unrelated providers). Other endpoints retain the existing defaults.

The extra sequential round trips for a cold catalog receive a bounded 60-second total deadline, measured from the start of retrieval, including credential lookup and reranking. This is not a per-batch reset. Cancellation, keyword fallback, usage recording and completed-batch caching remain intact; repeated requests reuse those vectors. Very slow cold catalogs can still time out rather than block writing indefinitely.

## Persistent preparation (1.96.0)

The author approved Prepare index / Rebuild index with progress and ready/outdated status. A compact, token-themed cache panel sits inside project retrieval settings, below model and threshold controls; model registration remains in Channels & Models. It is shown only with an embedding selection. Empty scope, loading, storage/model failure, progress, stopped and complete states have explicit text in both languages. Buttons wrap on narrow layouts and progress has an accessible label. Rebuild confirms the paid regeneration; preparation describes the selected-service transfer beside its action.

Prepare covers all entries in the current source scope, including those beyond the per-request 256-candidate retrieval bound. It fills only missing/changed vectors. Rebuild first invalidates the current scope in the selected namespace, then regenerates it. This makes a stopped rebuild resumable with Prepare instead of mistaking unfinished old vectors for ready data; other scopes and namespaces remain intact. Completed batches are saved transactionally and reused after an interruption. Each preparation request has the provider's bounded timeout; unlike a chat turn, explicit preparation has no whole-catalog deadline. Closing settings, changing scope/model, switching projects or Stop cancels the work. Per-project/namespace serialization prevents duplicate preparation by concurrent chats within one app instance; separate app instances may still encode the same missing entry concurrently, with safe atomic upserts.

On-demand retrieval uses the same persistence and batch logic. Cache writes use the established SQL transaction bridge; every successful inference still records usage via the existing ledger. No background paid work starts merely by opening settings. Status reads compare hashes locally. The project database follows existing project backup rules; the cache is not part of shared KB tree sync or app-config export. Old model namespaces are retained for reuse; automatic disk-size eviction is not included in this iteration.


## Current-document background retrieval (1.99.3)

Status: `shipped` · offline integration coverage; real-document relevance and latency remain `unverified`.

The author requested current-document retrieval to avoid repeatedly sending a large manuscript to a long-context model. The earlier expanding verbatim window can grow to hundreds of thousands of characters on a million-token model. A second, default-off **Retrieve from the current document** switch appears under the project's semantic retrieval controls. It reuses the selected models and score threshold; document retrieval requires an embedding model and optionally reranks. Opening settings or changing the switch performs no inference. The existing KB retrieval switch remains the parent opt-in. Assistant chat, roleplay, consistency review and other documents retain their previous policies.

Writing tasks pass an explicit project-relative document identity and the current editor snapshot, including unsaved changes. Task behavior still follows declarations, never task IDs. The recent-background allocation is capped at 16,000 characters in both the planner and the panel forecast. Recap layers share a separate 12,000-character cap while this mode is enabled, so the freed space is not refilled by unbounded memory/book recap budgets. The background cap includes a local window of up to 6,000 characters immediately before the edit/append anchor, plus retrieved excerpts and their character-offset labels. An explicit smaller reference window is respected; zero disables document retrieval. A short document needs no paid retrieval. Edits, polishing and summaries keep their **entire selection** as the task input: retrieval only replaces background, never the material to be rewritten or summarized. Consequently selecting a whole document to summarize or rewrite still transmits that whole selection. This feature does not implement hierarchical whole-document summarization.

Only text **before** the anchor and outside the retained local window is eligible; this preserves the existing no-future-text rule for a mid-document edit. Background is split into content-defined chunks of at most 1,200 UTF-16 units, favouring paragraph boundaries and overlapping by 159–160 units without splitting surrogate pairs (algorithm below). The query includes bounded author requirements/direction, task instruction, selection and nearby text (at most 4,000 characters). Embeddings rank the chunks, an optional reranker scores a 30-chunk shortlist, and the final threshold/budget admits at most six non-overlapping passages in source order. The prompt labels these as excerpts, never as a full-document representation. The task result shows status, candidate count, included offsets and scores alongside its existing context report.

Chunking scans only the eligible prefix with bounded lookahead and a bounded minimum queue. It remains linear in the scanned prefix even without paragraph breaks; the 4,096-chunk overflow sentinel stops oversized nonblank catalogs before indexing.

Vectors and content hashes live in a separate `document_embeddings` table in the project database. This separation is essential because existing KB pruning removes all rows absent from its catalog. A document namespace hashes its project-relative file identity, endpoint/model/configuration and chunk algorithm version; rows use prefixed text hashes, so unchanged chunks can be reused across restarts or offset shifts. No source prose, filenames or credentials are stored in cache rows. Only the current document namespace is pruned after a successful indexing pass. Document-cache reads and batch writes enforce the namespace LRU policy below, including for old model and deleted-file namespaces. The cache follows existing project database backup rules and is not app-config or shared KB-tree sync data.

First execution may encode many chunks and incurs usage. Completed batches survive cancellation/timeouts; subsequent executions reuse them and issue only missing chunk requests plus a fresh query and optional reranking. Provider-specific batch limits remain shared with KB indexing. Retrieval has a 60-second whole-phase deadline and a 4,096-chunk catalog limit; oversized catalogs report the limit instead of silently indexing an arbitrary prefix. Unconfigured/unavailable models, changed dimensions, timeouts, oversized catalogs and zero admitted excerpts fall back to contiguous prose before the anchor, filling the planned background allocation (at most 16,000 characters). This avoids wasting the remaining budget while preserving the cap and the no-future-text fence. Failure reports remain visible. A task snapshots retrieval preferences once for planning, KB retrieval and document retrieval so a later settings change cannot alter its allocation. Author cancellation stops the parent task. Serialization releases on abort even when a transport ignores cancellation. Selected edit/summary material remains intact in all failure cases.

Successful requests use the existing model/fee snapshot and dual-ledger `recordUsage` path under `document-embedding` / `document-rerank`; no new price formula is introduced. There are no paid background jobs or automatic retries. Offline tests cover chunk offsets, anchor fences, budget and forecast agreement, complete selections, opt-out compatibility, cache reuse/isolation, changed text, dimension invalidation, thresholds, timeout recovery, cancellation and usage task labels. They do not establish retrieval quality on author documents.


### Document cache lifecycle (1.99.11)

Document caches are bounded per project to **eight namespaces** and **64 MiB of live UTF-8 payload** (namespace, entry/hash keys and serialized vectors). A namespace is the existing document-path/model/configuration hash, so renaming/deleting a document or changing models cannot leave unlimited abandoned namespaces. These conservative fixed limits are cache policy, not model limits or author preferences. They bound the derived data carried forward while retaining several recently used documents/models; they do not promise a whole large book will fit.

`document_embedding_access` stores only namespace hashes and an access sequence. Cache hits and batch writes advance a SQLite sequence inside `sqlTransaction`, avoiding clock ties, clock rollback and per-window in-memory LRU state. The same transaction removes least-recently-used whole namespaces until the newest prefix fits both limits and removes orphan access records. Payload accounting is recomputed from rows, so replacement, namespace pruning, corrupted rows and an older build's writes cannot drift a persisted byte counter. Oversized individual namespaces are discarded before ranking the rest; one large document must not flush every smaller cache. Subsequent batches can still retain a partial cache for that document.

Existing databases need no destructive migration: the access table is created lazily, and rows without recency metadata are oldest (namespace order breaks legacy ties). The next document-cache read or batch write enforces both limits. A current read touches its namespace before eviction. The KB embedding table, usage ledgers, chat history and source files are untouched. Projects that never retrieve again are not scanned in the background.

A retrieval pass owns a validated in-memory vector map after its first read and adds each completed batch to that map. Eviction by a concurrent document/window may remove persisted rows but does not invalidate those vectors or restart the pass. We intentionally do not pin active namespaces: pinning would let simultaneous large documents defeat the storage bound, and process-local leases cannot protect against another app window. Transactions atomically combine batch insertion, access update and eviction. Cancellation and timeout keep the existing completed-batch recovery behavior subject to normal cache pressure. Evicted vectors are recomputed only during a later author-triggered retrieval and can incur provider usage; eviction itself never calls a provider or deletes usage history.

The bound covers **live payload**, not total `project.db` size, SQLite indexes/page overhead or its WAL. Deleted pages become reusable; an already-large database does not shrink immediately. No automatic `VACUUM` runs during retrieval, because that would lock/rewrite the author database. Project backup still checkpoints and copies the entire database, including surviving cache and access records; restoration preserves recency and the next retrieval enforces limits again. Shrinking an existing database's physical high-water mark is not claimed by this policy.

SQLite-backed tests cover first-use legacy eviction, count and byte pressure, oversized namespaces, read-hit recency, file/model replacement identities, concurrent writes, untouched KB/user tables, and checkpoint/copy/reopen restoration. Retrieval tests additionally force eviction of every completed batch and verify the current run still completes without duplicate embedding work.


### Stable document chunks (1.99.12)

Fixed offsets and greedy paragraph packing both let an early insertion shift later groups, invalidating otherwise unchanged embedding inputs. `document-cdc-v2` instead chooses content-defined anchors: a rolling 32-unit polynomial hash, mixed to a 32-bit fingerprint, is a boundary candidate when it is the unique minimum within 240 units on either side. Paragraph-end fingerprints receive a fourfold preference. The hash never resets at a cut, and minimum selection is independent of previous cuts. Once an edit leaves this bounded neighbourhood, unchanged content has the same natural anchors at shifted offsets.

Chunks retain a 1,200-unit hard maximum and 160-unit backward overlap (159 where necessary to keep a surrogate pair intact). Hard cuts fill gaps without natural anchors, and a short final chunk covers the remaining eligible prefix. The minimum queue holds at most 481 positions; no full-document fingerprint array or repeated prefix search is needed. Lookahead never crosses the eligible prefix, including the local-window boundary. Returned offsets always refer to the current snapshot. An anchor inside a surrogate pair excludes that code point from indexing.

Equal minima are not anchors: repetitive/constant text uses bounded hard cuts rather than generating tiny chunks at every character. Consequently this improves reuse, but does not guarantee every edit changes only a fixed number of chunks; anchorless regions can still shift. Existing content-hash deduplication applies to repeated chunks. Smaller content-defined chunks may increase catalog count, and the existing explicit 4,096 limit and contiguous fallback still apply.

The algorithm version participates in the namespace hash. The first eligible retrieval after upgrade builds a new namespace and can incur embedding usage; old namespaces age out under the existing LRU rather than being mixed with the new algorithm. No background migration or paid inference runs on upgrade. Offline integration tests require over 85% of cached embedding inputs to survive an early insertion/deletion in the retrieval fixture. Varied prose fixtures, both paragraph-separated and unbroken, require over 90% chunk reuse across four insertion positions, alongside offset/overlap/UTF-16/no-future regressions. These are fixture measurements, not a general cost or retrieval-quality guarantee.


## Shared model changes and deletion (1.99.14)

Model settings are app-wide, while retrieval selections belong to each project. Before saving a change to a retrieval model's type, enabled state, endpoint model ID, channel, active route, format, path or input prefixes, the model drawer asks for confirmation. Name and fee-only edits do not interrupt saving. The existing model/channel deletion dialog includes the same dependency policy, including retrieval models removed with a channel.

The active project's embedding and reranker IDs are checked even when retrieval is disabled: switching the Beta off does not remove the binding. A known binding is identified as belonging to the current project. Other projects are explicitly unverified; there is no global project count or filesystem scan. An unbound retrieval model still receives the uncertainty warning because other projects may select it. Existing stale bindings also qualify for deletion warnings.

Cancel leaves the model intact. Confirm performs the requested mutation but preserves project selections and caches. Automatically clearing or substituting a model could silently change retrieval behavior and provider usage; instead, the warning directs the author to each affected project's Labs retrieval settings to choose a replacement. Changes can require new embeddings and incur usage on the next author-triggered retrieval; the warning itself performs no inference. Channel editing, bulk config import and external config changes are outside this model-edit/deletion guard.

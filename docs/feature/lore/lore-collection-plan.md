# 知识库集合（Collections）——第二根轴

> 状态：**已实施**（数据层 + 设计稿 03 屏 24–31 的全部 UI + agent 的整理工具，见 §8）。设计任务书见
> [`lore-collection-ui-brief.md`](./lore-collection-ui-brief.md)，视觉口径见
> [`design-system.md`](../../reference/design-system.md) → 知识库设计语言 → 集合。
> 相关：[`lore-entry-type-plan.md`](./lore-entry-type-plan.md)（分类的类型 schema）、[`lore-facet-plan.md`](./lore-facet-plan.md)（条目内的粒度）。

## 1. 问题

一个项目的知识库里同时躺着好几摊互不相干的活——小说 A 的人物、小说 B 的人物、项目甲的
材料。作者的原话：

> 他们有时候需要互相引用来写作，有时候我又希望引用材料在某个集合内。

分类（category）解决不了这件事：它回答的是「这条**是什么**」，而且是磁盘上的文件夹、
带类型 schema。拿分类去凑「小说A-人物 / 小说B-人物」会让分类数按 作品 × 类型 爆炸，
还丢掉每个类型自己的槽位（用户自建分类没有 schema）。这是第二根轴，不是第一根轴的
更多取值。

## 2. 两根轴

| | 分类 category | 集合 collection |
|---|---|---|
| 回答 | 这条**是什么** | 这条**属于哪一摊活** |
| 例 | 人物 / 世界观 / 势力 | 小说A / 小说B / 项目甲报告 |
| 来源 | 能力包 + 作者自建分类 | 全部作者自建 |
| 归属数 | 恰好一个 | **任意多个，也可以零个（未归集）** |
| 磁盘 | 文件夹名 | 条目 frontmatter 的一个字段 |
| 类型 schema | 有 | 无 |

**取材范围（scope）** 是集合的用处所在：一个全局开关（一个集合名，或 null ＝ 全部），
按项目持久化，**手动切换**。生效时，AI 的自动取材只在这个集合里发生。

## 3. 四条不变量

1. **集合是字段，不是目录。** 见 §4.1。
2. **围栏只挡自动发现，不挡显式指定。** 置顶、`@` 引用、`[[lore:…]]`、点开的条目、
   扮演角色的绑定条目一律穿过围栏；被挡住的只有「自动匹配」和「模型自己去翻清单」。
   `selectLore` 里这条写成：`scope` 与 `excludeDirs` 一起只作用于 auto-match 循环，
   pin 解析发生在它之前。
3. **未声明的集合照样算数。** 作者手写进 frontmatter 的集合名要能看见、能筛、能当
   围栏用，只是不占声明列表的顺序。和孤儿分类同一套降级哲学——否则「墙上看得见的」
   会比「模型看得见的」还少，那正是 `indexCategories` 存在的理由。
4. **取材方式不变。** 仍然是名称/别名在正文里出现才注入。集合只缩小候选池，
   不是「整集塞进上下文」。

## 4. 取舍

### 4.1 为什么不是目录层级（`lore/<分类>/<集合>/<条目>/`）

看起来更直观，但 `dirPath` 这个字符串已经被四样东西持久化了：AI 面板的置顶
（`ai:pinnedLore:<project>`）、`[[lore:…]]` 引用、扮演角色的 `boundPaths`、知识库
同步的逐条内容哈希。加一层目录等于同时作废这四样并做一次有丢失风险的迁移。

而且**多归属根本没法用目录表达**——一条共享世界观要同时在两本小说下面，目录只能靠
复制或符号链接，两条路都会让「同一条条目」在墙上变成两条命运不同的文件。

frontmatter 是纯追加：缺席即「未归集」，老项目一个字节不用改，同步和导出白搭车
（内容哈希本来就覆盖 frontmatter）。

### 4.2 为什么集合的 id 就是它的名字

分类的 id 必须是 ASCII slug，因为它是文件夹名。集合没有这个约束，于是直接用名字本身
——这个值会落到作者每天要读的 frontmatter 里，`collections: ["小说A"]` 是能读的，
`collections: ["kb-2"]` 不是（`suggestCategoryId` 对纯中文标签正好产出 kb / kb-2 /
kb-3）。这个仓库里知识库是**作者会手改的纯文本**，可读性该赢。

代价：重命名要改写所有成员条目的 frontmatter（`refileCollection`）。那是个罕见操作，
而且改的东西作者看得见。

### 4.3 为什么多归属，而不是「单归属 + 一个公共集合」

单归属更简单，但表达不了「这份材料属于 A 和 B，但不属于 C」——只能要么进公共集合
（对 C 也可见），要么复制一份。作者的原话正是「有时候需要互相引用」，共享材料是常态
而不是例外。多归属让共享条目天然落在每个相关集合的范围内，不需要任何逃生口。

### 4.4 为什么是手动切换，不跟当前文档自动切

（作者选的。）自动跟随需要「集合 ↔ 文档分组」的绑定，是另一套配置，且一本书跨多个
文件夹时 1:N 要额外处理。手动切换先做，绑定留给以后——那时它是「默认值从哪来」的
问题，不影响这里的任何数据格式。

### 4.5 为什么没有「整集注入」

（作者选的。）报告类材料靠名字匹配可能命中不了，整集注入对那种场景更有用；但它是
另一种取材策略（预算填充 + 优先级丢弃），先把围栏做对。要加时它是 `selectLore` 的
一个新分支，不动存储格式。

## 5. 数据格式

**条目**（`.ai-writer/lore/<分类>/<条目>/index.md` 的 frontmatter）：

```yaml
---
name: "艾莉亚"
aliases: []
category: characters
summary: "北境骑士团副团长"
collections: ["小说A", "共享设定"]
---
```

未归集就**不写这一行**——已有的知识库在作者真正归档之前逐字节不变。写成带引号的行内
数组，名字里有逗号也能原样读回来；解析侧同时吃手写的 `collections: [小说A, 共享设定]`
（轻量 frontmatter 解析器对没引号的 CJK 行内数组交回的是一个字符串）。

**声明**（`.ai-writer/profile.json` v3，可选字段）：

```json
{ "version": 3, "enabled": ["novel"], "collections": ["小说A", "小说B"] }
```

只存声明，不存成员——成员在条目自己身上。这个列表存在只为两件成员关系表达不了的事：
**作者排的顺序**，和**一个还空着的集合**（先建集合，再往里装）。文件版本号没有跟着
涨：这是 v3 的一个新增可选字段，缺席即「全部集合都从条目里发现」。老版本 app 重写
profile.json 会丢掉这个列表，但**丢不掉归属**——集合会退化成「未声明」，即 §3 的
第 3 条，顺序和空集合没了，别的都在。

**取材范围**（`config.db` 的 prefs，按项目一行）：`lore:scope:<projectPath>`。
「全部」写成删掉这一行而不是存空串。项目从最近列表移除时随置顶一起清理
（`prunePrefsWithPrefix`）。

## 6. 围栏落在哪儿

围栏有两个作用面，语义不同，所以是两处而不是一处：

| 作用面 | 落点 | 语义 |
|---|---|---|
| 自动注入 | `selectLore(..., { scope })` | 只收窄 auto-match；pin 在此之前解析，因而豁免 |
| 模型的清单 | `ToolContext.loreScope` → `formatLoreIndex` | `list_lore_entities` 只列范围内的，并**报出挡掉了几条** |

`ToolContext` 存的是范围本身而不是一份过滤过的索引，因为 `findEntityByName` 一路不
设防：作者点名要改范围外的某一条时，运行不该假装那条不存在。被挡掉的数量要报出来，
否则一份安静缩短过的清单读起来就是「这个项目只有这几条」，模型于是理直气壮地告诉
作者他的人物不存在。

已接线的入口：AI 面板的全部任务（`aiTaskStore` 把 scope 折进 `extras` 一次，而不是
在三个 `assembleContext` 调用点各写一遍）、对话（种子 + 逐轮注入 + ToolContext）、
一致性检查（**必须**同一个围栏——范围外的条目在那里会被当成正文矛盾报出来）、扮演
（种子 + 逐轮；绑定条目豁免；记忆区的检索**不**受影响，它本来就是另一份索引）、
子代理（继承父运行的范围，否则「派给子代理」就成了绕过围栏的方法）、知识库的两个
AI 模态。

**新建条目会归进当前范围**（作者手建与 agent 建的都是）：范围生效时新建的条目若落成
未归集，它会立刻从作者刚刚建它的那面墙上消失。

## 7. UI（设计稿 03 屏 24–31）

设计师用一句话定了整套语汇：**分类用颜色，集合用装订；取材范围不是筛选，它把围栏外的
卡片翻面**。四个开放问题的答案都落进了实现：

- **多归属的条目在墙上出现一次**（屏 24 Q1）。墙从不按集合分区，归属画在卡片左侧
  22px 的装订边上，两个集合就是两道竖排标。代价是「属于哪一摊」要读边不读位置，换来
  的是位置不骗人；集合计数按**归属**计，于是各集合之和大于条目总数，装订栏底那行 mono
  算式（`7+5+4+3 = 19 > 18`）就是为这件事写的。
- **围栏与筛选靠形制分开**（屏 25 Q2）。筛选让卡片消失，围栏让卡片**翻面**——围栏外的
  条目留在原位，只剩名字和所属集合，没有头像、没有特征。围栏还带三样筛选**永远不会
  产生**的东西：顶部 `3px double` 的骑缝带、右页边的竖排标注、装订栏里的围栏说明卡。
  这条分界写在 CSS 注释里（`collections.module.css`），因为它是一条不能被后来的
  「顺手复用一下这个样式」抹掉的规则。
- **批量勾选落在装订边**（屏 28 Q3）。卡身已经是「打开条目」、方头像已经是「换图」，
  装订边是这一轮新增的第三条竖带，本来就只讲归属。三种进入方式：点勾选框、⇧ 点卡身
  连选、格纸空白处拖拽框选。批量归集**只加不减**，减法是单独的「移出集合」。
- **集合超过 8 个就折起**（屏 26 Q4）。切换器顶部出现 mono 过滤框，列表滚动，超出的
  折进「其余 N 个」。墙面不受影响——它从不按集合分区，所以「墙面分区怎么退化」这个
  问题被第一条一并消掉了。

组件在 `src/components/lore/collections/`：`ScopePicker`（骑缝带 + 头部按钮 + 切换器，
墙与 AI 面板共用同一份状态）、`CollectionRail`（装订栏）、`BindingEdge`（卡片装订边）、
`CollectionAssignMenu`（single / add / remove 三种用法一份清单）、`CollectionsManageModal`。

两处**没有**照搬设计稿：

- **不加 `shortName` 字段**（稿子把它标成「可选，你定」）。装订边的竖排短名改为
  `bindingLabel()`：剥掉书名号再取前四字，全名挂在 `title` 上。给声明格式加一层结构，
  就会让 profile.json 从一个字符串数组变成一串对象，而作者是要手改这个文件的——纯显示
  层的截断不值这个价。真需要时再加是**加宽**，不是迁移。
- **详情页不做集合面包屑**（稿子自己也否了）：多归属没有单一路径，两条归属串成一行
  面包屑会读成一条层级。集合落在主条目栏的元信息区。

## 8. Agent 侧：让 agent 帮你整理

条目一多，「帮我把资料按各自的作品归类」就是最自然的一句话。它需要 agent 能建集合、
能归档——而 `writeTools` 顶上原本写着「没有任何工具能建/改名/删分类」。

那条规矩没被推翻，是**被限定了适用范围**：它回答的是「agent 能不能自己发明组织结构」
（不能），而不是「作者委派的批量整理该怎么做」。让后者成立的机制本来就在——
`propose_lore_plan` → 方案卡 → 作者逐行批准。所以 agent 只能**提议**建集合，批准的是人。

### 8.1 方案步骤的第二根轴

`LorePlanStep` 加了 `target`（`entity` 缺省 / `collection` / `category`）和 `members`。
原因是**粒度**：「把 200 条按作品归类」写成 200 条条目步骤，卡片是一面墙，作者的批准
就退化成盖章——那比没有门更糟，因为它看起来像有门。一条 step = 一个集合、条目列在
行内，作者读 5 行看完一次重整，而这 5 行正是他真正在做的那个决定。

四个动作**没有扩充**（没有 file / rename 动词）：归档改的是集合的成员，所以是对**集合**
的 `update`；改名是身份的迁移，所以是 `move`。schema 的 enum 每轮常驻，能不涨就不涨。

`members` 同时是授权边界：`file_lore_entries` 只能动步骤里列到的条目——批准「归入
12 条」不等于批准归入第 13 条。

### 8.2 三个工具，全部 deferred

| 工具 | 作用 |
|---|---|
| `manage_collection` | `op: create / rename / delete` |
| `file_lore_entries` | `entities[]` + `add[]` / `remove[]`，一次一批 |
| `create_lore_category` | 只有 create |

**分类只给 create** 是唯一保留的不对称，不是嘴硬：分类是磁盘上的文件夹，新建只是建
目录，而改名/删除会让每个成员条目的文件夹搬家，并让 `[[lore:分类/id]]` 路径引用和特征
置顶失效。集合三个都给，因为它只是 frontmatter 上的一个字段，可逆且便宜。

`add`/`remove` 两个数组而不是一个 `set`：set 语义会在只想补一个标签时静静抹掉别的归属。

### 8.3 按方案形状装载

三个工具挂 `group: "lore_organize"`，方案批准前不下发。而且装载是**按形状**分的：
批准一份「改写条目正文」的方案不会带出集合工具，反过来也一样
（`runtime.ts`，测试在 `agentRuntimeToolGroups.test.ts`）。

这条路是 [`agent-tool-context-lld.md`](../agent/agent-tool-context-lld.md) §6 认可的那一条
——**由运行状态自动装载，不需要模型自己开口要工具**。让模型主动索取（`load_tools`）
那条路在那份文档里被实测否掉了：gemma4:12b 在工具就摆在眼前时，3 次里 0 次走通两步
流程，再加一层间接只会让一类任务从「做得差」变成「做不了」。

### 8.4 成本

唯一的常驻开销是 `propose_lore_plan` 的 schema 加了 `target` + `members`：**+190 token**，
棘轮从 9,150 抬到 9,300（账记在 `agentToolBudget.test.ts` 的注释里）。三个工具本身是
deferred，批准之前一分不花。

`list_lore_entities` 也补上了归属（集合目录 + 每条后面的 `[…]`）——那是**结果文本**、
不是 schema，只在模型真的调用时计费。没有它，模型要归得一致就得把条目一条条读过去。

## 9. 已知边界

- **取材范围指向一个不存在的集合**：重命名和删除会把范围一起带走或清掉，但手改
  profile.json / frontmatter 造出这个状态是可能的。此时 AI 一条条目也看不见，唯一
  的止损是界面上必须**始终显示当前生效的范围**（任务书里把这一屏标为最重要的一屏，
  就是为了这个）。刻意没有做「自动重置」：一个声明过但还空着的集合，作为范围时本来
  就该是「什么都看不见」。
- **未归集不能当范围。** 那是浏览时的筛选，不是取材意图——没有人会想让 AI 只用那些
  还没分好类的条目写作。
- `refileCollection` 逐条改写，单条失败只记日志不中断整批。它是可重跑的（跑第二遍
  只会跳过已经改好的），但一次中途失败会留下一半改完的状态。

## 1. 问题：匹配面比作者以为的窄得多

今天一条知识库条目能被自动召唤，靠的只有三样东西：

| 匹配面 | 代码 |
|---|---|
| `entity.name` | `lib/context/loreSelect.ts:403` |
| `entity.aliases[]` | 同上 |
| `facet.keys[]` | `lib/context/loreSelect.ts:561` |

判定方式是 `lower.includes(term.toLowerCase())` —— 小写化子串包含，没有分词、没有词干、没有相关度。

**条目正文从来不是匹配面。** 一条道具条目的正文里写着「渚变身时召唤的法杖」，这句话不参与任何召唤判定。

### 1.1 靶子（matchTarget）三个入口拼法不同

| 入口 | matchTarget | 代码 |
|---|---|---|
| AiPanel 任务 | `选中文本` + `锚点前 500 字` | `lib/context/rag.ts:387-390` |
| 对话首轮 | 同上 + **作者问题全文** | `stores/agentStore.ts:1165` |
| 对话后续轮 | `问题` + `文档尾部 500 字` | `stores/agentStore.ts:1277` |
| 角色扮演 | 作者这一句（+ 角色条目恒为 pin） | `lib/roleplay/run.ts:420-421` |

`TaskExtras.extraMatchText` 全仓**只有 `agentStore` 传**。AiPanel 的自定义指令、大纲、附加要求一个字都不进靶子。

### 1.2 走查：「写渚的变身场景」

知识库：

```
characters/nagisa/
  index.md            name: 渚  aliases: [Nagisa, 小渚]
  magical-outfit.md   facet: 魔法少女战斗服  keys: [变身, 战斗服]  group: outfit
  daily-outfit.md     facet: 日常校服        keys: [校服, 日常]    group: outfit
items/magic-staff/
  index.md            name: 星辉之杖  aliases: [魔法杖]
                      正文：渚变身完成时从掌心召唤的法杖……
```

| 入口 | 渚 | 战斗服 | 星辉之杖 |
|---|---|---|---|
| 对话「写渚的变身场景」 | ✅ 由「渚」命中 | ✅ 由「变身」命中 | ❌ **字面没出现** |
| AiPanel 续写 + 同一句自定义指令 | ❌ **指令不进靶子** | ❌ 实体没中，无从判 | ❌ |

四个失败模式，性质各不相同：

| # | 失败模式 | 性质 |
|---|---|---|
| F1 | 作者意图不进靶子 | **缺陷**，一行的事 |
| F2 | 「杖还没出场所以取不到」 | **结构性**：子串只能取到已写下的字，取不到将要写的字 |
| F3 | 20 条上限按 `Object.values` 遍历顺序截断 | 排序缺失 |
| F4 | 短别名（「渚」「杖」）到处误伤 | 精度，CJK 下无干净解 |

F1 是 bug，F3 是排序，F2 才是真问题 —— 而 F2 的解药**不是相似度**（见 §6.1）。

## 2. 三条不变量

贯穿三片 PR，任何一条被打破就退回重做：

1. **子串通道是高精度通道，新增的一切都排在它后面。**
   `selected` 数组的顺序就是预算优先级（`loreSelect.ts:413`）。顺序恒为 `pin → 子串命中 → 引用带入 → 扩展词命中`。新机制永远不许把已经工作正常的命中挤出预算。

2. **每一条进上下文的东西，作者都要能问出"为什么"，并且答案要是他能动手改的。**
   `LoreActivationReport` 是这个系统的主反馈回路（`loreSelect.ts:17-19`）。「由「变身」命中」作者能去改 keys；「相似度 0.72」他什么也做不了。**新来源必须有自己的 `reason`，并在报告里与子串命中分列** —— 同「常驻层和本轮检索必须是两个字段」那条规矩。

3. **没有静默截断。**
   凡是被上限砍掉的、被围栏挡掉的、被超时跳过的，报告里都要有数。一个安静变短的列表读起来是「这个项目就这么多条目」。

## 3. PR-A · 作者意图进入匹配靶（F1 + F3）

### 3.1 传什么

`aiTaskStore` 在两个 `assembleContext` 调用点（`aiTaskStore.ts:525-526`、`:705`）补上：

```ts
extraMatchText: [
  customInstruction,              // 作者在指令框打的字
  extras?.outline,                // 大纲 / 写作方向
  extras?.requirement,            // 附加要求
  extras?.additionalKnowledge,    // 附加背景
].filter(Boolean).join("\n"),
```

### 3.2 **不**传什么 —— 这条比传什么重要

不要传 `instruction`。它是拼好的成品（`aiTaskStore.ts:314-333`），里面有两样东西必须挡在靶子外：

- **内置模板**（`i18n.t(task.instructionKey)`）—— 应用自己的字。它命中的任何条目都是噪声，而且是**每次运行都稳定复现**的噪声。
- **工作流卡清单 + docx 格式清单**（`aiTaskStore.ts:324-332`，`tools: "full"` 的任务尾部挂着）。那两份清单里全是名词短语，跟条目名撞车只是时间问题，撞上之后表现为"某个条目莫名其妙每次都进"。

规则一句话：**只有作者亲手打的字才是意图。**

### 3.3 顺带修 F3 —— 必须和 3.1 同一片 PR

`loreSelect.ts:398-411` 现在是「边遍历边收，够 20 条就 `break outer`」。分类的遍历顺序（`Object.values(loreIndex)`）决定谁被砍。

PR-A 会显著加长靶子（一份大纲可能几千字，命中几十条），**不一起修就是把一个潜在缺陷变成必现缺陷**。

改法（纯函数，可单测）：先收全部命中，再排序，再截断。

```
排序键（降序）：
  1. 最长命中词的长度   ——「星辉之杖」比「渚」可信
  2. 命中词条数
  3. dirPath           —— 确定性 tie-break
```

被砍掉的记进 `LoreActivationReport.autoCapped: number`（不变量 3）。

### 3.4 靶子长度不设上限

考虑过给 `extraMatchText` 截断（取头部 2000 字）。不做：一份三千字的大纲提到的人物**就是这次要写的人物**，截掉后半段等于告诉作者「大纲写太长会漏设定」，这是没人能猜到的规则。3.3 的排序让长靶子的后果从「取到分类顺序最靠前的 20 条」变成「取到最相关的 20 条」，那才是正确的降级方式。

### 3.5 验收

- AiPanel 续写、自定义指令填「写渚的变身场景」、正文里没有「渚」字 → 渚 + 战斗服都进
- 同上但指令留空 → 行为与今天完全一致（回归）
- 一份提到 30 个人物的大纲 → 报告显示 20 条 + `autoCapped: 10`
- 单测：内置模板里的常见词（「续写」「润色」）不出现在任何 `matchedTerms` 里

## 4. PR-B · 引用图扩展（F2 的第一半）

作者在渚的正文里写 `[[lore:星辉之杖]]`，这是他**显式声明的关联**，比任何相似度都准。今天这个声明只用于渲染时点击跳转（`lib/lore/citations.ts`），取材侧一眼都没看。

### 4.1 采集：零额外 IO

`readEntity`（`lib/lore/entity.ts:110`）扫描时**已经**把 `index.md` 和每个 facet 文件的原文读进内存了（`:123` 和 `:182`）。在这两处各加一次纯函数调用即可：

```ts
// lib/lore/citations.ts —— 与解析同住，可单测，无 DOM
export function collectCiteTargets(markdown: string): string[]
```

`LoreEntity` 新增 `refs: string[]`，存**原始 target 字符串**，不在扫描时解析成实体。两个理由：扫描时索引还没建完；存名字对改名更健壮（`resolveCitation` 三级回退：名字 → 别名 → `category/id` 尾）。

与「Content is NOT kept in memory」（`entity.ts:176`）不冲突 —— `refs` 是几十字节的派生元数据，不是正文。

### 4.2 注入：降级层，一跳，排最后

在 `selectLore` 里，实体选定之后、L0 之前插一步：

```
对每个已选中实体 s（reason: pinned | auto）：
  对 s.entity.refs 里每个 target：
    e = resolveCitation(target, loreIndex)
    e 不存在 / 已在 selected / 在 excludeDirs / 在 coreDone → 跳过
    !inScope(e, scope) → 跳过并计数        ← 围栏对引用有效
    否则 → 以 reason: "ref"、refFrom: s.entity.name 追加到 selected 末尾
```

五条取舍，逐条写明理由：

**① 引用带入的条目只给 L0 摘要 + L0.5 配图行，不给 L1 正文，不激活任何 facet。**
这是"提醒模型这东西存在"，不是"把它讲一遍"。给正文的话，一个引用了五件道具的人物就把预算吃光了，而挤掉的正是直接命中的条目（违反不变量 1）。一行摘要 30 字 × 5 = 150 字，可接受；模型看完摘要要细节，`read_lore_entity` 就在手边 —— 工具通道存在的意义正是这个。

**② 只走一跳，不递归。**
杖引用「魔法结社」，结社引用「魔法体系」，体系引用「世界观」…… 两跳就能把整个知识库拉进来。一跳是「直接相关」，两跳是「什么都相关」。

**③ 围栏（取材范围）对引用有效。**
引用扩展是**自动发现**的一种，而围栏的唯一规则就是"只narrow自动发现"（`lore-collection-plan.md`）。反过来说：pin 能越栏，引用不能。

**④ 顺序恒在自动命中之后**（不变量 1）。

**⑤ 有上限，且报出来**：每个源实体最多带入 5 条，全局最多 10 条，超出记 drop（不变量 3）。

### 4.3 报告与 UI

- `LoreEntityReport.reason` 加 `"ref"`，新增 `refFrom: string`
- `AiPanel.tsx` 的 `LoreReportSection`（`:587`）今天只画 pin 图标 + 名字 + 别名 + 层 chips，**连 `matchedTerms` 都没画**。这一片要补：`ref` 来源显示为「← 渚 引用」
- 视觉语汇**留给设计**：`TurnTrace.tsx` 已经用「同一根线的四种终止方式」区分四种来源，第五种来源该长什么样不在这份文档里发明。3px 双线一次都不能用 —— 那已归集合所有

### 4.4 相邻问题，搭车修

`readLoreEntity`（`lib/agent/tools.ts:150`）是 `found.mdFiles` 全量遍历，**不看 `group`**。模型主动读渚，两套服装同时出现，混搭是可预期的。

在结果文本里打出组标注即可（一行改动，且是**结果文本**、不占每轮常驻的工具 schema 预算）：

```
=== magical-outfit.md === [group: outfit —— 与同组其它特征互斥，同一场景只应采用其一]
```

### 4.5 验收

- 渚的正文写了 `[[lore:星辉之杖]]`，对话「写渚的变身场景」 → 杖以 `reason: "ref"` 进，只有摘要一行
- 取材范围设为某个不含杖的集合 → 杖不进，报告里有计数
- 杖的正文也写了 `[[lore:魔法结社]]` → 结社**不**进（一跳）
- 预算调到刚好装下渚 → 杖被 drop，渚完整（不变量 1）

## 5. PR-C · 查询扩展（F2 的另一半）

引用图只能取到作者**已经连起来**的东西。作者没写 `[[lore:…]]`，或者关联本来就不该写进正文（"变身场景通常要召唤法杖"是叙事常识，不是设定），就还得靠别的。

### 5.1 做法：扩展词喂回现有的子串匹配器

发请求前，一次结构化调用把作者意图扩成词表：

```
「写渚的变身场景」  →  { terms: ["渚", "变身", "魔法少女战斗服", "星辉之杖"] }
```

然后把 `terms` 追加进 `matchTarget`，**走今天这套子串匹配**。

这是整个方案里最要紧的一步选择：报告仍然能说「由「星辉之杖」命中」，只是标一下这个词是扩展出来的。**新机制完整复用了既有的可解释链路**（不变量 2），而不是在旁边另起一套评分。

### 5.2 关键：给它候选名单，不让它自由联想

自由联想会产出「咏唱」「魔力回路」这类知识库里根本不存在的词 —— 命中不了任何东西，纯浪费一次调用。

所以输入里必须带一份**名单**，任务是"从这份名单里挑相关的"：

```
实体名 + 别名 + 每个 facet 的标题 + 每个 facet 的 keys
```

facet 那半截不能省 —— 名单里没有「变身」这个词，它就答不出「变身」。

名单由 `loreIndex` 现算，随扫描变化，天然不会过期。

### 5.3 怎么跑

- 一次 `runStructuredTask`（`lib/agent/structured.ts:82`），schema `{ terms: string[] }`
- **不能放进 `assembleContext`** —— 那是纯装配函数，塞一个网络调用进去会让它的全部单测变成集成测试。调用方（`aiTaskStore` / `agentStore`）在装配**之前**跑，结果并进 `extraMatchText`
- 模型绑定：`SUBAGENT_KINDS` 加 `"retrieval"`，**不进 `DELEGATE_KINDS`** —— 同 `imagegen` / `translate` 的先例（它不是对话，没有工具可循环，助手也不该能"调用"它）。作者在 设置 → 子代理 里给它绑一个本地小模型
- 默认**关**。没绑模型 = 这一级不存在
- 只在作者意图非空时跑（AiPanel 无自定义指令的续写不跑，省掉绝大多数轮次）
- **超时 3 秒，超时跳过**。它坐在首字延迟的关键路径上，绝不许把一次取材优化变成一次卡顿
- 任何失败静默降级到 PR-A 的行为，报告里记一笔

### 5.4 验收

- 「写渚的变身场景」，渚的正文**没有**任何 `[[lore:…]]` → 星辉之杖仍然进，报告标「扩展词「星辉之杖」命中」
- 拔掉子代理模型 → 行为与 PR-B 完全一致（回归）
- 把扩展模型指向一个不通的地址 → 3 秒后照常出结果，报告里有「扩展跳过」

## 6. 明确不做的事

### 6.1 向量 / embedding —— 推迟，不是否决

**这条路走过一次。** `lib/project.ts:132-145`：

> `lore_entities` is the remains of an earlier design where the knowledge base was indexed in SQLite (**hence `embedding_status`**) … Neither table has ever been read back by any shipped code path.

表建了、列留了、没接上、最后被 `DEAD_PROJECT_TABLES` 删掉。重启之前要先能回答"这次为什么会接上"。

**规模事实**：200 条 × 6 个单元（摘要 / 正文 / 每个 facet）≈ 1200 个向量，768 维 float32 = 3.6MB。暴力余弦 92 万次乘加，JS 里不到 1ms。**不需要 sqlite-vec、不需要 ANN、不需要任何"向量数据库"** —— 实现就是一个 BLOB 列加一个 `for` 循环。检索从来不是难的部分。

难的是这三样：

| 难点 | 具体 |
|---|---|
| 供应商依赖 | Anthropic 没有 embedding API。这个特性永远只能是可选通道 |
| 新鲜度 | `loreSelect.ts:29-32` 明写"每次调用重读磁盘，所以手改永不过期"。加缓存就是打破这条；唯一安全解是按内容 hash 作键、对不上就当没有向量 |
| **可解释性** | 不变量 2。余弦分数是作者无法动手改的东西，而取材报告的全部价值就在于可动手 |

**还有一条判断**：对 F2（「杖还没出场」），查询扩展比向量更可靠。模型懂「变身场景通常要召唤法杖」这种叙事常识；向量只知道两段文字长得像不像 —— 而"变身场景"和杖的正文像不像，取决于作者当初写没写"变身"那两个字，那正是我们想摆脱的依赖。

**重启条件**：PR-A/B/C 上线并用过一段真实创作之后，如果取材报告里仍然频繁出现「作者认为该进、三条通道都没取到」的条目，且这些条目的共同点是**正文相关但名字/引用/常识都不搭**，那就是向量真正的地盘，届时重开一份文档。

### 6.2 FTS5 / BM25

同样推迟。SQLite FTS5 在 CJK 下要自定义 tokenizer（unigram 勉强能用），而它解决的问题（正文进入匹配面）与 6.1 高度重合。两个都推迟，不要一次引入两套检索。

### 6.3 别名词边界（F4）

不做。CJK 没有词边界可用，任何启发式都会在别处出错。缓解手段有两条，都在 PR-A 里：排序时长词优先（3.3），以及别名编辑框加一句提示 —— 别名越短，误召唤越多。

### 6.4 facet keys 的自动生成

不做。keys 是作者调优的把手，自动生成会把一个可解释的字段变成一个"它自己会变"的字段。要减轻作者负担，正确的位置是 PR-C 的扩展词（运行时的，不落盘），而不是替作者改文件。

## 9. 实现出入

### 9.1 引用带入的条目**不能**用 L0 保底层 —— 本文被证伪的一条

§4.2 ① 说引用带入的条目「只给 L0 摘要 + L0.5 配图行」。写下来才发现这句话
自己打自己：**L0 是保底层，它明写着不受预算限制**（`loreSelect.ts` 的
「guaranteed even over budget: it's the floor, not a filler」）。把引用挂上去，
十条引用的摘要就会在预算之外挤掉一个直接命中条目的正文 —— 正是不变量 1 禁止的事。
一开始的实现真的这么写了，测试「预算不够时先牺牲引用」当场红了。

改成新的 **L3 层**：排在 facet 填充之后，逐行核预算，装不下就不装。

保底层存在的理由是「正文点了名的条目不该颗粒无收」；**没人点名的条目颗粒无收
是对的**，不是失败。这句话就是 L0 和 L3 的分界。

### 9.2 `LoreEntity.refs` 是可选字段

原计划是必填。加上去之后十来处手搭的测试 fixture 全红。按 `dict` 的先例改成
`refs?: string[]` —— `scanLore` 永远填，缺席读作「没有引用」，那对一个没被扫描过
的实体本来就是老实答案。

### 9.3 三片 PR 是**线性栈**，不是并行

§8 说「A 和 B 之间没有依赖，可并行」。错了：两片都往 `LoreActivationReport`
加字段（`autoCapped` / `refCapped` / `refOutOfScope`），并行就是一次必然的冲突。
实际按 文档 → A → B → C 线性叠着做。

### 9.4 `retrieval` 在设置页自成一组

§5.3 只说了「进 `SUBAGENT_KINDS`、不进 `DELEGATE_KINDS`」，没说它在界面上归哪。
现有三组是 对话委托 / 直接工具 / 收尾成文，而「直接工具」那句 hint 写的是
「助手通过工具直接调用」—— 没有任何模型调用它，是应用在组装请求之前调的。
于是加了第四组「取材扩展」，并且**排在最前**：四组的顺序就是流水线的顺序。

同理它**不出现在对话芯片里**（`SubAgentChips`）：轮到那排芯片渲染的时候，这一轮
的扩展早就跑完了，一个只对下一轮生效的开关不该混在「本轮开关」里。

### 9.5 `acceptExpansion` 的出参过滤是承重的，不是保险

§5.2 把名单说成输入侧的事。实现时把它做成了**双向**的：回来的词再按名单滤一遍。
理由在测试里写着 —— 一个模型自己造的词在 matchTarget 里什么也命中不了，
**却会混进注入报告的命中来源**，让作者去找一个他知识库里根本没有的条目。
「请只从名单里选」是提示，不是保证。

### 9.6 顺带落地的两件小事

- `read_lore_entity` 现在给同组特征打组标注（§4.4 的搭车项，已做）
- 自动匹配上限、引用上限、越栏的引用，三者都在面板上报数（不变量 3）

### 9.7 仍然没做

- **`matchedTerms` 在 AiPanel 上仍然只是 chip 的 `title` 提示**，没有独立展示。
  数据一直都在，缺的是一笔设计 —— 和 `reason: "ref"` 的视觉语汇是同一个问题，
  一起留给设计稿。
- **角色扮演侧没有接查询扩展。** `run.ts` 的 `matchText` 是作者说的那一句，接上去
  是对的，但扮演每轮都要过一次 3 秒超时的外部调用，值不值得要先看真机手感。

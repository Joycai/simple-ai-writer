## 0. 结论先说

**可行,而且比预期容易 —— 但工作量的重心不在服务端。**

服务端本身是一个平淡的 CRUD + 全文检索服务(P0/P1 合计约 1000~1500 行),
真正的成本在客户端:整个 app 里,「知识库条目」的**身份就是它在磁盘上的绝对路径**
(`LoreEntity.dirPath`,全库 132 处引用)。要接远程库,必须先把
「条目 = 磁盘目录」这个假设从**读写两条路径上**拆掉,换成一层可分派的仓储抽象。

好消息是这层拆解的**范围是可枚举的**(§3 给出了完整清单,约 20 个直接文件调用点),
而且注入、引用解析、导航三条最复杂的链路**都不需要改算法**,只需要换掉两个读函数。

坏消息是有一条容易被漏掉的安全退化:agent 的 L1 自动写工具靠「写前自动备份」当安全阀,
而这个备份在远程路径上会**静默失效**(§5.4)。这条不处理,远程知识库上线当天
就等于把 agent 的写保护关了。

需要用户先拍板的两个问题在 §8。

> **§9 起是两个更轻的方案。§13~§18 是最终推荐的那个**(命名知识库 + 整库定向同步);
> §9~§12 是通向它的中间形态,保留作为推导记录。先说退化方向::服务端只当**按条目的备份/同步引擎**(推送 / 下载,
> 不做合并,冲突只有改名或覆盖)。那个方案把上面最贵的三块整个删掉,
> 而且 `lib/lore/transfer.ts` 已经写好了 80%。**如果两个都想做,应该先做退化方案** ——
> 理由见 §12。

## 1. 现状:知识库到底是什么

| 维度 | 现状 |
|---|---|
| 真相来源 | `.ai-writer/lore/<category>/<entity>/` 目录树,**纯文件,无数据库副本** |
| 数据库 | 无。`project.db` 里曾有 `lore_entities`(带 `embedding_status`),已作为死表在 `project.ts` 的 `DEAD_PROJECT_TABLES` 里删除 |
| 条目 | 目录 = 一个条目;`index.md` 的 frontmatter 提供 `name`/`aliases`/`summary` |
| 特征(facet) | 同目录下带 `facet:` frontmatter 的普通 `.md`;`keys`/`group`/`priority`/`mode` 控制激活 |
| 图片 | 目录内的 `avatar.*` + `images.md` 描述的图库,渲染时读成 base64 data URL |
| 索引 | `scanLore(projectPath)` 全量扫盘 → `LoreIndex = {[category]: LoreEntity[]}`,存在 `loreStore.index` |
| 注入 | `selectLore()` 三层预算(summary / index.md 正文 / facet),**每次调用都重新读盘取正文**,以保证手改不被缓存成陈旧内容 |
| 检索 | 无索引、无向量。就是对 `name` + `aliases` 做**大小写无关子串包含**(`lower.includes(term)`,CJK 友好) |

这张表有两条直接决定可行性的结论:

1. **没有本地数据库要同步。** 不存在「SQLite 索引 ↔ 文件树」的一致性问题,
   远程化只需要接管「一棵目录树」,不需要接管两份状态。
2. **命中是纯文本子串匹配,不是语义检索。** 所以「搜索/命中」这件事
   **不需要服务端算力** —— 只要客户端手上有全量的 `name`/`aliases`/facet `keys`,
   匹配就能完全在本地跑,和现在一模一样。这个观察是 §4 缓存策略的地基。

## 2. 已经现成、可以直接复用的东西

接远程库这件事,这个代码库里已经躺着不少半成品:

- **`lib/http.ts`** —— 走 Tauri `reqwest` 的 fetch,天然绕开 webview CORS,
  已经在处理 Origin 覆写和本地地址判定。连自建服务端可以直接用,一行不用改。
- **`lib/keyStore.ts`** —— OS keyring(Keychain / Credential Manager / Secret Service),
  凭证的现成归宿。只需把 key 的命名空间从 `apikey:<providerId>` 扩到
  `kb:<sourceId>`,并复用它已经写好的 `KeyringError`「keyring 坏了 ≠ 没配置」的区分。
- **`lib/lore/transfer.ts`** —— 已有 `manifest.json` + `lore/<cat>/<id>/…` 的 zip bundle
  格式,以及 `overwrite`/`skip`/`keepBoth` 三种冲突策略。这就是现成的
  **首次导入 / 全量推送**载荷,服务端的存储布局照抄它即可。
- **`lib/agent/registry.ts` 的 lore 工具契约** —— `list_lore_entities` /
  `read_lore_entity` / `create_lore_entity` / `update_lore_file` /
  `update_lore_meta` / `append_lore_file` / `edit_lore_file` /
  `move_lore_entity` / `delete_lore_entity`。这已经是一套设计过的 CRUD 面,
  **服务端 REST API 几乎可以 1:1 照抄**,连语义都不用重新想。
- **`scanLore` 的孤儿分类逻辑** —— 「分类目录存在但没有能力包声明它」时,
  条目降级为可读可注入、但不可新建。远程库带来本地没启用的分类时,
  需要的正是这套语义,**不用新设计**。

## 3. 核心障碍:`dirPath` 是身份证

`LoreEntity.dirPath` 是绝对路径,而它同时被当作**主键**用:

- pin 以 `"<dirPath>"` 或 `"<dirPath>#<facetFile>"` 字符串持久化(`prefs` 的 `ai:pinnedLore:<项目路径>`)
- `loreStore.detailPath` / 导航历史(`navStore`)记录的是 dirPath
- `citations.ts` 的第三条兜底解析规则是 dirPath 的 `category/id` 尾巴
- agent 工具、备份、图库、注入,全部靠 `` `${dirPath}/${file}` `` 拼路径直接读写

**需要改造的直接文件调用点(已枚举完毕,共 ~20 处 + agent 侧 29 处引用):**

| 文件 | 性质 |
|---|---|
| `lib/lore/entity.ts` | 扫描/创建/改名/搬迁/facet 读写 —— 8 处,**主战场** |
| `lib/context/loreSelect.ts:371,381` | 注入取正文 —— **只有 2 处,且是整条注入链路的唯一读盘点** |
| `lib/lore/gallery.ts` | 图库 + avatar 二进制 —— 6 处 |
| `lib/agent/writeTools.ts` | agent 写工具 —— 引用 `dirPath` 29 处 |
| `components/lore/{LoreDetail,LoreSplitModal,LoreGenerator}.tsx`、`ai/LoreImageGenModal.tsx` | 组件直接调 fs —— 4 处 |

**建议的拆法:保留 `dirPath` 这个字段名,但把它降级为不透明句柄。**

```
本地: /Users/x/proj/.ai-writer/lore/characters/alice      (原样,零迁移)
远程: kb://<sourceId>/characters/alice
```

新增 `lib/lore/repo.ts` 作为唯一分派层,把上面所有调用点收口成 6~8 个函数
(`readEntryFile` / `writeEntryFile` / `readEntryBinary` / `writeEntryBinary` /
`removeEntryFile` / `entryFileExists` / `createEntry` / `moveEntry`),
按 `dirPath` 前缀分派到本地 fs 或远程 HTTP。

**为什么不新开一根 `source` 字段而是复用 `dirPath`:** 因为 pin 字符串、导航历史、
citation 解析这三处**已经落盘的历史数据**都是路径形状的。换字段等于要写迁移;
换前缀不用 —— 老数据天然全是本地路径。这和 `lore-entry-type-plan.md` 里
「不新开一根 `type` 轴」是同一个判断。

### 3.1 意外之喜:「关闭远程库」这件事,现有代码已经天然安全

关掉远程源 = 索引里那批 `kb://` 条目消失。三个会踩到悬空路径的地方**都已经写对了**:

- `selectLore` 明确跳过 stale pin(包括 facet 指向的文件已不存在的情况),不会退化成隐形的整条目 pin
- `citations.ts` 解析不到就标 `data-missing`,不跳转
- `loreStore.detailPath` 注释写明「解析不到就渲染网格」

也就是说 **§0 需求里的「可以屏蔽远程知识库」几乎是免费的** ——
只要开关只影响「合并进 index 与否」,不去清理 pin(清理才是 bug:
远程库重新连上时 pin 应该复活)。

## 4. 注入路径:唯一的性能陷阱,以及它的解法

`selectLore` 的设计前提是**读盘几乎免费**:每次调用都重新读实体正文和每个候选
facet 的正文(为了不把作者的手改缓存成陈旧内容)。一次续写命中 5 个实体 × 3 个 facet
= 20 次文件读 —— 本地无所谓,**远程就是 20 次 HTTP 往返,一次续写卡两秒**。

这是整个方案里最容易做错的地方。但因为 §1 的第二条结论(匹配是纯本地子串比较),
有一个干净的解法:

> **把「匹配」留在本地,只把「取正文」搬到远程,并且批量取。**

- 连接时拉一次**全量元数据**:每个条目的 `name` / `aliases` / `summary` /
  `category` / facet 的 `title`/`slot`/`keys`/`group`/`priority`/`mode`/`charCount`。
  这正好是 `LoreEntity` 减去正文 —— 几千条目也就几十 KB,一次拉完常驻内存。
- `selectLore` 的三层预算算法**一行不用改**:它只读 `entity.name`/`aliases`/
  `facet.keys` 做匹配,读正文只发生在最后两个函数里。
- 那两个函数换成走 `repo`,并加一个**批量端点** `POST /entries:fetch`
  (一次请求取回本轮选中的全部正文)+ ETag 本地缓存。20 次往返变 1 次。

元数据的新鲜度用一个 `GET /index?since=<version>` 的增量拉取维持,
比每次注入都回源便宜几个数量级。

## 5. 风险清单(按严重性排序)

### 5.1 同步语义 —— 建议 v1 直接回避

facet 是文件、元数据在 frontmatter 里,冲突不是行级 diff 能解决的
(两个人同时改 `aliases`,merge 出来是坏 YAML)。

**建议:v1 不做双向同步。远程为唯一权威,本地只做只读缓存,写入直接打 API,
用乐观锁(`If-Match: <version>`)防覆盖。** 双向同步留给 v2,而且到那时
更可能的答案是「服务端就用 git 裸仓库」(见 §6)而不是自己写 merge。

### 5.2 本地库 + 远程库合并成一个 `LoreIndex`

结构上很容易(`{[category]: LoreEntity[]}` 直接 concat),但有三个语义问题:

- **同名实体**:本地和远程都有「爱丽丝」→ auto-match 会两个都注入,
  citation 解析会随机命中一个。**建议:本地优先,远程重名的在墙上打冲突标记。**
- **分类 id 撞车**:远程的 `characters` 和本地的 `characters` 是不是同一个?
  **建议:是,直接合并** —— 分类只是个文件夹名,合并才符合作者直觉。
- 需要在 `LoreEntity` 上加 `origin: "local" | <sourceId>`,供 UI 打标、
  写工具决定走哪条路径、以及作者一眼看出这条是不是团队共享的。

### 5.3 离线

桌面写作应用,断网必须能继续写。→ **本地缓存必须是持久的**,
落在 `.ai-writer/remote-cache/<sourceId>/`,形状和本地 lore 树完全一样
(这样离线时 `repo` 的远程分支可以直接降级成读这棵树,零特判)。
离线期间的写入排队,重连后按乐观锁重放,冲突交给作者裁决。

### 5.4 ⚠️ agent 写保护会静默失效 —— 必须显式处理

这是代码阅读里最值得单独拎出来的一条。

`docs/feature/agent/unified-agent-plan.md` §3.2 的分级写策略是:L1(lore/memory)**不需要作者确认、
自动落盘**,安全阀是 `lib/agent/backup.ts` 的「写前自动快照到 `.ai-writer/backups/`」。
而 `backupFile()` 的第一行是:

```ts
if (!(await fileExists(absPath))) return null;   // 不存在 = 新建文件,无需备份
```

远程条目的 `dirPath` 在本地磁盘上**不存在**,于是 `fileExists` 返回 false,
`backupFile` 返回 `null` —— **不报错、不阻断,写照常进行**。
结果:agent 对远程知识库的所有自动写入,都没有任何可回滚的快照。
而 lore 写工具的注释明确要求「备份失败必须当作写入失败,绝不能照写」。

**必须二选一(或都做):**
- 服务端为每次写入保存版本历史(git 后端天然满足);
- `repo` 的远程写分支在提交前**先把旧内容拉下来写进本地 `backups/`**,拉不到就拒绝写。

顺带:`propose_lore_plan` 的计划审批闸门是纯客户端逻辑,远程化不影响它 —— 这条是安全的。

### 5.5 安全边界

`src-tauri/src/scope.rs` 的 `FsScope` 只约束本地路径。`kb://` 路径完全绕开它,
需要在 `repo` 的远程分支自建校验:`sourceId` 必须在已注册白名单里,
`category`/`entityId`/文件名各段用现成的 `CATEGORY_ID_RE` 和
`checkEntityFilename`/`checkFacetFilename` 校验,防止服务端返回
`../../` 这类段被拼进本地缓存路径造成穿越写。

### 5.6 图片

avatar / 图库走二进制 + base64 data URL。远程需要独立的 blob 端点 + 强缓存
(按内容哈希做 URL,永久缓存),否则每次打开知识库墙都会重新拉一遍全部头像。
这条不难,但别忘了排进 P2。

## 6. 服务端形态建议

| 决策 | 建议 | 理由 |
|---|---|---|
| 存储 | **git 裸仓库**,或 SQLite(元数据/FTS)+ 文件树(正文) | 内容本来就是 markdown。git 白送版本历史、回滚、冲突检测和 §5.4 要的写前快照。自己写这些不划算 |
| API | REST,约 8 个端点 | 见下 |
| 检索 | v1:SQLite FTS5 + name/alias 精确匹配即可 | 客户端的命中是子串匹配,不需要语义检索。向量检索是 v2,且 `lore-granularity-research.md` 已把「向量兜底」列为未实现方向 |
| 认证 | Bearer token,存 OS keyring | 复用 `keyStore` |
| 并发 | 每条目版本号 + `If-Match` 乐观锁 | 比行锁简单,对写入稀疏的知识库够用 |

端点(直接照 agent 工具契约来):

```
GET    /v1/index?since=<version>     元数据全量/增量(§4 的地基)
POST   /v1/entries:fetch             批量取正文(注入路径唯一的热点)
GET    /v1/entries/{cat}/{id}        单条目全文 + facet 列表
POST   /v1/entries                   新建
PATCH  /v1/entries/{cat}/{id}        改元数据 / 单文件(If-Match)
DELETE /v1/entries/{cat}/{id}
POST   /v1/entries/{cat}/{id}/move   改名/换分类
GET    /v1/search?q=                 服务端检索(v1 可选)
GET    /v1/blobs/{hash}              图片
```

## 7. 分期建议

**P0 —— 远程只读(拿到 ~90% 的价值,几乎不碰写路径)**
连接配置 + 凭证 + `repo` 抽象层 + 元数据拉取 + 批量取正文 + 合并进 `LoreIndex`
+ UI 打 origin 标 + 总开关。写路径全部对远程条目禁用(工具直接返回「该条目只读」)。
客户端约 800~1200 行,服务端约 600 行。

**P1 —— 远程写**
乐观锁 + §5.4 的备份补救 + agent 工具放开 + 手工编辑放开 + 冲突提示 UI。
客户端约 500~800 行,服务端约 400 行。

**P2 —— 打磨**
持久离线缓存与写入队列、图片 blob、服务端检索、多人协作(锁或 CRDT)。

## 8. 需要你先拍板的两件事

这两个答案会实质改变 P0 的设计,建议动手前定下来:

1. **场景是「一个人多设备」还是「一个团队共享」?**
   前者可以放心用「远程为权威 + 乐观锁」,冲突基本不会发生;
   后者需要认真做条目锁 / 冲突 UI,P1 的成本会翻倍。
2. **远程库是**「唯一权威、本地只缓存」**,还是**「本地和远程都能独立编辑、事后合并」**?**
   本文的所有建议都基于前者。选后者的话,§5.1 说的 merge 问题会成为整个项目
   最大的一块,那时应该直接把服务端做成 git,让 git 去解决。

## 9. 结论:显著更可行,而且 80% 已经写好了

这不是「小一号的方案 A」,而是**另一件事** —— 它把方案 A 里最贵的三块整个删掉了。

| 方案 A 的问题 | 退化方案 |
|---|---|
| §3 `dirPath` 主键改造(最大一块,~20 个调用点 + 29 处引用) | **归零。** 远程条目从不进入 `LoreIndex`;下载落盘后它**就是**本地条目,`dirPath` 是真路径 |
| §4 注入路径的 HTTP 往返陷阱 | **归零。** `selectLore` 一行不碰 |
| §5.2 本地/远程双 index 合并、重名、分类撞车 | **归零。** 只有一个 index |
| §5.4 agent 写保护静默失效 | **归零。** agent 永远写本地文件,`backupFile` 正常工作 |
| §5.3 离线 | **归零。** 断网 = 不能同步,本地照常写 |
| §5.5 FsScope 绕过 | 大幅缩小:远程内容只经暂存目录落地,复用现有的两阶段暂存 + 路径校验 |
| §5.1 同步语义 | 按需求直接取消 —— 这正是「不做合并」的意思 |

### 9.1 `lib/lore/transfer.ts` 已经是这个方案了

现有的 lore bundle 导入导出**就是这件事**,只差两点:传输是 zip 文件 + 原生对话框而非 HTTP;粒度是整棵树而非条目。

而**粒度这件事几乎是免费的**:

- `walkLoreTree` 已经按 `{category, id, name}` 逐条枚举
- `applyLoreImport` 已经是**逐条循环 + 逐条冲突判定**
- `StagedEntity.conflicts` 已经是每条一个布尔

改成「勾选要推/要拉哪些条目」是 UI 工作,不是引擎工作。

更关键的是,**冲突策略 `overwrite | skip | keepBoth` 正好就是你说的「改名/覆盖」**,
而且 `displaceEntity` 已经把 overwrite 做对了:它不是 `removeDir`,而是把被替换的条目
**移进 `.ai-writer/backups/`**,并且在移入失败时会把作者的条目**搬回原位**
(否则 "overwrite" 会变成 "delete 了但没导入成功",两边都没有)。
这块连同它的注释一起,不要重写。

## 10. 真正要做的四件事

### 10.1 Rust:两个不带对话框的 zip 命令(~50 行)

现有 `zip_export_dialog` / `zip_import_dialog` 绑死了原生对话框(设计如此:webview 永远
不能自己指定目标路径)。但内部的 `zip_dir` / `unzip_into` 是纯函数,已经有前缀校验和
路径穿越防护,连测试都有(`unzip_ignores_entries_outside_the_prefix_and_traversal_names`)。
加两个受 `FsScope` 约束的 `zip_dir_to_path` / `unzip_from_path` 即可。

**为什么载荷必须是压缩包而不是 JSON:** 一个条目是**目录**,含 `avatar.*` 和图库二进制。
JSON 化意味着 base64 塞图片,得不偿失。

### 10.2 ⚠️ 条目身份 —— 退化方案唯一的新问题,而且必须先解决

**现在的条目没有稳定 id。** 目录名是 `name` 的 slug(`slugifyEntityId`),而:

- `saveEntityMetaAndBody` 换分类时会 `uniqueEntityId` + `renamePath` → **目录名变了**
- `moveLoreEntityTool` 改名同理
- 冲突判定是 `fileExists(<root>/<category>/<id>)` —— **纯路径比较**

后果有两个方向,都很难受:

- A 机器把「爱丽丝」改名成「爱丽丝·冯」再推 → 服务端认成**新条目** →
  B 机器下载后得到**两条**,而不是一次更新;
- 两个毫不相干的项目各有一个「张三」→ slug 相同 → 被判成冲突,其实是两个东西。

**解法很便宜:** `index.md` frontmatter 加一个 `uid`(创建时生成,改名/换分类都不变),
服务端按 uid 索引,冲突判定改成 uid 优先、路径兜底。

**但有个坑:frontmatter 不透传未知字段。** `serializeEntityFrontmatter` 是从
`EntityMeta` 的四个字段(name/aliases/category/summary)**重建整块**的 —— 只加 uid
而不改 `EntityMeta`,作者在 UI 里改一次 summary 就把 uid 弄丢了。需要改的写入口正好三个:

| 入口 | 要做什么 |
|---|---|
| `EntityMeta` + `serializeEntityFrontmatter` | 加字段并写出;缺失时保持缺失(老条目在首次同步时补) |
| `createEntity` / `createEntityWithContent` | 生成 uid |
| `updateLoreFileTool` | 模型重发整个 frontmatter,**会丢 uid** —— 校验时强制回填原值(比要求模型带回来可靠) |

`update_lore_meta` / `append_lore_file` / `edit_lore_file` **安全**:它们用
`splitFrontmatter` 按原始字节保留头部,写不到 frontmatter 里去。这正是那三个工具
拆出来的理由,现在顺带也保护了 uid。

### 10.3 服务端:一个哑存储(~300 行)

比方案 A 简单一个量级 —— **不需要理解 markdown、不需要全文检索、不需要合并**:

```
PUT    /v1/entries/{uid}    上传条目压缩包 + 元数据(name/category/updatedAt/来源设备)
GET    /v1/entries          列表(uid/name/category/updatedAt/size),供下载端勾选
GET    /v1/entries/{uid}    下载压缩包
DELETE /v1/entries/{uid}
```

服务端对 lore 的内部结构**一无所知**,只是按 uid 存 blob + 一点元数据。
这意味着它对 facet / slot / 图片格式的后续演进天然免疫 —— 客户端怎么改,
服务端不用跟。认证复用 `keyStore` 的 OS keyring。

### 10.4 UI:两个面板

推送(列出本地条目 → 勾选 → 显示哪些远端已有)+ 拉取(列出远端 → 勾选 → 三选一冲突策略)。
直接照现有 bundle 导入的两阶段 UI 做。

## 11. 三个会咬人的细节

**a. 「不做合并」要求作者看得见自己在覆盖什么。**
现在 `StagedEntity.conflicts` 只是个 bool。文件导入时这够用(作者刚选了那个 zip,
心里有数);**同步场景下不够** —— 作者需要知道「本地这条比远端新还是旧」。
至少要展示两边的 `updatedAt` 和 summary,否则 overwrite 就是闭眼赌。
这是整个退化方案里**最值得投入的一处 UI**,因为它是「不做合并」这个决定的唯一安全网。

**b. keepBoth 生出 `alice-2` 时,必须重新生成 uid。**
否则本地会有两个条目共享同一个 uid,下次同步互相打架。一行代码,漏了就是反复重复导入。

**c. 条目不是自包含的。**
facet 正文里可能有 `[[lore:另一个条目]]`。单条目下载后引用可能解析不到 →
渲染成 `data-missing`(降级路径已经写对,不会崩)。建议在下载前用现成的
`resolveCitation` 扫一遍,提示「这 3 条引用了你还没有的条目」。锦上添花,不是阻塞项。

# 推荐方案:命名知识库 + 整库定向同步

> 需求最终形态:服务器托管**若干个有名字的知识库**。app 连上服务器后,
> 选一个已有的库或新建一个,然后把本地知识库**整体推上去**或**整体拉下来**
> (单向覆盖,不做合并)。条目带 hash 做一致性判断。

## 13. 评价:这个形态是对的,而且比 §9 更好

三个理由:

**a. 「命名知识库 = 仓库」把身份问题从条目层抬到了库层。**
在整库定向覆盖的语义下,条目的身份**就是它的相对路径** `<category>/<id>` ——
不需要 uid。这意味着 §10.2 那条「必须先给条目加 uid,而且要小心 frontmatter
不透传未知字段」的前置工作**在这个方案里不成立**。

> **修正上一轮的建议:** §12 结尾说「即使要做方案 A 也该先做退化方案,因为 uid 是
> 共同的前置」。在你这个语义下这条**要收回** —— 整库镜像不需要 uid,而它是唯一
> 需要改动存量落盘格式的部分。uid 降级成 v2 的事:只有将来想做**选择性同步**
> 或**双向同步**时才需要。也就是说这个方案比 §9 还少一块地基工作。

**b. 单向覆盖没有 merge,语义能对作者说清楚。** 作者能预测结果,这在数据安全类
功能里比什么都重要。

**c. hash 让整库同步从「每次全量传」变成增量** —— 更重要的是变成**可预览**的。见 §14.2。

## 14. 但有三件事必须钉死,否则会出事

### 14.1 「override」是镜像还是叠加?建议镜像

两种解释,结果完全不同:

- **镜像** —— 目标端 = 源端的完整副本,**目标端多出来的条目要删**
- **叠加** —— 只覆盖同路径的,目标端多出来的留着

叠加听起来更安全,但它是**伪安全**:两台机器来回同步几次后,没人说得清哪条是活的;
更要命的是**删除永远同步不过去**(A 机器删了一条推上去,B 机器拉下来它还在,
下次 B 推上去它又回来了)。

**建议镜像** —— 语义干净、可判定。代价是必须配合下面两条(预览 + 快照),
这两条本来也该有。

### 14.2 ⚠️ hash 的两个用途,重要的那个不是性能

- **传输优化**(显而易见的那个):只传 hash 变了的条目
- **安全护栏**(真正重要的那个):在覆盖前告诉作者
  「你要推的这个远端库,有 3 条在你上次同步之后被别的机器改过」

要做到后者,客户端必须记住**上次同步时的 hash 清单**,而不只是比对当前两边的 hash。
三方对比:

| 本地 vs 上次快照 | 远端 vs 上次快照 | 结论 |
|---|---|---|
| 变了 | 没变 | 安全推送 |
| 没变 | 变了 | 安全拉取 |
| 都没变 | | 无事可做(hash 相同,连传都省了) |
| **变了** | **变了** | **⚠️ 红色警告 —— 覆盖必然丢东西** |

最后一行正是「不做合并」时**唯一需要作者人工介入**的场景。有了它,
「整库覆盖」就从一个黑盒变成一张可预览的 diff 表
(新增 N / 修改 M / 删除 K / ⚠️ 冲突 J),作者点确认再执行。

**这是我对这个方案的主要增强建议。** 加上它,单向覆盖是安全的;
不加,迟早会有一次闷头误覆盖 —— 而且发生时作者不会当场知道。

上次同步的快照存 `.ai-writer/sync.json`,和 `profile.json` 同级 ——
`lib/profile/store.ts` 就是项目级 JSON 配置的现成先例(含「文件缺失/损坏都降级
成默认值,绝不阻塞项目打开」的写法,照抄即可)。

### 14.3 覆盖前必须自动留一份本地快照 —— 这是命门

知识库是作者几十上百小时的积累,一次误拉取就归零。

好消息:**现成的两块拼起来就够了** —— `transfer.ts` 的整库 zip 导出,
加上 `displaceEntity` 已经确立的「覆盖 = 移进 `.ai-writer/backups/` 而不是 unlink」
模式。拉取覆盖前自动导一份到 `backups/`,大约 20 行。

但**没有它这个功能不该上线**。这不是打磨项。

## 15. hash 怎么算(有坑)

条目是**目录**(`index.md` + facet 们 + `images.md` + 二进制图片),
所以条目 hash 必须是目录内容的确定性组合:

- 按文件名排序后,把 `hash(相对文件名 + 文件内容字节)` 串起来再 hash。
  **`fs_read_dir` 已经 `sort_by(name)` 了**,确定性这一半是免费的。
- **绝不能掺 mtime** —— 跨机器、跨 zip 解压、跨备份恢复全都会变,
  那样每次同步都会显示「所有条目都改了」。必须是纯内容 hash。
- **算在 Rust 侧**(~60 行):不用把二进制图片读进 webview,而且目录遍历本来就在那儿。
- 小坑:大小写不敏感的文件系统(macOS / Windows)按**创建时的大小写**报文件名,
  所以 `Outfit.md` 与 `outfit.md` 会算出不同 hash。同一个人的多台机器上极少遇到,
  但如果将来做团队共享会浮出来 —— 值得在实现时留一句注释。

## 16. 服务端(比 §10.3 还简单)

> **已实现:[`server/`](../../../server/README.md)** —— Rust + axum,单个静态二进制。
> 端点、鉴权、前置条件与磁盘布局见该目录的 README;以下是当初的设计草案,
> 实现与它一致,并在几处收紧了(见本节末尾)。

```
GET    /v1/kbs                             列出知识库
POST   /v1/kbs                             新建(名字)
GET    /v1/kbs/{kb}/manifest               ← 协议核心:每条目 {path, hash, size, updatedAt}
GET    /v1/kbs/{kb}/entries/{cat}/{id}     下载条目压缩包
PUT    /v1/kbs/{kb}/entries/{cat}/{id}     上传(带 hash)
DELETE /v1/kbs/{kb}/entries/{cat}/{id}     镜像语义下的删除
```

`manifest` 一次拿到全貌,**diff 完全在客户端算**,服务端依旧对 lore 的内部结构
一无所知 —— 它只存 blob 和一张清单。

实现时相对这份草案收紧的四处:

1. **每个写操作都带前置条件**(`If-Match: "<hash>"` 替换/删除,`If-None-Match: *`
   创建)。客户端从取到 manifest 到真正写入之间可能过去几分钟 —— 没有它,
   §14.2 那道安全网会在下一层被静默绕过。412 会带上当前实际的 hash,
   客户端不用多一次往返就能重新规划。
2. **hash 写进文件名**(`<id>.<hash>.zip`),提交就是一次 `rename`,
   载荷和描述它的 hash 不可能对不上。sidecar 方案需要两次 rename,
   中间的窗口正好是客户端**检测不到**的那种失败。
3. **manifest 靠遍历现算,没有索引文件。** 索引是真相的第二份副本,
   它引入的分歧客户端同样看不见。
4. **没配 token 就拒绝启动**,监听地址默认回环。

`manifest` 另外返回一个 `digest`(所有 `path`+`hash` 排序后的 sha256),
一个值就能回答「整个库有没有变」。

## 17. 几个不大但容易搞反的点

- **配置存哪要分开:** 「这个项目绑定了哪个远端库」是**项目属性**,跟着项目走 →
  `.ai-writer/sync.json`(照 `profile.json` 的模式)。「服务器地址 + token」是
  **安装属性**,多个项目共用 → app 级 + OS keyring(照 `keyStore` 的模式)。
  搞反的话,换台机器打开同一个项目会连不上,或者每个项目都要重新填一次 token。
- **允许多个项目绑同一个库** —— 没问题,但同步是**项目级操作**,
  入口该在知识库墙 / 项目设置,不是全局设置页。
- **能力包错配是免费的:** 远端条目属于本地没启用的分类时,`scanLore` 的孤儿分类
  逻辑已经处理好(可读、可注入、不可新建),`applyLoreImport` 也已经在
  `hiddenCategories` 里报告这件事。零新工作,UI 把提示带上即可。
- **`.ai-writer/lore-import-tmp` 的两阶段暂存要保留** —— 拉取时先解到暂存目录、
  校验完整再搬进真实树。现有 `stageLoreImport` / `applyLoreImport` 的两阶段结构
  正是为此,别为了「同步更直接」把它拉直。

## 19. 后续:整库镜像之外的「逐条指定」

§13–§18 落地之后作者提出的第一个真实需求:同步不该只有「整库覆盖」一档。
本地有而服务器没有的条目,不一定是「忘了推上去」,也可能是**只想留在这台机器上的草稿**;
拉取时把它删掉是镜像语义的正确结果,却不是作者想要的结果。

### 19.1 一个开关就够,不需要第二套语义

推、拉、三种差异,听起来是六种新行为,其实只是**一个 per-step 开关**的六个侧面:

| 方向 | 差异 | 镜像动作 | 关掉这一步 = |
|---|---|---|---|
| 拉取 | 只有本地有 | `delete` | **保留**本地条目 |
| 拉取 | 两边都有 | `overwrite` | 跳过,本地这条不动 |
| 拉取 | 只有远端有 | `create` | 不下载这一条 |
| 推送 | 只有本地有 | `create` | 不上传这一条 |
| 推送 | 两边都有 | `overwrite` | 跳过,远端这条不动 |
| 推送 | 只有远端有 | `delete` | **忽略**远端条目 |

所以模型层只加了一个字段:`SyncStep.decision: "apply" | "skip"`(`lib/sync/model.ts`)。
计划仍然按镜像语义生成——**计划描述的是「镜像会做什么」,不是「一定会发生什么」**——
作者在预览里逐条(或按当前筛选批量)关掉不想要的步骤,`actionableSteps()` 只返回
还开着的那些。执行器、服务端、hash 协议一行都没改:被跳过的步骤根本不会到达它们。

拒绝过的两个做法:

- **给方向加档位**(「拉取但不删除」当作第三个按钮)。它把一个可以逐条回答的问题
  压成了全局的一刀切,而且真实场景通常是「这 3 条留着,其余照镜像来」。
- **让 skip 影响 snapshot**。见 19.2——这会把安全栏杆本身拆掉。

### 19.2 ⚠️ 被跳过的条目**绝不能**写进 snapshot

`SyncBinding.snapshot` 的含义是「上次同步结束时两侧共同的状态」,它是 §14.2 三方比对
的第三条腿。跳过一条 = 两侧**依然不同**,所以 snapshot 必须继续这么记录。
一旦把跳过当成「已同步」写进去,下一次比对会认为这条自上次同步以来两侧都没动,
真正的冲突就会被判成「无变化」而静默丢失——这正是整个预览机制要防的那件事。

代价是**跳过不会被记住**:下次同步这条还会出现在列表里。这是诚实的代价,不是 bug。
真要「永久不同步某条」,那是另一个功能(sync.json 里一份显式排除清单),
它必须能在 UI 里看见、能取消,而不是伪装成一次跳过的副作用。

### 19.3 顺手修掉的一个静默 bug

`runSync` 原先只把**执行成功**的条目写进 snapshot,两侧本来就一致(`action: "none"`)
的条目从来没进去过。于是:两台机器各自已有同一条内容 → 首次同步显示「无变化」→
snapshot 里没有它 → 之后任何一侧改一次,`localChanged` 和 `remoteChanged` 会**同时**
为真(两边都 ≠ 缺席的快照值),于是作者推送自己的修改,却被报成「两边都改过」的冲突。

修法:`none` 步骤同样参与 snapshot 推进(两侧都没有则从 snapshot 移除)。
逐条跳过让这个 bug 更容易撞上(跳过会留下长期不一致的条目),所以一并修了。
回归测试在 `src/lib/__tests__/syncRun.test.ts`。

### 19.4 UI:预览表多一列,以及一条批量

- 每个可执行行末尾一个开关。按钮上写的是**它要做的那件事**:`delete` 步骤写「保留」,
  其余写「跳过」——作者选的不是抽象的「跳过一个步骤」,而是「这条留下」。
- 关掉的行变暗、动作标签划掉,但**警告文字保留**(那正是作者关掉它的理由),
  只去掉警示配色:它不再描述会发生的事。
- `summary` 改为只统计**还会执行**的步骤。这不只是数字问题:确认按钮的文案和
  「我已了解 N 条两边都改过」的勾选闸门都由它派生,把冲突全部跳过之后,
  闸门会自动消失——因为已经没有东西要丢了。
- 批量按钮作用于**当前筛选出的全部行**,包括 `ROW_CAP` 之外没渲染的那些。
  「保留只有我这里有的 200 条」应该是一次筛选加一次点击,而不是 200 次点击;
  只有逐行开关的话,看不见的那些恰好会被漏掉。

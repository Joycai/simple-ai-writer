# 互动式角色扮演创作 — 概要设计

> 状态：设计稿（未实现）。实现前先读 [02-design.md](02-design.md)。
> 术语：本文里「扮演 agent」= 演一个角色的对话体；「旁白 agent」= 看得见所有戏、和作者讨论故事的对话体；两者合称「戏搭子」。

## 1. 这是什么

作者在知识库里已经攒了一堆人物设定。今天这些设定只有一个用途——被 RAG 注入进写作任务。这个功能给它们第二个用途：**让作者能以第一人称走进去和它们说话**，把「设定」变成「能演」，用互动本身来找灵感、试语气、验人设。

一个扮演 agent = 一个绑定了主角条目的独立对话体，有自己的记忆，记忆不与任何其他 agent 共享。一个旁白 agent = 一个能读到所有扮演对话记录的讨论者，作为画外音和作者聊故事怎么发展，并能把一段精彩的互动梳理成正文写进稿子里。

**这不是聊天机器人玩具，判断标准是**：一次扮演结束后，作者的项目里应该多出点什么——一段可用的正文、一条更准的设定、或者一个想明白了的情节走向。所有设计取舍都朝这个方向倾斜。

## 2. 这**不是**什么（划清边界）

- **不是新的能力包（pack）。** pack 的契约是「贡献知识库分类 + 贡献任务菜单项」（`lib/profile/model.ts` 的 `WorkspaceProfile`），扮演功能两样都不产出。硬塞进去会让 pack 这个概念失去意义。它是一个 **Beta 开关**，形制照抄 `lib/pptx/flag.ts`。
- **不是对话助手的一个模式。** `agentStore.sendChat()` 有 270 行是写作助手专有的（文档焦点判定、故事记忆、计划模式、任务清单）。扮演一样都不需要。复用的接缝在 `runAgent()` 和 `assembleContext()`，**不在 `sendChat()`**。
- **不接管知识库的写入。** v1 里扮演 agent 完全只读；旁白 agent 可以写正文（走现有审批卡），但不写知识库。理由见 §6。

## 3. 四条不变量

这四条是整个设计成立的地基。任何一条被违反，功能就退化成「聊久了就 OOC 的玩具」。

### 不变量一：transcript 是资产，wire history 是缓存

每个 agent 在磁盘上有两份对话记录，职责完全不同：

| | `session.json` | `transcript.md` |
|---|---|---|
| 内容 | 协议格式的 wire history（含 tool 调用） | 人类可读的对话正文 |
| 生命周期 | **可被压缩折叠、可被裁剪、可以丢** | **只追加，永不改写，永不删** |
| 谁读 | 模型（作为上下文） | 作者、旁白 agent、导出 |
| 丢了会怎样 | 重开会话，损失可接受 | **作者的创作没了** |

一切「记忆」需求都从 `transcript.md` 派生，而不是从 wire history 派生。这一条直接解决了两个问题：压缩不会吃掉作者的创作，旁白能读到的东西不依赖别人上下文的存活状态。

### 不变量二：绑定内容进 prelude，永不进 seed 块

`buildCompactedHistory`（`lib/agent/compact.ts:349`）压缩时丢弃 `meta.seedContext` 指向的那条消息，但 **prelude 里其余消息原样保留**；`trimHistory`（`lib/agent/runtime.ts:156`）只裁剪 tool 结果和图片，不动普通消息。

所以扮演会话的历史必须这样播种：

```
[0] system    ← 人设 + 扮演规则 + 作者身份        （永远整条存活）
[1] user      ← 【绑定设定】绑定词条正文           （prelude，压缩不丢）  ← 关键
[2] user      ← 【场景】首轮自动命中的其他词条      （meta.seedContext，压缩会丢，正确）
[3] user      ← 作者的第一句话                    （turnStart）
```

把绑定内容放进 `[1]` 而不是塞进 `[2]`，是「角色永不失忆」的**全部机制**。不需要给压缩加白名单——这是核实代码后的结论，不是猜测。

### 不变量三：旁白读的是别人的 transcript，永远不是别人的 wire history

隔离必须是结构性的，不能靠 prompt 约定。旁白的工具只能触达 `transcript.md` / `summary.md` 这两个**只读的、派生的**文件；它拿不到任何其他 agent 的 `session.json`，代码上也没有那条路径。

这条同时保证了：扮演 agent 之间**永远**互相看不见（它们的工具集里根本没有 scene 工具），而旁白的「全知」是一个显式的、可审计的能力，不是权限泄漏。

### 不变量四：记忆是记录，不是摘要

滚动摘要和角色记忆是两种东西，必须并存，职责不能混：

| | 滚动摘要 | 角色记忆 |
|---|---|---|
| 回答的问题 | 「之前大致发生了什么」 | 「现在有哪些还在生效的约定 / 待办 / 关系」 |
| 性质 | 有损压缩，会被重写、会被再压缩 | 无损记录，**只增改，不删** |
| 位置 | 折叠时生成，替换旧摘要 | **恒在 prelude**，与绑定块同级 |
| 谁维护 | 系统自动 | 角色自己（工具）+ 作者（手改） |

「他答应了雪停就一起去塔下」不是「之前发生的事」，是**一个还没兑现的状态**。被折进摘要就等于失效——摘要会被再次摘要，一条约定三轮之后就变成「他们聊了一些计划」。所以记忆走独立的存储、独立的注入位置、独立的生命周期。

细节见 [02-design.md §5](02-design.md)。

```
│   RoleplayPanel = 花名册 + 对话区 + 编排抽屉             │

                       │
┌─ 状态 ───────────────▼──────────────────────────────────┐
│ stores/roleplayStore.ts                                  │
│   agents: Record<agentId, RoleplayAgent>   ← 元数据       │
│   sessions: Record<agentId, LiveSession>   ← 活的会话     │

└──────────────────────┬──────────────────────────────────┘
                       │
┌─ 领域逻辑 ───────────▼──────────────────────────────────┐

│   sceneTools.ts  旁白的 4 个只读 scene 工具                │
│   presets.ts     ROLEPLAY_PRESET / NARRATOR_PRESET        │
└──────────────────────┬──────────────────────────────────┘
                       │ 全部复用，零改动
┌─ 现有内核 ───────────▼──────────────────────────────────┐
│ lib/agent/runtime.ts   runAgent()  — 已经完全解耦          │
│ lib/agent/registry.ts  工具注册表                          │
│ lib/context/rag.ts     assembleContext / selectLore        │
│ lib/context/loreSelect 钉住(pinned) + 自动命中(auto)       │
│ lib/agent/compact.ts   折叠压缩                            │
│ lib/agent/chatRefs.ts  @ 注入                              │
└─────────────────────────────────────────────────────────┘
```

**改动集中在上三层，最下层一行不动。** 这是这个功能能做的根本原因：`AgentRuntimeOptions`（`runtime.ts:233`）只要求 `messages + preset + toolContext + 回调`，它不知道 store，也不假设「只有一个会话」。

## 5. 磁盘布局

```
.ai-writer/roleplay/
├── agents.json                 花名册：顺序、id、名字、类型、绑定、模型
└── <agentId>/
    ├── agent.md                人设卡：frontmatter + 作者可编辑的扮演指令
    ├── transcript.md           对话记录（只追加，人类可读，旁白读这个）
    ├── memory.md               角色记忆：约定 / 待办 / 事件 / 关系（只增改，恒注入）
    ├── summary.md              滚动摘要（压缩时更新，旁白也读这个）
    └── session.json            wire history + meta（机器格式，可丢）
```

选文件而不选 SQLite 的理由：

1. **它跟着项目走，不是全局数据。** `.ai-writer/` 下的东西会被 `projectBackup` 自动带走（排除表是白名单式的），也在知识库同步的射程内。
2. **`chat_sessions` 表用不了。** `sessionDb.upsertChatSession` 每次写入都执行「只保留最新 5 个」的 DELETE（`lib/agent/sessionDb.ts`）。对话助手的对话是缓存，删了无所谓；**攒了两周的角色互动被一次普通提问挤掉，是不可接受的数据丢失**。
3. **作者能直接打开看、能改、能搜。** transcript 是 markdown，在文件树里就能读；`summary.md` 写歪了作者可以手动改。这与知识库、`task.md` 的既有做法一致。

## 6. 五个决策及理由

| # | 决策 | 理由 |
|---|---|---|
| 1 | **旁白用工具式读取，不用注入式** | 注入式在 N 个角色聊久后必然爆窗口，且每轮都付钱重发。工具式多一轮往返，但可以翻很久以前的记录、可以检索、可以只读需要的那一段——和现有 `read_file` 分页读是同一套心智。 |
| 2 | **落盘 `.ai-writer/roleplay/`** | 见 §5。 |
| 3 | **「写入正文」复用现有写工具，不新建** | 旁白读完场景后自己把它梳理成散文，然后调 `create_chapter` / `append_file` / `propose_edit`。新建一个 `compose_from_scene` 只会是这三个的重复实现，还要重新走一遍审批卡、备份、占位符校验的老路。从作者视角看能力完全一样。 |
| 4 | **并发上限 3，实现为信号量** | 不是三个硬编码分支。`MAX_CONCURRENT_RUNS` 是一个常量 + 一个排队器，改成 5 或做成设置项都是改一个数。 |
| 5 | **每个 agent 独立选模型，子代理沿用全局设置** | `resolveConn(models, providers, modelId)` 已经是按 id 解析的，per-agent 模型就是传 `agent.modelId ?? activeModelId`。子代理（识图/联网）是 app 级设置，自动生效——但**有个坑**，见 02-design §8。 |
| 6 | **角色记忆只在四个时刻刷新注入块，绝不在写入的当下刷新** | `remember` 的 tool 结果本身就留在历史里，模型这一轮和之后若干轮都看得见；真正的失效边界是**那条结果被折叠掉的时刻**，也就是压缩发生时——而压缩本来就重建了历史、缓存本来就作废了。所以「压缩后刷新」不是省钱的优化，它精确地就是正确性边界。写入即刷新只会每记一件事就作废一次 prompt 缓存前缀，换来零收益。见 02-design §5.5。 |

## 7. 被否掉的方案

**A. 改造 `agentStore` 成多会话 Map。**
它有 1500 行，`turns` / `chatHistory` / `chatRunning` / `chatAbort` / `chatUsage` / `chatSessionId` / `chatTaskWorkspace` / `planMode` 全是单值字段，改造会波及 `AgentChat`、`AiDrawer`、审批队列、任务工作区、上下文条。收益是「代码复用」，代价是让一个已经工作的核心功能进入高风险重构。**否掉**：新建 `roleplayStore` 天然就是 `Record<agentId, …>`，且 `agentStore` 一行不改。

**B. 引入「舞台 / 场」的分组层，让一个项目能有多组互不相干的扮演。**
它确实能回答「旁白该看多少」，但作者没要，而且现在的答案很清楚：旁白看这个项目里所有扮演 agent。**否掉，但留了口子**：旁白的 scene 工具全部按 `agentId` 取参，将来加一层分组只是加一个过滤条件，不是重构。

**C. 每轮重发绑定词条，保证一定新鲜。**
破坏 append-only 的历史，prompt 缓存前缀每轮作废，长会话成本会失控。**否掉**：绑定块进 prelude 一次，作者显式点「刷新绑定」时才重写（那一次缓存作废是作者的选择，不是系统的默认行为）。

**D. transcript 存 JSONL，机器友好。**
作者读不了，也编辑不了。**否掉**：markdown + 严格的标题语法 + 容错解析器（解析失败降级成一整块文本，绝不抛异常）——和 `taskWorkspace.ts` 的「机器头 + 人类正文」是同一个先例。

**E. 扮演 agent 也给 `propose_edit`，方便随手改稿。**
扮演到一半弹出一张「要不要改第三章」的审批卡，是把两种完全不同的心流搅在一起。**否掉**：扮演 agent 全只读；要落到稿子上，切去旁白。

## 8. 范围外（明确不做，留给以后）

- 扮演 agent 之间互相对话（agent↔agent，无人类在场）
- 旁白写知识库（`propose_lore_plan` 那套闸门要在新面板里再渲染一套 PlanCard，v1 不上）
- 「舞台 / 场」分组
- 把角色记忆自动提炼成知识库条目（记忆刻意不进正典，理由见 02-design §5.7）
- 群聊（一条消息同时发给多个角色）
- 语音 / TTS

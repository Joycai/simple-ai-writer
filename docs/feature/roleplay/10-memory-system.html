What the Character Remembers

The roleplay agent runs four kinds of memory at once, on four different clocks. Two of them never leave the context window. One is rebuilt whenever the history gets too long. One lives on disk and is retrieved like a search index. This is the map of which is which, and when each one moves.

01

What is always kept in context

A roleplay session seeds a wire history with a fixed shape. Position in that shape is the whole permanence mechanism — there is no whitelist anywhere in the compaction code. Three things survive forever because of where they sit:

The three permanent blocks, and why each one is there

[0] system

Who the character is. Persona body, the author’s own direction, who the author is playing, markup syntax, and the memory rules. Deliberately not built from profileSystemPrompt() — the writing-collaborator persona would make the character explain itself.

[1] 【绑定设定】

Pinned lore, verbatim. Entity or facet bodies for agent.boundPaths, up to 12 000 chars; overflow is named but not expanded, with a note to use read_lore_entity. A pin to a deleted facet goes to stalePaths — it never silently degrades into “inject the whole entity”.

[2] 【记忆】

What the character has written down. Only open records, up to 4 000 chars, grouped pact → todo → scene → bond → event → note. Overflow becomes “N more — use recall”.

The invariant that makes it work

The bound block must be its own message in the prelude, never merged into the seed block. Merged, it inherits meta.seedContext and dies at the first compaction — the character forgets its own character sheet mid-scene. __tests__/context.test.ts runs real compaction over a seeded history to hold this down.

Both prelude blocks are created unconditionally, even when empty (they render a one-line placeholder). Creating them lazily made “none → some” a state transition nothing could catch: a brand-new character that called remember mid-scene had no memory block for refreshMemoryBlock to write into.

What is not permanent, and why that is correct

  • 【场景】 the seed retrieval block is dropped at the first compaction. It is retrieval output — reproducible from the lore index at any time. The bound block is not: it is who this character is.
  • Per-turn lore injections ride inside their turn and fold with it. The injection ledger (meta.injected) holds each entity keyed by the message that carried it; when that carrier leaves the history the ledger entry is evicted, so a later mention re-injects.
  • Tool results — including remember’s confirmation — are the first thing trimHistory throws away, replaced by an elision marker. This is precisely why the memory block exists.
02

When compaction fires

Compaction is checked once per author message, on the continue branch only — inside prepareContinuedHistory, before this turn’s retrieval and before the question is appended. A freshly seeded session never compacts (there is nothing to fold yet), which is also why replay from transcript has its own hard char cap.

The trigger is a share of the message ceiling, not of the model’s context size. Two subtractions stand between them, and both matter:

The fold decision

  1. Is it due?estimateMessagesTokens(history) > ceiling × 0.7. No → return null, nothing happens.
  2. Is there anything foldable?Segment at meta.turnStarts. The last MIN_KEEP_TURNS = 2 turns are never folded; if that leaves nothing, return null.
  3. How much?Start from the largest legal fold, then walk backwards un-folding turns while the projection still fits under ceiling × 0.45. The projection charges the summary at its full 1 000-token budget, so the estimate is pessimistic on purpose.
  4. Summarize.One no-tools completion on the session’s own model. Injection carriers are skipped from the summarizer input — retrieval blocks are reproducible, and summarizing them would spend the budget on what the lore index already holds. Tool traffic is clipped to 200 chars per result, prose to 2 000.
  5. Rebuild.New array: prelude minus seed & old summary → new summary right after the prelude (maximal stable prefix for prompt caching) → kept turns verbatim. meta.turnStarts is reset; ledger entries whose carrier just left are evicted.

Failure is a no-op, by contract

A failed or empty summarize request returns null and leaves both history and meta untouched — the turn proceeds uncompacted and the threshold fires again next turn. Only an AbortError propagates, because that means the author cancelled the whole send. Compaction must never turn a network hiccup into a damaged session.

Why the gap between 0.7 and 0.45 is wide

A tight gap would compact almost every turn, and every compaction invalidates the prompt-cache prefix. One multi-tool turn can add thousands of tokens, so the retain target has to leave real headroom below the trigger.

The other trimmer: trimHistory, every round

Separate mechanism, separate clock. Inside the agent loop, before each round:

  • Images are elided unconditionally, regardless of the ceiling. The token estimate charges a flat rate per picture because that is what providers bill — but the payload is megabytes of base64, and a roleplay session persists across turns.
  • Then, only if still over the ceiling, tool results are replaced with an elision marker one at a time until it fits.

Note what it never touches: plain user and assistant messages. That is the second half of why the three prelude blocks are permanent.

03

The character’s private notebook

This is the part that is not a summary, and the distinction is the whole design. A rolling summary is lossy and gets summarized again: “he promised to go to the tower when the snow stops” folds once into the summary, and three turns later it has become “they discussed some plans”. But that was never an event that happened — it is an unresolved state, and it has to survive verbatim until it is kept or called off.

So memory gets its own storage, its own injection slot, and its own lifecycle.

Three tools, scoped structurally

ToolDoesRefuses to
rememberAppend one record: kind, title, body, subject, up to 8 keys. Gets an id that is never reused.Accept an unknown kind, or an empty title.
revise_memoryChange one record’s body and/or status by id.Create anything. An unknown id returns the list of real ids and changes nothing — silently creating would leave the author with two contradictory records.
recallList records, optionally filtered by kind, optionally including closed ones.—

They are named remember / revise_memory / recall and not read_memory / update_memory on purpose: those two already exist for a document’s story memory (a rolling summary keyed by source-text ranges). Same word, different thing.

The store is handed in as ToolContext.agentMemory and takes no agent id — there is no parameter through which a character could reach another character’s notebook. It also re-reads the file on every call, because ToolContext is a snapshot taken when the run started, and a recall right after a remember in the same run has to see what was just written.

Six kinds, three statuses

KindMeaningHas a “done” stateAt scene change
pactSomething promised to the other personyesstays if open
todoSomething intended, not done yetyesstays if open

sceneThe previous scene’s recap — one per scene, written only at a transitionnosinks

noteAnything else worth knowing laternosinks

The enum is fixed rather than pack-defined, unlike knowledge-base categories: these are products of conversation structure, not of a domain. Tabletop, romance and mystery all generate pacts and bonds.

Status is open / done / void. Only open records are injected — a kept or called-off promise is no longer a live state, and injecting it both costs budget and misleads the model into thinking the matter is still hanging. Closed records are reachable only through recall({include_closed: true}).

Three write rules that make an unapproved write tool safe

These are L1 auto-write tools: no approval card stands behind them. The only safety valve is making the worst case “extra noise”, never “something lost”.

  1. Add and revise only, never delete. There is no forget. Calling something off means setting status: "void" and keeping the text.
  2. Back up before every write, same as every other L1 write tool.
  3. No whole-file rewrite tool exists. The model can add one record and patch one record — so the blast radius of one bad call is one record.

Ids follow from rule 1: the next= counter in the file’s machine header never rolls back, even when a record leaves, because a reference to m7 in the transcript must always point at the same thing.

The parser never throws — hand-editing memory.md is a supported thing for the author to do. A block it cannot recognise is not discarded: it degrades into a note carrying the original text, so the next normalising write still contains what the author typed.

The four refresh moments — and the one that looks obvious but is wrong

Both refreshes mutate content in place and never swap the message object: meta.memoryBlock and meta.boundBlock hold those messages by identity, and replacing the object would cut the injection ledger loose from the thing it points at. When memory goes from “some” to “none”, the block is not deleted — it becomes a one-line placeholder, because removing a prelude message shortens the stable prefix and voids the cache for the sake of one line of text.

What the model is told about when to write

record

A promise made to the other person · something intended but not yet done · something that happened and will matter later · a change in how it feels about someone · anything that will need to be known later.

do not record

Ordinary conversation · the character’s own passing thoughts · things already written in the lore · anything already recorded. Over-recording is cheaper than missing something — an unrecorded promise gets forgotten.

Each record carries the transcript turn number it was written at, so the notebook panel can jump the author back to the moment. The store computes it as turns.length + 1 — the author’s turn is already on disk by then, so the character’s reply is the next one. A record the author adds by hand gets turn: 0, which keeps it out of the “just recorded…” line under the reply and out of rollback.

04

Scene change, and the memory area

Standing memory cannot grow forever — but nothing may be thrown away either. The resolution is a second tier: at a scene change, records that are no longer live sink out of the injected block into a searchable store, and come back only when something in the conversation matches them.

Two transitions, and only one of them keeps anything

A transition means this scene counts: it is archived, and a recap carries forward as memory. “Another scene” (另起一场) means the opposite — the scene was a trial run and is void. That distinction is the author’s, and for a long time the code did not honour it: sorting ran unconditionally, so a character’s remember calls from a throwaway scene sank into the memory area with their keywords intact and surfaced three scenes later. Nothing was discarded except the author’s intent.

Discarding is semantic, never physical

No transcript is ever deleted. A discarded scene is archived as transcript-NN.discarded.md — the marker rides the rename that was happening anyway, so there is no second source of truth to keep in step. The author can still read it in the archive viewer; the character and the narrator cannot. That last part is what matters: the narrator writes into the manuscript, and a trial run must not become plot.

The transition, in order

  1. Compute the scene number firstpeekNextArchiveNo — max existing number + 1, never the file count. After the author hand-deletes one archived scene, counting files would make “from scene N” point at the wrong scene. The same number is stamped on every record written during the scene (MemoryRecord.scene), which is what makes the next step addressable at all.
  2. Write the memories, then archiveThe reverse order loses a scene: if the recap fails to save after the transcript was already moved away, the author is looking at a blank screen with nothing kept.
  3. Kept → sink, one entry per recordEach sunk record becomes its own area entry with its own keys. Merging them into one prose block would turn them back into a summary — the exact thing the memory tier exists to avoid. Records only leave standing memory after every entry is written, so a mid-way failure duplicates at worst.
  4. Discarded → sort nothing, drop this scene’s recordsEverything stamped with this scene number leaves standing memory and never reaches the area. A record whose scene is 0 — written before the field existed — is never matched: nobody knows which scene it belongs to, and guessing “this one” would delete something the author did not mean to delete. As with every author-driven removal, the file is backed up first.
  5. Kept → write the recapThe generated recap is added as the one scene record, stamped with the scene that just ended — so it doubles as a pointer back to that transcript. With no memory area configured, the previous scene record is voided instead — text kept, just no longer findable.
  6. Archive by renametranscript.md → archive/transcript-NN.md, or -NN.discarded.md. A rename, never a truncation — the transcript is append-only and must not lose a character. The number-picking regex and the listing regex must accept the same names: teach only the listing about the discard suffix and the next scene reuses a taken number, silently overwriting that scene’s summary. session.json is the one file simply deleted: it is a cache, and a wire history that reconnects to no transcript is unreadable to anyone.

The recap is written by the character, in first person

Not by an outside summarizer — and this is an isolation requirement, not a style preference. A third-person omniscient summary would write down things the character was not present for. Asking it “what will you remember” naturally contains only what it can know. It runs as a structured single-shot on the character’s own system prompt, and lands in neither the transcript nor the wire history — stepping out of the scene is not a turn of it.

Why the area is never merged into the project’s lore index

The area holds what a character believes, which may contradict the manuscript. Merging it would turn isolation from “it is not in there” into a filter that has to be right in six places at once: per-turn injection, the lore read tools, the consistency check (which would report a character’s mistaken belief as a contradiction in the prose), the knowledge wall, sync export, and the narrator’s context. Missing one is a silent leak.

The area also belongs to itself, not to an agent — areas/<areaId>/, not <agentId>/. Delete the character and the area survives; bind a new character to it and the knowledge reconnects. One area may be bound to only one agent at a time, because two characters sharing a memory is isolation not existing.

05

Everything else that matters

Where it all lives

.ai-writer/roleplay/ ├── agents.json roster: order, metadata, author persona ├── areas/<areaId>/ the memory area — survives its character │ ├── meta.json name, boundTo, lastScene │ └── history/eNNN/index.md └── <agentId>/ ├── agent.md persona card (frontmatter + the author's direction) ├── transcript.md ASSET — append-only, never rewritten ├── memory.md ASSET — the private notebook ├── summary.md rolling summary, written at each compaction ├── session.json CACHE — wire history + meta, safe to lose └── archive/ transcript-01.md, summary-01.md, memory-01.md

It sits in the project directory rather than the chat_sessions table because that table truncates itself to the newest five sessions — fine for assistant chats, unacceptable for two weeks of character interaction. Living under .ai-writer/ also means projectBackup carries it along for free.

Asset versus cache — and what happens when the cache is gone

If session.json cannot be read, the next send re-seeds from disk and replays the transcript back into the new history. Without the replay the author would be staring at a full screen of conversation while the character says it does not know what happened — the page intact, the model amnesiac, which is the hardest failure mode to notice.

Two constraints on the replay, both load-bearing:

  • It must start at an author turn. Turn boundaries are marked on author questions; a slice starting with a character reply would leave that reply in the prelude, where compaction can never reach it.
  • It is capped at 12 000 chars, most recent first. Replay goes through the seeding path, and seeding does not compact — an unbounded replay would blow the first request. Everything earlier is carried by summary.md and memory.md, which is exactly why they exist.

Isolation is structural, not prompted

the character preset

Nine tools. No read_file, no search_text, no scene tools at all, and no write tool that touches the manuscript or the knowledge base. Characters cannot read each other because there is no code path, not because we asked them not to.

looking back at itself

search_conversation / read_conversation go through ToolContext.conversation, which takes no agent id. They replaced search_text, which scanned the manuscript and excluded .ai-writer/ — so it could never find a transcript, and what it could do was the one thing the design forbids.

the narrator

A different preset with list_scenes / read_scene / search_scenes / read_scene_summary / read_scene_memory, plus manuscript write tools. The channel is only handed to it when agent.kind === "narrator" — belt and braces on top of the preset.

round limits

Character: 5 rounds, force-text, and deliberately no round-limit card — that card would cut a scene in half and train the author to wave it through. Narrator: 20, since reading several scenes before writing prose can legitimately need them.

“Your setup changed” — the staleness baseline

The system layer holds four things read exactly once at seeding: the persona body, the author’s direction, who the author is playing, and the roleplay rules. The first three change whenever the author edits them, so refreshSystemPrompt rewrites history[0] in place, and contextSignature is the baseline for the “setup changed” hint.

The signature covers all of those inputs, not just the bound text — it once covered only the bound block, so the two most common edits (changing the persona entry, switching identity) never lit the hint at all. It hashes the inputs rather than the rendered prompt, because the rendered prompt contains i18n copy and switching UI language would mark every character stale. The hash lives on the roster, not on the live session, so a project with ten characters lights the right ones the moment the app opens.

If you add anything author-editable to the system layer, add it to that signature too — otherwise the hint never lights, and the author has every reason to believe an edit took effect.

Rollback: the one place records are actually removed

“Never delete” guards against the model deleting records it dislikes. An author rewinding to turn N is a different act: a pact born in a stretch of conversation that has been undone is worse kept than dropped, because the character will confidently bring up something that never happened. So dropRecordsFrom removes records with turn >= N; turn: 0 (author-written) is never touched, revisions are not un-done, and the id counter does not roll back.

Every other removal is a move into .ai-writer/backups/ — deleting an area, an area entry, or a whole character. The moment something is most likely to be deleted is the moment the author believes they no longer need it.

Five things that will bite you

  1. Merging the bound block into the seed block makes the character forget its own sheet at the first compaction. Keep it a separate prelude message.
  2. Adding an author-editable input to the system layer without adding it to contextSignature means the “setup changed” hint never lights again for that input.
  3. Refreshing the memory block on write looks obviously right and is wrong: it voids the cache prefix per recorded fact and buys nothing, because the tool result is still visible.
  4. Marking sunk records void instead of moving them out makes the sink filter match them forever, re-flooding the area on every transition — entries grow quadratically in scene count.
  5. Passing the raw input ceiling to planFold instead of messageCeilingFor silently ignores the tool schemas, and the context bar sails past its own compaction mark with nothing happening.

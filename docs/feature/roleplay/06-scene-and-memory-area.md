# 转场与记忆区

> **状态：设计，未实现。** 上游是 `05-implementation-notes.md` §3.6 里挂着的「场」
> 数据模型。这份设计的结论是：**不需要「场」这根轴**——转场就是新开会话，而让历史
> 不被遗忘的是一个可检索的记忆区。

## 1. 要解决什么

三件事，一直被当成三件事，其实是一件：

1. **「这一场结束了，换个地方继续」没有出口。** 现在只有「新开会话」，而它是彻底
   归档——从客厅走到卧室不该等于失忆。
2. **前情会堆积。** 把上一场的摘要塞进记忆，转场三次之后第三条是从第二条转写来的，
   而记忆的设计明确说过它**不是摘要**。
3. **删掉一个 agent，它攒的一切跟着进 backups。** 角色的知识和角色的壳绑死了。

## 2. 两条设计

**转场**：新开会话分两支——「另起一场」（无关，整场归档）和「接续」（相关，产出一份
前情）。

**记忆区**：每个 agent 绑定一个**独立于项目知识库**的知识区，格式与 lore 完全相同、
复用同一套代码，但**不进项目的 `loreIndex`**。旧前情、已了结的记录、零碎史料都归档
到这里，靠关键字在相关时被命中。

它们是一件事：**转场产出前情，记忆区让前情活下去**。

## 3. 分层：承诺 vs 史料

这是整份设计的核心，先说清楚。

记忆存在的全部理由是「一条没兑现的约定，三轮之后不该变成『他们聊了一些计划』」。
知识库是**命中制**的——不提到关键字就不出现。把记忆整个搬进命中制的存储，等于把
这条保证换掉了。所以必须分层，而且**按性质分，不能按预算溢出分**：预算不够就把
一条未兑现的约定挤进检索层，正是这套东西当初要防的事。

| 层 | 存哪 | 谁在这一层 | 何时进上下文 |
|---|---|---|---|
| **常驻** | `memory.md`（格式不变） | `pact` / `todo`（`open`）、`bond`、**最新一条前情** | 恒在 prelude |
| **史料** | 记忆区（lore 格式 + 关键字） | 归档的前情、已 `done`/`void` 的记录、`event` / `note` | 按关键字命中 |

常驻层因此是一个**有界的小集合**，`MEMORY_BLOCK_CHAR_CAP` 不再紧张。

### 3.1 降级只发生在转场

`event` / `note` 归哪一层？答案是：**先都进常驻层，在转场那一刻降级。**

理由：一件刚发生的事当然该无条件生效——它就发生在这一场里。而一场戏结束正是
「归档」这个动作天然的位置，和记忆刷新的四个时刻是同一种设计：**给一个语义清楚
的时刻，而不是一个持续生效的规则**。

转场时的分拣规则：

- `pact` / `todo` 且 `open` → **留在常驻层**（欠着的事不会因为换了个房间就不欠了）
- `bond` → **留在常驻层**（关系给每一句话上色）
- 其余（`event` / `note` / 已 `done` / 已 `void`）→ **并进这一场的前情条目**，移出常驻层
- 上一条前情 → 降级成记忆区里的一条独立条目

> **前情允许模糊，这正是约定单独成条的理由。** 承诺不会跟着摘要一起褪色，褪色的
> 只有叙事质感。这句话必须写在这里——否则以后一定有人拿「记忆不是摘要」来质疑
> 这个设计。

### 3.2 推与拉是一对

关键字匹配有天然缺口：作者说「还记得那天晚上吗」，命中不了 `塔`、`雪`。项目知识库
一直有这个毛病。

补它的是**已经存在的 `recall` 工具**：关键字负责「该出现时自动出现」，`recall` 负责
「模型自己觉得缺了什么就去翻」。两半配齐，才谈得上「历史不会完全遗忘」。本设计不
新增拉的一侧，只把 `recall` 的搜索范围扩到记忆区。

## 4. 记忆区：复用代码，不复用索引

**格式与 lore 完全相同**（`index.md` + frontmatter + 特征 + 配图），复用 `scanLore` /
`selectLore` / 条目详情页 / AI 整理那一整套。`scanLore` 里硬编码的只有一行
`${projectPath}/.ai-writer/lore`，加一个 root 参数即可。

**但它不进项目的 `loreIndex`。** 这一条是不变量，不是优化。

并进去的话，隔离性会从**结构性**降级成一个要在六个地方同时正确的过滤器：

| 地方 | 漏了会怎样 |
|---|---|
| `assembleTurnInjection` 的 `selectLore` | 甲的记忆命中乙的提问 |
| 扮演 preset 里的知识库读工具 | 角色直接 `read_entity` 别人的记忆区 |
| `consistency/scan.ts` | 它拿同一个 `loreIndex` 比对正文——角色的**错误认知**会被报成正文矛盾 |
| 知识库墙 | 每个 agent 一个顶层分类的杂物 |
| 知识库同步 / 导出 | 整棵 lore 树打包上传，把角色的私货一起传走 |
| 旁白的上下文 | 它本该只看 transcript |

六个都对才行，漏一个就是**静默泄漏**。放在自己的目录里，这六条全部自动成立。

### 4.1 记忆区归自己，不归 agent

存 `.ai-writer/roleplay/areas/<areaId>/`，**不是** `<agentId>/`。

因为它要能被继承：删掉 agent，记忆区还在；建一个新 agent 绑上它，知识就接上了。
agent 于是变成一个「壳」——人设卡 + 绑定 + 模型 + 记忆区的引用。

**一个记忆区同一时刻只能被一个 agent 绑定。** 两个 agent 共用一份记忆等于隔离性
不存在，而这不是一个值得留的口子：真要「双胞胎共享记忆」，那是一个独立设计。

### 4.2 角色的记忆可能和正典矛盾

角色以为沈砚死了，知识库里他活着。对扮演来说这是**特性**。但这意味着两者进上下文
时必须分块标明：

- 【设定】= 世界的事实
- 【记忆】= **这个角色以为的**事

合成一个块，角色会开始把自己的猜测当成公认事实说出口。

## 5. 转场

### 5.1 两支

- **另起一场**：现有 `newSession` 的行为。整场归档，可选「同时清空记忆」。
- **接续**：产出一份前情，然后归档。**不给「清空记忆」勾选项**——接续明摆着要保留，
  给了只会让作者怀疑自己理解错了。

接续时提供一个输入框：作者写摘要的侧重（「重点记下和塔有关的」），留空则模型自行
判断。

### 5.2 摘要由**角色自己**写

不是旁观者。这不是风格偏好，是隔离性要求：一段第三人称全知摘要会写进角色不该知道
的事。让角色以第一人称写「我会记住什么」，天然只含它知道的。

实现走 `lib/agent/structured.ts` 单发（角色的 system prompt + 这一场的 transcript），
**不进 transcript、不进 wire history**——它是出戏的一步，不是一轮对话。

产出：`{ title, body, keys[] }`。`keys` 就是这条前情的关键字，日后靠它被命中。

### 5.3 一次摘要，两个去处

| 去处 | 服务谁 |
|---|---|
| `memory.md` 的最新一条前情 | 角色永不遗忘刚发生的事 |
| 新一场的 `summary.md` | 旁白的 `read_scene_summary`；下次压缩把它当 `prevSummary` 接着滚 |

（`seedRoleplayHistory` 的 `priorSummary` 已经就位，只是现在的条件是
`priorTurns.length`，接续分支要放宽。）

### 5.4 顺序：先摘要，成功了再归档

摘要失败就整个中止，什么都不动。否则会出现「场归档了但前情没写成」——作者眼前
一片空白，而上一场已经不在当前 transcript 里。和「先落盘再排队」是同一条纪律。

## 6. 存储布局

```
.ai-writer/roleplay/
├── agents.json                    花名册（+ 每个 agent 的 areaId）
├── areas/
│   └── <areaId>/                  记忆区：格式与 .ai-writer/lore 完全相同
│       ├── meta.json              名字、创建时间、当前绑定者
│       └── history/               分类目录（区内的分类另行定，见 §9 待定）
│           └── <entry>/index.md
└── <agentId>/
    ├── agent.md · transcript.md · memory.md · summary.md · session.json
    └── archive/                   历次转场封存的场次
```

## 7. 检索与账本

逐轮注入变成两路，**分别匹配、分别成块**：

```
【设定】 ← selectLore(matchText, projectLoreIndex, …)
【记忆】 ← selectLore(matchText, areaIndex, …)
```

账本（`meta.injected`）共用一份，记忆区的键加前缀 `area:<dirPath>`，否则要么和项目
条目撞车，要么每轮重发。

预算分开：记忆区有自己的 `areaBudgetChars`，不和设定抢——一场戏聊到深处时最不该
发生的事，是角色的记忆把它自己的人设挤出去。

## 8. 被否掉的方案

- **给 lore 加一根 `area` 轴。** 类型系统那份设计（`docs/lore-entry-type-plan.md`）明确
  否掉过第二根轴，并留话说真需要跨切面归组时那是 `tags`、是第三样东西。而且 tags
  也给不了 §4 那六条隔离。
- **记忆区做成用户自定义分类。** 机制上可行（`projectStore.setCustomCategories`），
  但它仍然在项目索引里，六条隔离一条都不成立。
- **全在记忆区，常驻层用 pin 表达。** 只有一个存储，很诱人。但 `remember` 一条约定
  就要往花名册里写一个 pin，而绑定块是「设定已更新」的哈希基线——每记一件事就误报
  一次。
- **记忆区条目带 `standing` 标记。** 干净，但那是给 lore 格式加语义，等于又开了一根轴。
- **按预算溢出分层。** 见 §3：会把未兑现的约定挤进检索层。
- **前情只留最新、旧的自动 `void`。** 这是记忆区出现之前的备选。它在**丢信息**——
  记忆区让旧前情仍然可被找回，严格更好。

## 9. 待定（实现时要先答的）

- **记忆区内部用什么分类？** 全部平铺在一个 `history/` 下，还是按「人 / 地 / 事」分？
  倾向平铺——分类是给作者导航用的，而记忆区的导航靠搜索和关键字。
- **AI 优化记忆区**（合并重复、补关键字）算这一期还是下一期？倾向下一期：先让它
  长出来，再谈整理。
- **旁白读不到 `archive/`** 仍然没解决，但转场让它更明显了。§5.3 把摘要写进
  `summary.md` 能缓解一半。真正的解法是 `list_scenes` 打开到归档，而**这个方案正好
  给了场号的定义**：场号就是每个 agent 自己的归档序号，返回 `(agent, 场号)` 二元组，
  不需要全局场编号。建议紧随其后做。

## 11. 不变量

在既有四条之外，这份设计加两条：

5. **记忆区永不进项目的 `loreIndex`。** 隔离靠「不在那里」成立，不靠过滤成立。
6. **常驻层只按性质决定，永不因为预算被降级。** 一条 `open` 的约定进不了上下文，
   就是这套东西失效了。

## 12. PR 1 的实现记录

落地时定下来、设计里没写的几条：

**摘要要先预览再落盘。** 设计只说了「先摘要成功再归档」，实现时多加了一步：跑出来
的前情**先给作者看，可以改标题、正文和关键字**，确认了才写。理由是它会成为角色的
长期记忆——一份没被看过就生效的记忆，作者三场之后才会发现它记错了，而那时原始
transcript 已经在 `archive/` 里。所以 store 上是两个动作：`previewRecap`（只跑，不写）
和 `newSession`（把确认过的那份带进去）。

**`keys` 现在就存，尽管还没人读。** 记忆区是下一期，那时再回头补关键字就得把整场戏
重新摘要一遍，而 transcript 早已进了 archive——代价和现在顺手存下它完全不成比例。
格式是记录头行的 `keys=a,b,c` 字段；关键字里的 `·` 和 `,` 会被清掉，否则这一行读不
回来（`memory.test.ts` 有往返测试守着）。界面上它可见可改，不是一个作者看不到的
隐藏字段。

**摘要用角色自己的 system prompt。** `buildSystemPrompt` 的产物原样传进
`runSceneRecap`，只追加一段「现在做一件出戏的事」的口径。换掉 system 就等于换了一个
人来回忆这场戏——§5.2 那条隔离性要求，落在代码上就是这一行。

**写记忆 → 归档 → 写新 summary，顺序不能动。** 归档会把旧的 `summary.md` 一起搬走，
所以新一场的摘要必须在归档**之后**写；而记忆必须在归档**之前**写，否则摘要落盘失败
时上一场已经不在当前 transcript 里了。

**前情的 `turn` 是 0。** 它讲的是整整一场，不属于任何一轮——和作者手写的记录同一个
约定（`turn: 0` 的记录不会在对话区冒出「记下了：…」）。

**旧前情作废而不是删除。** 转场时把上一条 `scene` 标 `void`，正文保留。§3.1 的完整
降级（并进记忆区）要等 PR 2。

**界面第一版按现有视觉语言自定，稿子到了之后已对齐**（见 §13）。

## 13. 对齐 TURN 2 设计稿（屏 2a / 2b / 2f）

稿子推翻了第一版的两个判断，都是对的：

**转场不是弹层，是就地向上展开。** 第一版做成 560px 居中卡片，稿子明确写着「不居中、
不遮挡、不加第二层阴影——只是从一行变成了一块」。理由是它一天可能用好几次，居中弹层
每次都要打断一次注意力。改回 footer 就地展开。

**两支的差别用一道线表达，不用图标也不用第二个颜色。** 另起一场是**断掉的线**（＝什么
都不带过去），接续是**中间嵌一个赭石实心方块的线**（＝带一块东西过去）。这比任何一句
说明文字都直接，而且不引入新的视觉元素。

其余按稿实现：

- 头部报**场号 + 轮数 + token 估算**（`当前第 3 场 · 18 轮 · 约 9.2k tok`）。场号 =
  归档数 + 1，稿面顶端那条带和这里必须是同一个数，所以两边都从 `listArchives` 数。
- 两支的附加项**位置相同、只出现一个**（接续＝摘要侧重，另起一场＝清空记忆）。
- 生成中**原地替换整块**，带步骤列（读完 N 轮 ✓ / 侧重 ✓ / 写前情与关键字 ⟳）和计时。
- 关键字在预览里是**芯片**，不是一行文本——它们是一组独立的东西，每个都要能单独去掉。
- **「不要前情」不等于取消转场**：它按另起一场落地。预览是最后一次拦住模型写进角色
  脑子的机会，所以确认按钮说的是「封存并开始」，不是「保存」。

**屏 2f：存档带和前情提要合成一件东西。** 原来是稿面顶端一行「此前已封存 N 场 · 查看」，
现在是一条压在顶端的带子，前情挂在它下面。它不是一轮对话——没有左规、没有名标、不占
正文行距，靠满栏底色和上下两道细线和对话分开。收起态只留标题（收起的是正文，不是「这
一场从哪儿来」）。前情直接读常驻层里那条 `open` 的 `scene` 记录，所以作者在记事本里改
完，稿面立刻跟着变，不需要第二条同步路径。

**没做稿子里的场次分隔线**（`第 4 场 · 晨 · 码头`）：它要一个场的名字和时间，而那是
§9 待定里的东西。只有场号的话，它和正上方那条带说的是同一件事，纯属重复。

**屏 2c / 2d / 2e / 2g 是记忆区**，随 PR 2 做。

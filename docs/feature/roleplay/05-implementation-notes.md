# 实现记录（设计稿 08 TURN 1 + 角色记忆）

> 对应 UI 设计稿 `08 扮演 Roleplay.dc.html`（claude.ai/design 项目
> `17a6a5ce-f60e-4996-8f94-5948958206d0`）的 1a–1i 九屏。
> 计划见 [03-plan.md](03-plan.md)——这一轮一次做完了原计划的 PR1 / PR2 / PR4 / PR5，

## 1. 这一轮做了什么、没做什么

**做了**：Beta 开关、`.ai-writer/roleplay/` 存储、花名册、扮演对话（播种 / 逐轮注入 /
流式 / transcript 落盘 / 会话恢复）、混合文本排版、并发闸（3 个 + FIFO 队列）、
per-agent 模型、`@` 引用、旁白 agent + 四个 scene 工具、新建/编辑抽屉、空态、
绑定失效与「绑定内容已更新」、窄窗口的 tab 分档。

**第二轮补的**：卡片按界面路由（见 §2.5）、旁白的轮数上限卡。

**第三轮补的**：「绑定内容已更新」的基线进花名册（见 §2.6）。

**第八轮（一次审查）修的**：system 层不是只播种一次的（§2.16）、`search_text` 是个
死胡同（§2.17）、自定义身份补上入口（§2.18）。

**第四轮补的：角色记忆。** `memory.md`、三个工具（`remember` / `revise_memory` /
`recall`）、旁白的 `read_scene_memory`、记事本面板、对话区的「记下了：…」痕迹。
播种出来的历史因此变成 `[system, 绑定块, 记忆块, seed 块, 提问]`——记忆块和绑定块
一样是 prelude 里的独立消息，同样不进 `meta.seedContext`，因此同样免疫压缩。

设计稿 TURN 1 没有画记事本面板，所以那一屏的判断是自己做的，理由写在
`components/roleplay/MemoryPanel.tsx` 的开头：**可收起的第三栏，但入口带计数**。
稿面固定 640px 是这个面板不肯让步的一条，一栏常驻的记事本会把它压到 640 以下；
而计数常驻在信息带上，是因为记事本不是配置，是作品的一部分——作者应当一眼看到
「这个角色还欠着三件事」。

## 2. 与 02-design 的差异（都是实现时才看清的）

| 差异 | 为什么 |
|---|---|
| `session.json` 里 `turns` 存空数组 | 显示用的对话从 `transcript.md` 派生。少存一份就少一份要保持一致的东西——这正是不变量一想要的：session.json 丢了只损失模型脑子里的细节，一个字的对话都不少。**反序列化失败就从 transcript 重新播种**——第一轮只做了显示层，wire 层第六轮才补上（§2.10）。 |
| 摘要在**压缩发生时**顺手落盘 | `compactChatHistory` 本来就在生成那段文字，再单独跑一遍摘要是白花钱。旁白的 `read_scene_summary` 读的就是它；还没触发过压缩的短会话没有摘要，工具会如实说「太短，直接 read_scene」。 |
| 输入框的实时着色**只换颜色** | 设计稿 1c 给四种标记配了字号（16/18/15/12）和斜体，那是**稿面**的排版。输入框是 textarea 上盖一层镜像 div，字号、字重、字形任何一项不同，光标就会和字错开。颜色足以传达「标记生效了」，而它是唯一能精确对齐的维度。 |
| 组字期间镜像层让位 | textarea 的文字默认透明（可见的是底下带色的镜像）。中文输入法的候选文字如果落在透明层上，作者看不见自己在打什么——`compositionstart` 时换回不透明，`compositionend` 时换回来，也正好落在设计稿说的「闭合的那一刻做 160ms 颜色过渡」。 |
| 每个 agent 懒创建一个标准 task workspace | `routeTools` 的两条规则会互咬：vision 子代理可用时剥掉 `read_image`，而 `delegate` 只在有 workspace 时才追加。没有 workspace 的 agent 一开 vision 就**既不能自己看图、也不能委派**。代价是任务列表里会出现扮演产生的条目，可接受——资产是 transcript，不在 `tasks/` 下。 |
| 「绑定内容已更新」的触发信号是 lore index 的**对象身份** | 起初用条目总数，但改一段特征不会改变条目数——最常见的一种「绑定内容变了」恰好是计数看不见的那一种。 |
| 自动批准的 key 是本次运行的 `AbortController` | `CHAT_AUTO_APPROVE_KEY` 是对话助手专用的字面量；几个 roleplay agent 共用一个字面量会让 A 的「本次都批准」悄悄覆盖到 B。用对象身份，`autoApproveScope()` 自动把它判成 run 级。 |
| 「把对话写进正文」没有新工具 | 旁白读完场景后自己改写成散文，再走现成的 `create_chapter` / `append_file` / `propose_edit`。新建一个 `compose_from_scene` 只会重复实现审批卡、备份和占位符校验。 |

## 2.5 卡片路由（第二轮补的）

第一轮漏了一件事：**被阻塞的卡片没有归属**。`agentStore` 的四个队列（审批 /
方案 / 轮数上限 / 截断）一直是被对话助手和任务面板**整个**渲染出来的——在扮演
出现之前这没问题，同一时间通常只有一个界面在跑。扮演打破了这个假设：它能同时
跑三个 agent，每个都可能提出自己的改稿请求。不区分的后果不是难看，是**卡片
出现在另一个 tab 里**：作者看到旁白停住不动，而唯一能解开它的按钮在他没打开的
那一页上——旁白最重要的那条能力（把互动写进正文）因此实际走不通。

规则落在 `lib/agent/approvalRouting.ts`，只有一条，故意做成加法：

- **没有 `surface` 的卡片**属于默认界面（对话助手 + 任务面板），行为与从前完全
  一致，所以没有任何既有路径会因为这次改动突然把卡片藏起来。
- **带 `surface` 的卡片**只由同名界面渲染。今天唯一打标的是扮演面板，用 agentId
  打标，于是三个并发的 agent 各看各的。

**默认必须是「显示」而不是「过滤」**：在这里「藏起来」等于「那次运行永久挂起」。

配套的两处：

- **轮数上限 / 截断卡只接给旁白。** 扮演 agent 的 `maxRounds: 4` 是刻意的小，撞到
  说明模型在做错的事，force-text 收尾正是想要的降级——弹一张「要不要再给四轮」
  只会训练作者为一个本就不该需要轮数的模式一再放行，顺带把一场戏切断。旁白不同：
  `maxRounds: 20`，读几场戏再改写成正文完全可能撞上，撞上就直接收尾等于半途而废。
  **存盘暂停不给**（`canPause: false`）——扮演这边没有恢复已暂停任务的入口，给了
  就是一个存进去再也拿不出来的按钮。
- **`stop()` 要主动排空本次运行的队列。** 中止信号解不开一张正阻塞着的卡片：
  `onRoundLimit` 等的是一个 Promise，而 abort 不会让它 reject。`stopChat` 早就
  这么做了，扮演这边第一轮漏了——没有它，「停止」按下去 agent 会永远卡在那张卡上。

## 2.6 「绑定内容已更新」的基线存在花名册里（第三轮补的）

第一轮把基线哈希放在内存的 `LiveSession` 上，于是它只对**本次运行里打开过**的
agent 存在——攒了十个角色的项目，刚打开应用时一个都不会亮，而那恰恰是最需要它
亮的时刻（离开的这段时间里改的条目，正是作者想知道的）。

基线因此移到 `RoleplayAgent.contextHash`（第八轮之前叫 `boundHash`，那时它只覆盖绑定
块，见 §2.16），跟着 `agents.json` 走。这不是把会话状态
硬塞进元数据：花名册里早就有 `turnCount`，同样是会话派生的事实缓存在这里，理由
也一样——**花名册要在不打开会话的前提下把它显示出来**。

三条随之确定的行为：

- **没有基线的 agent（还没开过口）不参与比对。** 它没有任何已经烘进上下文的旧
  内容，下一次发送就是新的；标成「已更新」是在报一件没发生的事。
- **「刷新绑定」在没有活历史时也要更新基线。** 否则下一轮比对又把它标成过期，
  那个按钮会变成点了没用的按钮。
- **改绑定之后不直接置 `stale = true`，而是重新比对一遍。** 判断留在唯一的一处，
  否则作者把绑定改回原样之后，那条提示会赖着不走。

没有加「先比索引里的元数据签名、不同再读文件」的快路：绑定通常是个位数条目、
agent 通常是个位数个，而比对只在知识库重扫之后跑一次。先加一层缓存，等于为一个
还没量到的问题增加一处会和真相不同步的状态。

## 2.7 记忆：两条落地时才定下来的事

- **记忆块「有」变「没有」时不删消息，改成一句「（暂时没有。）」。** 删一条
  prelude 消息会让历史的稳定前缀变短，等于白白作废一次 prompt 缓存，而它只是
  一行字。
- **作者手加的记录 `turn: 0`，模型记的带真实轮号。** 对话区的「记下了：…」按轮号
  挂在那条回复下面；`turn: 0` 因此永远不会冒出这句话——它的意思是「角色刚刚记住
  了」，而作者自己写的那条不需要被告知，它只活在记事本里。

刷新的四个时刻（播种 / 压缩之后 / 会话恢复 / 作者手动）按 02-design §5.5 实现，
其中「压缩之后」那一次挂在 `compactChatHistory` 返回之后、`set()` 之前。

## 2.8 信息带不能裁剪，重试不重发（第四轮补的）

作者报的两个问题，根子都在「这一轮已经做过一次的事」上。

**模型选择器的菜单被切成一条缝。** 信息带固定 46px 高，而第三轮为了不让它折成
两行，给 `.band` 加了 `overflow: hidden`——那同时把它自己的绝对定位子元素（模型
菜单）裁掉了。记事本拉开时还有第二道：`.bandNarrow .modelSlot` 上也有一个
`overflow: hidden`。

改法不是把菜单挪出去，而是**取消裁剪，让它本来就挤不满**：`.isolation`（那句只读
说明）先省略号、再在窄档 `display: none`，`.modelSlot` 常设 `flex-shrink: 1`（触发器
内部本来就有省略号）。460–900px 实测 `scrollWidth === clientWidth`，46px 单行不变。

> 教训：**一条带子里如果有绝对定位的弹层，就不能用 overflow 来防溢出**。防溢出
> 是「谁让位」的问题，该在子元素的收缩规则上解决。

**跑失败之后没有重试。** 补 `retry(agentId)`。关键是它**不重发作者轮**——作者轮在
`send()` 里就落盘了（不变量一），重试是接着那一问再跑一次模型。

难点是 `runJob` 会**就地** push 进 `session.history`，所以原样重排一次队会让同一句
话在上下文里出现两次。因此 `Job` 上加了 `committed`：置上的作业跳过整段组装
（压缩 / 逐轮注入 / push 提问），直接拿现有 history 开跑；置上的时机是**组装完成
之后、调模型之前**，所以在压缩或检索那一步炸掉的作业仍然会整套重来。

重试入口只挂在错误带上，含义是**这一轮压根没有回复**（网络断了、密钥不对、模型
返回错误）。有回复、只是不合意，不走这条路——那已经是 transcript 里的一轮，
transcript 只追加不改写。作者主动「停止」也没有这个入口：它不进错误带，而给中止
的那一轮补一个重试口子需要另一处界面，留给下一轮。

## 2.9 镜像层要跟着 textarea 滚（第五轮补的）

输入框超过可见行数（3 行）之后排版就乱了：带色的字停在原地，光标和真正的文本
各走各的。

两个原因叠在一起：

1. **`mirrorRef` 挂错了元素。** 它挂在外面那层没有样式的 wrapper 上，而会滚动的
   是 `.mirror` 自己（`position: absolute; inset: 0; overflow: hidden`）。wrapper
   的高度是 0、`overflow: visible`，给它设 `scrollTop` **静默无效**——浏览器不会
   报错，只是什么也不做。
2. **组字期间镜像层是卸载的。** 它让位给原生文本（否则作者对着一片透明打字），
   组完字重新挂上来时 `scrollTop` 归零，而这中间 textarea 早滚下去了。**中文
   输入法下每打一个词都会撞上这条**，所以只挂 `onScroll` 不够。

改法：ref 移到 `.mirror` 本身（`ComposerMirror` 收一个 `innerRef`），滚动同步抽成
`syncMirror()`，`onScroll` 和 `useLayoutEffect([draft, composing])` 各调一次。

实测两层度量完全一致（`clientHeight` 86 / `scrollHeight` 173 两边相同），且
`overflow: hidden` 的元素**可以**用 `scrollTop` 程序化滚动——这是这套方案成立的
前提，值得记一笔。

> 教训：**盖一层镜像做实时着色，就要把 textarea 的每一种位移都照抄过去**——滚动
> 是一种，卸载重挂是另一种。度量对齐只保证静止时对得上。

## 2.10 从 transcript 重建：第一轮只做了一半（第六轮补的）

作者删掉 `session.json` 之后继续聊，角色说它不知道之前的进度。

**症状是「稿面完好、模型失忆」**，这是最难自查的一种坏法：显示层的对话派生自
`transcript.md`，所以满屏记录一个字都不少，看上去完全正常；而
`seedRoleplayHistory` 只接一个 `firstMessage`，**从不回放过往轮次**，模型拿到的是
一段全新的历史。

设计（02-design §11）写的是「反序列化失败 = 从 transcript + memory.md 重建」，
而实现里只有 memory.md 那一半成立——记忆是每次播种都从盘上重读的，所以约定和
待办确实活了下来，这恰恰让故障更不明显。第一轮的实现记录把整条标成了「已实现」，
是一次**没有测试守着的文档断言**。

改法：`seedRoleplayHistory` 收 `priorTurns` 和 `priorSummary`，播种时回放。两条
约束写在 `selectReplayTurns` 里：

- **切片必须从作者轮开始**。轮的边界由 `noteTurnStart` 标在作者的提问上；若切片以
  角色轮打头，那条 assistant 消息会落在 prelude 里（第一个 turnStart 之前），
  压缩永远够不着它，它会一直占着上下文直到会话结束。
- **按字符封顶（`RESTORE_REPLAY_CHAR_CAP = 12000`），取最近的**。回放走的是**播种**
  那条路，而播种不经过压缩——几万字原样灌进去会当场撑爆首次调用。更早的事由
  `summary.md` 和 `memory.md` 承担，那正是它们存在的理由。

`summary.md` 一并接回来，`meta.summary` / `meta.summaryText` 都补上，位置与
`buildCompactedHistory` 摆放摘要的位置一致（prelude 末尾、turns 之前），下一次压缩
不用挪它。

> 教训：**「A 丢了就从 B 重建」这类断言，验证时必须验到模型那一层**。给作者的验证
> 清单写的是「对话是否仍在」——他看到对话仍在，答了「正常」，而两个人验的是同一句话
> 的两个不同意思。要问的应该是「角色还记不记得之前说好的事」。`context.test.ts` 现在
> 有 8 条守着这一组。

## 2.11 新开会话（第六轮补的）

在此之前，「这一场我想重来」的唯一办法是**删掉 agent 重建**——配置、绑定、人设卡、
记忆一起烧掉。不合理。

`newSession(agentId, { clearMemory })`：

- **封存靠 `rename`，不靠改写。** transcript 是只追加、永不改写的资产（不变量一）；
  移动一个文件不违反它，就地清空则会。`transcript.md` → `archive/transcript-NN.md`，
  `summary.md` 同理。
- **编号按已有文件名解析出的最大值 + 1，不按文件个数。** 作者手动删掉中间一场之后，
  按个数会撞名，直接覆盖掉另一场的记录。
- **`session.json` 直接删。** 它按定义就是缓存，而且封存它毫无意义——一段接不回任何
  transcript 的 wire history 谁也读不懂。
- **记忆默认不动**，作者在确认条上勾选才一并封存。这一条是有意的：记忆是角色的长期
  知识，本就设计成能跨越压缩活下来；换一场戏不该让角色忘掉你们约好的事。「推倒重来」
  是另一种意图，所以给一个勾选项，而不是替作者选。
- **跑着的时候拒绝执行**，否则正在写的那一轮会追加到一个已经被移走的文件上。
- `contextHash` 一并清空——它是「绑定内容已更新」的基线，新的一场还没播种过，没有基线可比；
  留着旧的会让提示按上一场的状态亮（`checkBindings` 跳过 `contextHash === null` 的 agent，
  所以清空是安全的）。

**入口在编辑抽屉的 footer**，两段式：点「新开会话」footer 就地换成确认条（勾选项 +
一句说明 + 取消/确认）。没有弹模态——一个只有一句话加一个勾的模态，比它要确认的动作
本身还重。

### 存档是只读的，而且旁白也看不见

`ArchiveViewer`（稿面顶部的「此前已封存 N 场」进入）能读，不能续。能继续的会话只有
一个，这就是「存档」这个词的全部含义。

旁白的 scene 工具**只读当前 transcript**，读不到 archive。这是这一轮的取舍而不是遗漏：
`list_scenes` 现在返回「每个 agent 一场」，把存档并进去就得回答「第 3 场是谁的第 3 场」——
那是「场」数据模型的问题（见 §3 的场次分隔线一条），不该在这里顺手定一个。作者要让
旁白读旧场次，目前的办法是把那段文字贴给它。

## 2.12 关掉面板不该打断运行（第六轮补的）

作者报的：关掉 AI 抽屉再打开，正在生成的那一轮就断了；对话助手没有这个毛病。

根因在 `load()` 的第一行——它无条件 `set({ sessions: {}, running: [], queue: [], aborts: {} })`。
而 `load` 挂在 `RoleplayPanel` 的 mount effect 上，抽屉一关整棵子树就卸载
（`AiDrawer` 是条件渲染 + `AnimatePresence`），再打开就重跑一次。

于是：正在生成的那一轮**并没有真的停下**（没有人调 `abort`），只是界面不再认识
它——`running` 空了所以不显示「生成中」，`aborts` 空了所以连「停止」都够不到它的
controller。对话助手没事，是因为 `agentStore` 不在挂载时重置。

改法两条：

- **同一个项目已经装好了就直接返回**。`load` 变成幂等的，重新挂载是无操作。
- **换项目时先 `abort()` 再清**。原来直接丢掉 `aborts` 表，等于把在跑的运行变成
  谁也停不了、还在往旧项目里写的孤儿。`reset()` 同理。

> 教训：**挂在 mount effect 上的 `load` 必须幂等**，因为「组件卸载」和「数据失效」
> 是两件事。把运行态和加载态放在同一个 store 里，就得由 `load` 自己分清哪些字段
> 属于「这个项目的数据」、哪些属于「此刻正在发生的事」。

## 2.13 回退到某一轮（第六轮补的）

作者要的：回到历史上某一句，改了重发。

撤销的东西分四份，每份的理由不同：

| 撤销什么 | 怎么做 | 为什么 |
|---|---|---|
| transcript | 备份后截到那一轮之前 | 这是唯一重写这个文件的地方。只追加那条纪律防的是**悄悄丢字**——模型跑飞、程序出错、并发写坏；而回退是作者指名道姓要撤销哪一轮。仍然先 `backupFile`，因为「作者按了」不等于「作者按对了」。 |
| wire history + `session.json` | 整个丢掉 | 不做外科手术式的回卷：`meta` 里挂着轮起点、注入账本、摘要，一条条往回拆很难拆对。下一次发送本来就会从截断后的 transcript 重新播种（§2.10）——**这个功能几乎是那次修复的免费副产品**。 |
| 记忆中 `turn >= N` 的记录 | 备份后删掉 | 一条诞生于已被撤销的对话的约定，留着会让角色言之凿凿地提起一件没发生过的事，比丢掉它更糟。`turn: 0`（作者自己写的）永不触碰。 |
| `summary.md` | 备份后清掉 | 滚动摘要是散文，没法按轮号截断，而它很可能已经把被撤销的那几轮写了进去。**一份悄悄断言了不存在的事的摘要，正是这个功能要消除的东西。** 代价是长对话的远期上下文，换回来的是它不会撒谎。 |

**不撤销的**：某条旧记录在被撤销的那几轮里被标成 `done`，不会翻回 `open`——那要给
每条记录存一份状态变更史，而回退是低频动作，代价不成比例。`next` 也不回退，id 只增
不重用。

入口是作者轮名标行上悬停才出现的「回到这里重说」（撤销动作不该在稿面上一直举着
手）。最后一轮不给这个入口，回到最后一轮等于什么也没撤销。

### 确认条长在被选中的那一句下面（第八轮改的）

第一版把确认条放在稿面**底部**，和错误带、停止带同一套视觉——理由是它们扮演同一
个角色：一件需要作者当场处理的事。**这个类比是错的。** 错误带说的是「刚刚这一轮」，
它天然就在底部；而回退问的是「你点的**那一句**」，那一句可能在几屏之上。作者点完
按钮，页面上什么也没变——问题问了，没人看见。

现在确认条渲染在被选中的那一轮**里面**（`TurnBlock` 的 `confirm` 插槽），因此也不
再自带左规和缩进：那一句的左规就是它的左规。同时，**它之后的每一轮调淡到 0.34**
（`.turnDoomed`）——「和它之后的 N 条」是一个数字，调淡是那个数字在稿面上的样子，
作者在确认之前就能看见自己要丢掉什么。被选中的那一句本身不调淡，它承载着问题。

两条附带的：确认打开期间**其他轮的「回到这里重说」不出现**（同时举着两个撤销入口
只会让人点错）；确认条挂载时 `scrollIntoView({ block: "nearest" })`——作者点的那一
句可能正贴着可视区下沿，`nearest` 只在真的看不见时才滚。

`transcript.test.ts` 里最要紧的一条是**往返**：截断后重写的文件必须能被
`parseTranscript` 读回同样的轮次。这条路径上一旦出错，作者丢的是已经写下的字。

## 2.14 两个模型选择器，谁管谁（第七轮补的）

作者问的：抽屉左上有一个模型选择器，对话标题栏也有一个，哪个优先？

**答案：标题栏那个（每个 agent 自己的）优先。** 解析链只有两级：

```
agent.modelId ?? 全局 activeModelId
```

创建时绑的和标题栏里选的**是同一个字段**——`setAgentModel` 直接写 `agent.modelId`
并立刻存进 `agents.json`。所以不存在"优先级"，后改的覆盖先改的，永久生效。

会问出这个问题，说明界面没把它讲清楚。三处都改了：

1. **标题栏的选择器加前缀「本角色」。** 它和抽屉头部那个长得一模一样，改的却是
   两个作用域完全不同的东西（一个全局默认、一个永久重绑这个 agent）。同形不同义，
   标签是唯一能当场分清它们的东西。
2. **没绑模型时不再显示空态。** 原来 `value=undefined` 在受控模式下算"未选中"，
   于是显示「选择模型」+ 灰点——**界面说没有，实际有**，跑起来用的正是全局模型。
   现在显示全局那一个 + 一个虚线的「跟随全局」签：它是借来的，不是绑定的。
3. **菜单脚注给出回头路。** 原来一旦在标题栏点过一次就再也回不到"跟随全局"，
   那个按钮只在编辑抽屉里。现在撤销绑定的入口就在改绑定的地方。编辑抽屉里那个
   独立的「跟随全局」链接跟着删掉了——一件事一个入口。

新增的两个 `ModelSelector` 属性（`prefix` / `onFollowGlobal`）是可选的，lore 的六个
模态不受影响：它们的 `value` 初始就取全局、改动不写回，脚注仍是那句静态的
「默认跟随全局设置」。

### 顺带修的一个老问题

`.trigger` 里的上下文徽标和「跟随全局」签都是 `flex-shrink: 0`，被挤窄时会**顶出
按钮的边界压在邻居身上**——信息带里它右边紧挨着「记事本」，实测能压过去 113px。
给 `.trigger` 加 `overflow: hidden` 裁掉即可；弹层是这个按钮的**兄弟**节点（同在
`.root` 下），裁不到它。1100/900/700/620/560 五档实测：带子零溢出、与「记事本」
恒留 14px 间距、触发器从 351px 平滑收到 102px。

## 2.15 补齐与对话助手的差距（第七轮）

作者要求把「小补丁 / 对话助手有的 / 设计稿剩的」三批一起做掉。逐条的取舍：

**按停之后能重试。** 停止和报错不是同一件事（一个是「出了问题」、一个是「我不想要
这一条」），但后果一样：这一问已经在 transcript 里却没有回复。所以两边通向同一个
`retry`，只是稿面上给一行比错误带更轻的提示——作者自己按的停止不该留下一道警示。

**`RoleplayAgent.taskId` 是死字段，删了。** 类型上有，从来没有人写回去，于是每次
重启都在 `.ai-writer/tasks/` 里新建一个再也没人认领的目录。改成 `LiveSession.taskId`，
`select` 时从 `session.json` 的快照恢复。**存在会话上而不是 agent 上**是有意的：工作区
跟着「这一场」走，「新开会话」就该换一个，而 `emptySession()` 的 `taskId: null` 正好
就是这个语义。

**「我此刻是谁」可以只对一个角色覆盖。** 菜单顶部先选**作用域**再选人，而不是让两级
挤在一张列表里：「这一次改的是谁」必须在按下之前就知道，事后从高亮上反推太晚了。
撤销覆盖的入口在做出覆盖的地方，和模型选择器那条（§2.14）同一个道理。

**图片附件按 agent 绑的模型判定，不是全局那个。** `allowImages` 现在读
`agent.modelId ?? 全局` 解析出的模型是否多模态——和 `runJob` 里那一句必须是同一句话。
候选里也只在这条链看得见图片时才放图片进去：挂一个模型物理上读不到的附件，作者只会
看见一个芯片，然后角色像什么都没有一样回答。超限在**选中的那一刻**就拒绝，不留到
发送时——那时作者早忘了自己挑过什么。

**子代理开关存在会话上，不共用 agentStore 的。** 对话助手和三个并发的扮演 agent 是
四段互不相干的对话，共用一份「本次关掉了什么」等于互相改设置。`SubAgentChips` 因此
加了两个可选属性把状态交给调用方；不传时行为完全不变。

**`ContextBar` 抽成独立组件，但样式仍借 `AgentChat.module.css`。** 把 `ctx*` 那十几条
规则搬家只会给一个正在用的界面凭空加一次回归风险，而借用同一份 CSS module 在这个仓库
里有先例（`LoreImproveModal.module.css` 被四个模态借着用）。**改 `ctx*` 类名前先看谁在
import 它。** 配套加了 `LiveSession.contextVersion`：`history` 是就地 push 的，引用从头到
尾不变，没有这个计数器构成条永远不会重算。

**选区默认带上，发完就摘掉。** 有选区几乎总意味着「我说的是这一段」；但同一段选区跟着
后面每一条消息一路走下去，是在替作者做一个他只做过一次的决定。

**窄面板的头像轨用容器查询，不用媒体查询。** 该让位的是**这个面板**挤不挤得下，不是
窗口有多宽——抽屉宽度将来一改，绑在 `vw` 上的断点就悄悄错了。名字退进 `title`，否则
收起来之后完全认不出谁是谁。

**分类 chips 读 `indexCategories(loreIndex)`**，不是写死的六个：能力包关掉之后的孤儿
分类也按它自己的规矩显示。只列真的有条目的分类（空分类的 chip 点下去只会得到一张空
列表），且只在两类以上时出现（一个项目只有「人物」时，一排唯一的 chip 是纯装饰还占掉
一行）。

**仍然不做「执行日志摘要行」**，理由没变：它要的字段散在三处，而 `AgentLog` 已经把它们
都渲染好了，为一行摘要再拼一遍是重复实现。

## 2.16 system 层不是只播种一次的（第八轮修的）

第八轮是一次审查，抓到的三件事根子上是同一件：**`buildSystemPrompt` 只在播种那一刻
跑过一次，`history[0]` 此后再没被重写过。** 于是这三个作者动作全部静默失效——

| 作者做了什么 | UI 的反馈 | 模型实际看到的 |
|---|---|---|
| 换「我此刻是」 | chip 变了，之后的署名也变了 | 旧身份 |
| 改主角条目 `index.md` | 什么都没有 | 旧正文 |
| 改「作者给你的指令」（`updateAgent`） | 已落盘 | 旧指令 |

这是最难自查的一类坏法：**操作看起来生效了**。前两种尤其常见——边聊边调人设本来就是
这个功能的用法。而且「刷新绑定」按钮也救不了，它当时只重写绑定块。

修法是三处，缺一不可：

- **`refreshSystemPrompt`（`lib/roleplay/context`）就地改 `history[0].content`。** 和
  `refreshBoundBlock` 同一条纪律：不换消息对象。但它**不需要**像绑定块那样在 meta 里
  被持有——system 恒在 0 位，`buildCompactedHistory` 按对象身份把 prelude 搬进新数组、
  `trimHistory` 不动普通消息、`repairToolCallPairing` 只 splice 配不上对的 tool 消息。
  所以 `session.json` 的格式一个字都不用改。这条性质由 `lib/agent/compact` 决定而不由
  这里决定，所以 `context.test.ts` 跑一次真实压缩守着它。
- **基线从 `boundHash` 扩成 `contextHash`**（`contextSignature`）。原来只覆盖绑定块，
  于是上表后两行连提示都不会亮。现在覆盖 system 层的全部作者可改输入：角色名、绑定
  正文、扮演指令、主角条目正文、作者身份（`lore` 模式连条目的名字和摘要一起算——
  system 行里写的就是这两样）。旁白跳过身份和主角正文：它的提示词根本不读这两样。
- **`setAuthorPersona` / `setAgentPersona` 之后跑一次 `checkBindings`。** 换身份和改
  条目是同一件事。

两个刻意的选择：

- **取输入算哈希，不取 `buildSystemPrompt` 的产物。** 产物里含 i18n 文案，切一次界面
  语言会把整个花名册标成「绑定内容已更新」，而那不是作者改的东西。
- **不自动重写 system，只亮提示。** 重写会作废这个 agent 的 prompt 缓存前缀，所以它
  必须是作者的显式动作——和 §2.6 里「刷新绑定」的理由完全一样。

`agents.json` 里的旧 `boundHash` **读进来当 `contextHash` 用**，不是丢掉。丢掉就是基线
归 null，而对一个已经有活 `session.json` 的 agent 来说，基线只在重新播种时才会重建
（`checkBindings` 跳过 `contextHash === null`）——它会安静地再也不亮提示。迁过来的旧值
算法不同、必然对不上，于是升级后每个 agent 会亮一次「绑定内容已更新」，点一下就回到正轨。
一次可解释的误报，好过一个永远不响的提示。

## 2.17 `search_text` 是个死胡同（第八轮修的）

同一次审查的第二件事。扮演 preset 里的 `search_text`，理由写在 02-design §6：「你还
记得我们在雪原上说的话吗」这类问题需要检索。需求是真的，工具是错的，而且错了两层：

1. 它扫的是**工作区里的稿件**并排除 `.ai-writer/`，而 transcript 就住在那底下——它
   一辈子搜不到那句话。它实际能给的只有作者的稿子，也就是同一节上一条刚说过不该给
   的东西。
2. 它的结果是「路径:行号」，工具描述明写着接着去 `read_file`，而扮演 preset 故意没有
   `read_file`（`presets.test.ts` 还专门断言了这一点）。模型只能去调一个不存在的工具。

换成 `search_conversation` / `read_conversation`（`lib/roleplay/conversationTools`），
作用域由 `ToolContext.conversation` 绑死：**没有 agent id 参数**，所以它只够得到本次
运行那个 agent 的 transcript，不变量三仍然是结构性的。渲染不和 `sceneTools` 共用——
那边的说话人标签和「先读摘要再读原文」的引导是写给旁白的，这边是写给一个正在戏里的
角色，参数化只会让每次改动都要先想清楚「这句话是对谁说的」。

**只给扮演，不给旁白**：旁白已经有 `search_scenes`（读别人的），再摆一个名字相近、
作用域相反的工具，换来的是它每一轮都要先分清该调哪个。它自己那一场读不回来是个真实
的小缺口，但代价比收益大。

这一条也留下一个可复用的判断：**一个检索工具的结果必须指向一个这个 preset 真的有、
且真的能读到那个东西的读工具。** 上一版两条都不满足，却在 preset 里躺了很久——因为
「模型调了一个不存在的工具」只表现为「这一轮它说了句奇怪的话」。

## 2.18 自定义身份补上了入口（第八轮）

`AuthorPersona` 的 `mode: "prompt"` 从第一轮起类型、解析（`store.ts` 的
`coercePersona`）、system 行（`personaLine`）、显示名（「自定义身份」）就全都在，唯独
菜单里没有产生它的地方——全仓库没有一处写出过 `mode: "prompt"`。补的是 `PersonaChip`
里的一个表单：点「自定义身份」把菜单整个换成输入框，**写完确认才生效**，不逐字生效
（身份进的是 system 层，每次改动都会亮一次「绑定内容已更新」，逐字生效会让那条提示闪个
不停）。

保留而不是删掉，是因为它是三种模式里唯一能表达「我是知识库里还没有的人」的那一种，
而试写和跑团里作者常常正是那个人。

## 9. 第九轮（第二次审查）：记忆生命周期的三处塌方与一批数据完整性修复

这一轮是一次全量代码审查的产物。三个高严重度问题共享同一个根因——**块的
「存在性」没有被当成受管理的状态**——外加一批各自独立的数据完整性修复。

### 9.1 块恒存在（对不变量二/四的收紧）

原实现「有内容才建块」：播种时零记忆就不建记忆块、零绑定就不建绑定块。这让
「无→有」成为一个到处接不住的状态迁移：

- **零记忆开场的新角色**（最常见的情形），首场戏里 `remember` 的东西在第一次
  压缩把工具结果折叠掉之后，`refreshMemoryBlock` 面对不存在的块只能沉默——
  记忆从上下文里永远消失，与工具告诉模型的 "This survives context compaction"
  直接矛盾。
- 播种时没有绑定的 agent，作者中途加绑定点「刷新绑定」：基线更新了、提示灭了、
  块却没插进去——**操作看起来生效了，其实没有**（§2.16 警告过的同一类坏法）。

现在 `seedRoleplayHistory` **无条件**创建两个块，空时只是一行占位（
`roleplay.section.memoryNone` / `boundNone`）。所有刷新路径天然闭合，prelude
的稳定前缀长度也不再随内容有无而变。

### 9.2 memoryBlock 的身份要过序列化这一关

`serializeChatSession` 只认 `ChatSessionMeta` 的字段；Roleplay 扩展的两个块
引用一概不存。boundBlock 靠 `SerializedSession` 单独存下标救了回来，
memoryBlock 没有——于是**重启一次，记忆块就永久失联**：`select()` 恢复出的
meta 里它是 undefined，四个刷新时刻里除播种外全部静默 no-op，历史里那条
【记忆】消息内容冻结在上次存盘时刻。

修法照抄 boundBlock：`SerializedSession.memoryBlock` 存下标（加法字段），
`select()` 两个都重连。对本版本之前播种的残缺历史，恢复和「刷新绑定」入口
先过 `ensureBlocks`（context.ts）补块——历史里如果还留着旧块消息，会多出一条
几十字的惰性消息，代价有界且只发生一次，换取不用按 i18n 文案去历史里猜。

### 9.3 转场沉降是「移出」，不是「标 void 留档」

06 §3.1 的原文是「移出常驻层」，实现写成了标 `void` 留在 memory.md——而分拣
过滤器对 `void` 记录**永远命中**，于是每转一场，全部历史 event/note/done/void
记录都被再灌进记忆区一遍，条目随转场次数平方级膨胀。

现在分拣是 `memory.ts` 的纯函数 `takeSinkable`（幂等有测试钉着），沉降的记录
在全部写进记忆区之后从 doc 移除——中途失败最多把已沉的重复一次，绝不丢。
「只增改不删」防的是模型删自己不想要的记录；转场分拣和回退（`dropRecordsFrom`）
一样是作者按下的动作。`next` 计数器照旧不回退。

### 9.4 播种轮也要想起旧事

记忆区检索原来只活在 runJob 的续跑分支里，播种那条路（新开会话、以及每次
重启后的重播种）的第一问永远想不起任何旧事——而转场后的第一句恰恰最需要。
现在两条路共用 `injectAreaRecall`；播种且无回放时载体会落进 prelude（永不
折叠、账本永不过期），所以那种情况下它被标成自己的轮起点——`segmentHistory`
按 Set 判断轮起点，不看 `turnStarts` 的数组顺序，这一手是安全的。

### 9.5 数据完整性小修（各自带测试）

| 修的 | 曾经的坏法 |

| `loadRoster` 的死分支 | 「JSON 合法但条目全坏」返回空花名册，docstring 承诺的目录重建从未发生 |

## 11. 第十一轮：图例可以点了

**问题**：书写约定是四种标记，而作者的原话是「感觉输入好麻烦」——`「」` 在中文
输入法下不是一个键，`*…*` 要打两次，元指令的方括号要切半角。输入框上方那条图例
一直只是**说明文字**：它把四种写法摆在离输入框最近的地方，却什么也不做。

**做法**：图例的四项都变成按钮，点一下＝把**光标所在的那一行**改成那一类
（`markup.applyLineKind`，纯函数，`markup.test.ts` 里 6 个用例）。收起态的一行和
展开的卡片共用同一份 `SYNTAX_ITEMS`。

三个不显然的决定：

- **作用于整行，不是「在光标处插一对符号」。** 标记是行级的（`classifySegment`
  按整行判定），所以插在行中间的一对符号产出的是 `他说*笑了笑*然后…`——整行仍然
  是场景，**看着像生效了，其实没有**。作用于整行则永远产出一个合法的行。
- **先脱掉已有标记再套新的。** 点「台词」在一行动作上得到的是那句话变成台词，
  而不是 `「*他没有回头。*」`。于是「裸文本」那一项也有了确切的动作：它是这条
  路径上只脱不套的那一支，即**取消标记**——原先它是图例里唯一没东西可点的一项。
- **写回的引号固定是 `「」`。** 解析认四种引号，写只能选一种，选稿面上的正解那
  种；`quoteNote` 那行照旧告诉作者 `“”` 更好打。

走的是和 `openMentionFor`（`+ 条目` 按钮）同一条路：`setDraft` + `mention.sync` +
`setSelectionRange`。镜像层、提名状态、光标由同一次编辑一起更新，「点出来的」和
「手打的」不会分岔成两套行为。

**没做**：多行选区批量改类型（选区跨行时仍只作用于光标那一行）、以及给这四项配
快捷键。前者没遇到过，后者要先想清楚和 `Enter` 发送、`@` 提名的键位怎么共存。

# 实现记录（设计稿 08 TURN 1 + 角色记忆）

> 对应 UI 设计稿 `08 扮演 Roleplay.dc.html`（claude.ai/design 项目
> `17a6a5ce-f60e-4996-8f94-5948958206d0`）的 1a–1i 九屏。
> 计划见 [03-plan.md](03-plan.md)——这一轮一次做完了原计划的 PR1 / PR2 / PR4 / PR5，
> **PR3（角色记忆）没做**，理由见 §1。

## 1. 这一轮做了什么、没做什么

**做了**：Beta 开关、`.ai-writer/roleplay/` 存储、花名册、扮演对话（播种 / 逐轮注入 /
流式 / transcript 落盘 / 会话恢复）、混合文本排版、并发闸（3 个 + FIFO 队列）、
per-agent 模型、`@` 引用、旁白 agent + 四个 scene 工具、新建/编辑抽屉、空态、
绑定失效与「设定已更新」、窄窗口的 tab 分档。

**第二轮补的**：卡片按界面路由（见 §2.5）、旁白的轮数上限卡。

**第三轮补的**：「设定已更新」的基线进花名册（见 §2.6）。

**第四轮补的：角色记忆。** `memory.md`、三个工具（`remember` / `revise_memory` /
`recall`）、旁白的 `read_scene_memory`、记事本面板、对话区的「记下了：…」痕迹。
播种出来的历史因此变成 `[system, 绑定块, 记忆块, seed 块, 提问]`——记忆块和绑定块
一样是 prelude 里的独立消息，同样不进 `meta.seedContext`，因此同样免疫压缩。

设计稿 TURN 1 没有画记事本面板，所以那一屏的判断是自己做的，理由写在
`components/roleplay/MemoryPanel.tsx` 的开头：**可收起的第三栏，但入口带计数**。
稿面固定 640px 是这个面板不肯让步的一条，一栏常驻的记事本会把它压到 640 以下；
而计数常驻在信息带上，是因为记事本不是配置，是作品的一部分——作者应当一眼看到
「这个角色还欠着三件事」。

## 2. 与 02-design 的差异（都是实现时才看清的）

| 差异 | 为什么 |
|---|---|
| `session.json` 里 `turns` 存空数组 | 显示用的对话从 `transcript.md` 派生。少存一份就少一份要保持一致的东西——这正是不变量一想要的：session.json 丢了只损失模型脑子里的细节，一个字的对话都不少。**反序列化失败就从 transcript 重新播种**——第一轮只做了显示层，wire 层第六轮才补上（§2.10）。 |
| 摘要在**压缩发生时**顺手落盘 | `compactChatHistory` 本来就在生成那段文字，再单独跑一遍摘要是白花钱。旁白的 `read_scene_summary` 读的就是它；还没触发过压缩的短会话没有摘要，工具会如实说「太短，直接 read_scene」。 |
| 输入框的实时着色**只换颜色** | 设计稿 1c 给四种标记配了字号（16/18/15/12）和斜体，那是**稿面**的排版。输入框是 textarea 上盖一层镜像 div，字号、字重、字形任何一项不同，光标就会和字错开。颜色足以传达「标记生效了」，而它是唯一能精确对齐的维度。 |
| 组字期间镜像层让位 | textarea 的文字默认透明（可见的是底下带色的镜像）。中文输入法的候选文字如果落在透明层上，作者看不见自己在打什么——`compositionstart` 时换回不透明，`compositionend` 时换回来，也正好落在设计稿说的「闭合的那一刻做 160ms 颜色过渡」。 |
| 每个 agent 懒创建一个标准 task workspace | `routeTools` 的两条规则会互咬：vision 子代理可用时剥掉 `read_image`，而 `delegate` 只在有 workspace 时才追加。没有 workspace 的 agent 一开 vision 就**既不能自己看图、也不能委派**。代价是任务列表里会出现扮演产生的条目，可接受——资产是 transcript，不在 `tasks/` 下。 |
| 「设定已更新」的触发信号是 lore index 的**对象身份** | 起初用条目总数，但改一段特征不会改变条目数——最常见的一种「设定变了」恰好是计数看不见的那一种。 |
| 自动批准的 key 是本次运行的 `AbortController` | `CHAT_AUTO_APPROVE_KEY` 是对话助手专用的字面量；几个 roleplay agent 共用一个字面量会让 A 的「本次都批准」悄悄覆盖到 B。用对象身份，`autoApproveScope()` 自动把它判成 run 级。 |
| 「把对话写进正文」没有新工具 | 旁白读完场景后自己改写成散文，再走现成的 `create_chapter` / `append_file` / `propose_edit`。新建一个 `compose_from_scene` 只会重复实现审批卡、备份和占位符校验。 |

## 2.5 卡片路由（第二轮补的）

第一轮漏了一件事：**被阻塞的卡片没有归属**。`agentStore` 的四个队列（审批 /
方案 / 轮数上限 / 截断）一直是被对话助手和任务面板**整个**渲染出来的——在扮演
出现之前这没问题，同一时间通常只有一个界面在跑。扮演打破了这个假设：它能同时
跑三个 agent，每个都可能提出自己的改稿请求。不区分的后果不是难看，是**卡片
出现在另一个 tab 里**：作者看到旁白停住不动，而唯一能解开它的按钮在他没打开的
那一页上——旁白最重要的那条能力（把互动写进正文）因此实际走不通。

规则落在 `lib/agent/approvalRouting.ts`，只有一条，故意做成加法：

- **没有 `surface` 的卡片**属于默认界面（对话助手 + 任务面板），行为与从前完全
  一致，所以没有任何既有路径会因为这次改动突然把卡片藏起来。
- **带 `surface` 的卡片**只由同名界面渲染。今天唯一打标的是扮演面板，用 agentId
  打标，于是三个并发的 agent 各看各的。

**默认必须是「显示」而不是「过滤」**：在这里「藏起来」等于「那次运行永久挂起」。

配套的两处：

- **轮数上限 / 截断卡只接给旁白。** 扮演 agent 的 `maxRounds: 4` 是刻意的小，撞到
  说明模型在做错的事，force-text 收尾正是想要的降级——弹一张「要不要再给四轮」
  只会训练作者为一个本就不该需要轮数的模式一再放行，顺带把一场戏切断。旁白不同：
  `maxRounds: 20`，读几场戏再改写成正文完全可能撞上，撞上就直接收尾等于半途而废。
  **存盘暂停不给**（`canPause: false`）——扮演这边没有恢复已暂停任务的入口，给了
  就是一个存进去再也拿不出来的按钮。
- **`stop()` 要主动排空本次运行的队列。** 中止信号解不开一张正阻塞着的卡片：
  `onRoundLimit` 等的是一个 Promise，而 abort 不会让它 reject。`stopChat` 早就
  这么做了，扮演这边第一轮漏了——没有它，「停止」按下去 agent 会永远卡在那张卡上。

## 2.6 「设定已更新」的基线存在花名册里（第三轮补的）

第一轮把基线哈希放在内存的 `LiveSession` 上，于是它只对**本次运行里打开过**的
agent 存在——攒了十个角色的项目，刚打开应用时一个都不会亮，而那恰恰是最需要它
亮的时刻（离开的这段时间里改的设定，正是作者想知道的）。

基线因此移到 `RoleplayAgent.boundHash`，跟着 `agents.json` 走。这不是把会话状态
硬塞进元数据：花名册里早就有 `turnCount`，同样是会话派生的事实缓存在这里，理由
也一样——**花名册要在不打开会话的前提下把它显示出来**。

三条随之确定的行为：

- **没有基线的 agent（还没开过口）不参与比对。** 它没有任何已经烘进上下文的旧
  内容，下一次发送就是新的；标成「已更新」是在报一件没发生的事。
- **「刷新设定」在没有活历史时也要更新基线。** 否则下一轮比对又把它标成过期，
  那个按钮会变成点了没用的按钮。
- **改绑定之后不直接置 `stale = true`，而是重新比对一遍。** 判断留在唯一的一处，
  否则作者把绑定改回原样之后，那条提示会赖着不走。

没有加「先比索引里的元数据签名、不同再读文件」的快路：绑定通常是个位数条目、
agent 通常是个位数个，而比对只在知识库重扫之后跑一次。先加一层缓存，等于为一个
还没量到的问题增加一处会和真相不同步的状态。

## 2.7 记忆：两条落地时才定下来的事

- **记忆块「有」变「没有」时不删消息，改成一句「（暂时没有。）」。** 删一条
  prelude 消息会让历史的稳定前缀变短，等于白白作废一次 prompt 缓存，而它只是
  一行字。
- **作者手加的记录 `turn: 0`，模型记的带真实轮号。** 对话区的「记下了：…」按轮号
  挂在那条回复下面；`turn: 0` 因此永远不会冒出这句话——它的意思是「角色刚刚记住
  了」，而作者自己写的那条不需要被告知，它只活在记事本里。

刷新的四个时刻（播种 / 压缩之后 / 会话恢复 / 作者手动）按 02-design §5.5 实现，
其中「压缩之后」那一次挂在 `compactChatHistory` 返回之后、`set()` 之前。

## 2.8 信息带不能裁剪，重试不重发（第四轮补的）

作者报的两个问题，根子都在「这一轮已经做过一次的事」上。

**模型选择器的菜单被切成一条缝。** 信息带固定 46px 高，而第三轮为了不让它折成
两行，给 `.band` 加了 `overflow: hidden`——那同时把它自己的绝对定位子元素（模型
菜单）裁掉了。记事本拉开时还有第二道：`.bandNarrow .modelSlot` 上也有一个
`overflow: hidden`。

改法不是把菜单挪出去，而是**取消裁剪，让它本来就挤不满**：`.isolation`（那句只读
说明）先省略号、再在窄档 `display: none`，`.modelSlot` 常设 `flex-shrink: 1`（触发器
内部本来就有省略号）。460–900px 实测 `scrollWidth === clientWidth`，46px 单行不变。

> 教训：**一条带子里如果有绝对定位的弹层，就不能用 overflow 来防溢出**。防溢出
> 是「谁让位」的问题，该在子元素的收缩规则上解决。

**跑失败之后没有重试。** 补 `retry(agentId)`。关键是它**不重发作者轮**——作者轮在
`send()` 里就落盘了（不变量一），重试是接着那一问再跑一次模型。

难点是 `runJob` 会**就地** push 进 `session.history`，所以原样重排一次队会让同一句
话在上下文里出现两次。因此 `Job` 上加了 `committed`：置上的作业跳过整段组装
（压缩 / 逐轮注入 / push 提问），直接拿现有 history 开跑；置上的时机是**组装完成
之后、调模型之前**，所以在压缩或检索那一步炸掉的作业仍然会整套重来。

重试入口只挂在错误带上，含义是**这一轮压根没有回复**（网络断了、密钥不对、模型
返回错误）。有回复、只是不合意，不走这条路——那已经是 transcript 里的一轮，
transcript 只追加不改写。作者主动「停止」也没有这个入口：它不进错误带，而给中止
的那一轮补一个重试口子需要另一处界面，留给下一轮。

## 2.9 镜像层要跟着 textarea 滚（第五轮补的）

输入框超过可见行数（3 行）之后排版就乱了：带色的字停在原地，光标和真正的文本
各走各的。

两个原因叠在一起：

1. **`mirrorRef` 挂错了元素。** 它挂在外面那层没有样式的 wrapper 上，而会滚动的
   是 `.mirror` 自己（`position: absolute; inset: 0; overflow: hidden`）。wrapper
   的高度是 0、`overflow: visible`，给它设 `scrollTop` **静默无效**——浏览器不会
   报错，只是什么也不做。
2. **组字期间镜像层是卸载的。** 它让位给原生文本（否则作者对着一片透明打字），
   组完字重新挂上来时 `scrollTop` 归零，而这中间 textarea 早滚下去了。**中文
   输入法下每打一个词都会撞上这条**，所以只挂 `onScroll` 不够。

改法：ref 移到 `.mirror` 本身（`ComposerMirror` 收一个 `innerRef`），滚动同步抽成
`syncMirror()`，`onScroll` 和 `useLayoutEffect([draft, composing])` 各调一次。

实测两层度量完全一致（`clientHeight` 86 / `scrollHeight` 173 两边相同），且
`overflow: hidden` 的元素**可以**用 `scrollTop` 程序化滚动——这是这套方案成立的
前提，值得记一笔。

> 教训：**盖一层镜像做实时着色，就要把 textarea 的每一种位移都照抄过去**——滚动
> 是一种，卸载重挂是另一种。度量对齐只保证静止时对得上。

## 2.10 从 transcript 重建：第一轮只做了一半（第六轮补的）

作者删掉 `session.json` 之后继续聊，角色说它不知道之前的进度。

**症状是「稿面完好、模型失忆」**，这是最难自查的一种坏法：显示层的对话派生自
`transcript.md`，所以满屏记录一个字都不少，看上去完全正常；而
`seedRoleplayHistory` 只接一个 `firstMessage`，**从不回放过往轮次**，模型拿到的是
一段全新的历史。

设计（02-design §11）写的是「反序列化失败 = 从 transcript + memory.md 重建」，
而实现里只有 memory.md 那一半成立——记忆是每次播种都从盘上重读的，所以约定和
待办确实活了下来，这恰恰让故障更不明显。第一轮的实现记录把整条标成了「已实现」，
是一次**没有测试守着的文档断言**。

改法：`seedRoleplayHistory` 收 `priorTurns` 和 `priorSummary`，播种时回放。两条
约束写在 `selectReplayTurns` 里：

- **切片必须从作者轮开始**。轮的边界由 `noteTurnStart` 标在作者的提问上；若切片以
  角色轮打头，那条 assistant 消息会落在 prelude 里（第一个 turnStart 之前），
  压缩永远够不着它，它会一直占着上下文直到会话结束。
- **按字符封顶（`RESTORE_REPLAY_CHAR_CAP = 12000`），取最近的**。回放走的是**播种**
  那条路，而播种不经过压缩——几万字原样灌进去会当场撑爆首次调用。更早的事由
  `summary.md` 和 `memory.md` 承担，那正是它们存在的理由。

`summary.md` 一并接回来，`meta.summary` / `meta.summaryText` 都补上，位置与
`buildCompactedHistory` 摆放摘要的位置一致（prelude 末尾、turns 之前），下一次压缩
不用挪它。

> 教训：**「A 丢了就从 B 重建」这类断言，验证时必须验到模型那一层**。给作者的验证
> 清单写的是「对话是否仍在」——他看到对话仍在，答了「正常」，而两个人验的是同一句话
> 的两个不同意思。要问的应该是「角色还记不记得之前说好的事」。`context.test.ts` 现在
> 有 8 条守着这一组。

## 2.11 新开会话（第六轮补的）

在此之前，「这一场我想重来」的唯一办法是**删掉 agent 重建**——设定、绑定、人设卡、
记忆一起烧掉。不合理。

`newSession(agentId, { clearMemory })`：

- **封存靠 `rename`，不靠改写。** transcript 是只追加、永不改写的资产（不变量一）；
  移动一个文件不违反它，就地清空则会。`transcript.md` → `archive/transcript-NN.md`，
  `summary.md` 同理。
- **编号按已有文件名解析出的最大值 + 1，不按文件个数。** 作者手动删掉中间一场之后，
  按个数会撞名，直接覆盖掉另一场的记录。
- **`session.json` 直接删。** 它按定义就是缓存，而且封存它毫无意义——一段接不回任何
  transcript 的 wire history 谁也读不懂。
- **记忆默认不动**，作者在确认条上勾选才一并封存。这一条是有意的：记忆是角色的长期
  知识，本就设计成能跨越压缩活下来；换一场戏不该让角色忘掉你们约好的事。「推倒重来」
  是另一种意图，所以给一个勾选项，而不是替作者选。
- **跑着的时候拒绝执行**，否则正在写的那一轮会追加到一个已经被移走的文件上。
- `boundHash` 一并清空——它是「设定已更新」的基线，新的一场还没播种过，没有基线可比；
  留着旧的会让提示按上一场的状态亮（`checkBindings` 跳过 `boundHash === null` 的 agent，
  所以清空是安全的）。

**入口在编辑抽屉的 footer**，两段式：点「新开会话」footer 就地换成确认条（勾选项 +
一句说明 + 取消/确认）。没有弹模态——一个只有一句话加一个勾的模态，比它要确认的动作
本身还重。

### 存档是只读的，而且旁白也看不见

`ArchiveViewer`（稿面顶部的「此前已封存 N 场」进入）能读，不能续。能继续的会话只有
一个，这就是「存档」这个词的全部含义。

旁白的 scene 工具**只读当前 transcript**，读不到 archive。这是这一轮的取舍而不是遗漏：
`list_scenes` 现在返回「每个 agent 一场」，把存档并进去就得回答「第 3 场是谁的第 3 场」——
那是「场」数据模型的问题（见 §3 的场次分隔线一条），不该在这里顺手定一个。作者要让
旁白读旧场次，目前的办法是把那段文字贴给它。

## 3. 与设计稿的差异（明确没做的部分）

| 设计稿里的东西 | 为什么没做 |
|---|---|
| 场次分隔线「第 3 场 · 夜 · 西厢」 | 需要一个「场」的数据模型（谁划分、怎么命名、能不能改）。它是一个独立的小设计，不该顺手猜一个出来。 |
| 窄窗口 < 820px 的 56px 头像轨 | tab 的三档收紧做了（gap 28 → 18 → 14）；头像轨是花名册的第二套布局，等真的有人在那么窄的窗口里用再说。 |
| 绑定选择器头部的分类计数 chips（人物 12 / 场所 9…） | 现在是一个搜索框。分类过滤在条目多起来之前是纯装饰，而它要和 `loreCategories()` 的动态分类对齐，不是一行代码。 |
| 执行日志那行「查了 3 项设定 · 沈砚/寡言、… · 1.4s · 2.3k tok」 | 折成「执行日志 · N 步」，展开是现成的 `AgentLog`。设计稿那行要的字段散在三处，而 `AgentLog` 已经把它们都渲染好了——为一行摘要再拼一遍是重复实现。 |
| `@` 插入后的芯片行 | 现在只在输入框脚注显示「N 项引用」。芯片要能单独移除，那是 `AgentChat` 里已有的一套 UI，值得抽出来共用而不是抄一遍——留给下一轮。 |
| 首次使用默认展开语法提示 | 默认折成一行。「第一次」需要一个 pref，而这条提示折起来也已经写着四种标记了。 |

## 3.5 对话助手有、扮演还没有的

都是可以整体搬过来的既有组件，这一轮为了先把主干跑通没接：图片附件（`send` 里
`allowImages: false`）、引用选中的正文段落、上下文构成条（`contextBreakdown`）、
子代理的会话级开关 chips、任务工作区入口、片段插入。另外 `RoleplayAgent.authorPersona`
（每个 agent 单独覆盖「我此刻是谁」）类型有、UI 没有，目前恒为 null，永远走全局设置。

## 4. 新增的设计令牌

`--rp-*` 家族（`src/styles/tokens.css`，深浅各一套），沿用 `--lore-*` / `--stg-*` /

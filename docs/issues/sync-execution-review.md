# 同步执行器审查（2026-10-09）

> 状态：`open`——连接与对比状态修复期间的源码审查发现；下列三项尚未修复。
> 没有连接作者的服务器，也没有在真实项目上执行推送或拉取。

## P1：拉取落地前没有复核本地目标

`src/lib/sync/run.ts` 的 `pullStep()` 校验下载包的哈希和预览的 `sourceHash`，
但没有把本地目标此刻的哈希与预览的 `targetHash` 比较。删除分支也直接
`displace()`，没有复核。

触发：预览拉取方案 → 编辑本地同一条目（或外部程序改动它）→ 确认拉取。
新编辑仍会被移到备份，然后由远端内容替换；预览没有展示这份新编辑。
条目备份与拉取前全树备份仍在，所以不是不可恢复删除，但用户需要手工找回。

后续修复应在覆盖、删除前重新核对本地目标（包括预览时不存在、此刻新建的情况），
发生变化则跳过该步并要求重新预览。测试应覆盖新增、覆盖、删除三个分支，
以及下载期间本地发生变化。不要把此类错误描述成「服务器发生变化」。

## P1：绑定的服务器地址没有在执行入口校验

`SyncBinding.serverUrl` 被保存和读取，但 `refreshCounts()`、`startPreview()` 和
`confirmRun()` 都使用装机级的当前 client，没有核对它是否仍指向绑定里的服务器。

触发：项目已绑定服务器 A → 在管理连接中改为服务器 B → 点击推拉。
请求会使用 A 的 `kbId` 访问 B。库标识不存在时表现为失败；如果 B 有同一标识
（例如克隆的服务器），则预览和写入会指向另一份数据，而绑定仍记录 A。

后续应把已连接的服务器身份与绑定身份一起验证；不匹配时明确要求重连原服务器
或重新绑定，比较、预览、确认三个入口均应拒绝继续。测试需覆盖两台服务器存在
相同 `kbId`，以及预览后才更换服务器的情况。

## P2：拉取前全树备份的文件名会碰撞

`backupLoreTree()` 只用分钟时间戳和项目文件夹的末级名称拼接文件名。
同一分钟对同一项目连续拉取，或者两个同名项目拉取，会得到相同路径。
`renamePath()` 落到 Rust 的 `std::fs::rename`，在允许覆盖已有目标的平台上，
后一次备份会替换前一次；在拒绝覆盖的平台上，第二次拉取会失败。

源码注释认为同一分钟的两次拉取对应相同的拉取前状态，这不成立：第一次拉取
已经改了本地内容。后续应使用唯一的备份文件名，保留每次操作之前的快照；
用固定时钟测试同一分钟两次拉取及两个同名项目，确保返回不同的备份路径。

## 本次已核对的边界

- HTTP 写入携带 `If-Match` / `If-None-Match`，412 转为冲突。
- 推拉从 `startPreview()` 进入预览；连接与对比只读，不会调用执行器。
- 拉取在逐条落地之前先备份全树，替换与删除使用移动备份；下载包先验哈希。
- 快照按已成功条目前进，跳过和失败的条目不冒充已同步。

这些结论来自代码审查与模拟边界的测试，不代表真实网络与所有平台的端到端验证。
